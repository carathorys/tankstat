# Backup and restore

For operators: what a backup of a Tankstat instance is, how to make one, how to keep it safe, and how to get the data out of it again.

An instance's data is spread over the database (SQLite, PostgreSQL, SQL Server or MySQL), the uploaded pictures and photos (`Storage:Path`, and `Storage:PhotosPath` where set), the keys that protect the sign-in cookies and the stored refresh secrets (`DataProtection:KeysPath`) and [the app's own settings file](configuration.md#the-apps-own-settings-file) (`Settings:Path`). A backup is one file with all of it, the settings file with what was set on the *Server settings* page (the sign-in mode among them) included; settings held by **environment variables** are named in it, or with `Backups:Environment=Merge` carried in its copy of the settings file ([What is in the file](#what-is-in-the-file)), and a restore on a server where one of them would have no value is refused. The tables come from one consistent read of the database (a live SQLite file is copied with its backup API, never with `cp`; a server database is read inside one transaction that sees one snapshot: `REPEATABLE READ` on PostgreSQL and MySQL; on SQL Server `SNAPSHOT` isolation where the database allows it, which it does not by default (`ALTER DATABASE <name> SET ALLOW_SNAPSHOT_ISOLATION ON`), else `SERIALIZABLE`, which is just as consistent but makes writers wait while the tables are read, and the log warns about it). The pictures, photos and keys are copied after the tables, once that read has ended, not in the same snapshot: a file uploaded meanwhile is simply not in the backup, or is in it without a row.

A backup in the backups folder is a **restore point**: the instance can be taken back to it at any time (below). Administrators find them on the administration page too ([below](#on-the-administration-page)), and the app can write one every day and remove the old ones ([Schedule and retention](#schedule-and-retention)).

## Making a backup

The commands run inside the application (every setting applies, no server is started), with the same environment the server runs with:

```sh
# Docker: the file lands in /data/backups (a folder of the volume)
docker exec tankstat dotnet Tankstat.Api.dll backup

# without Docker, from the published build, with the server's environment variables set
dotnet out/Tankstat.Api.dll backup
```

`backup` writes `tankstat-backup-<date>T<time>Z.zip` into `Backups:Path` (default `backups` next to the working directory's database; the Docker image uses `/data/backups`) and prints what went in. Options:

| Option | Meaning |
| --- | --- |
| `--output <file>` | write to this file instead (never overwrites an existing one: that is refused before anything is written) |
| `--photos` | take the photos of logs along when they have a root of their own (`Storage:PhotosPath`); same as `Backups:Photos=true` for this run |
| `--environment record\|merge` | what this run does with the settings environment variables hold, over `Backups:Environment` (below). The command records and merges the environment of **its own process**: run it with the server's (`docker exec` has it; a cron job on the host does not) |
| `--passphrase-stdin` | encrypt this one backup for a passphrase read from the standard input (one line), with a fresh salt; the manifest says how to derive the key again |

The server may run meanwhile. **An upgrade backs up by itself**: a start that finds database migrations to apply on a database that holds data writes a backup first (a safety net, `safetyNet: true`, encrypted and with the photos as the settings say), and only then migrates; when that backup cannot be written (the backups folder or its disk, settings that do not validate), nothing is migrated and the start stops with the reason in the log. A new, empty database is not backed up, and neither is one a waiting restore replaces: a restore writes no backup at all (see [Restoring a backup](#restoring-a-backup)). A start also removes the backups a stopped run left half written (`*.zip.partial`), but only one that no process holds open: a run keeps its file open while it writes it. On Linux that is an advisory lock, which the processes of one host honour; on a network share used by several servers at once it may not be, and a file another server is still writing could then be removed (that backup fails). To keep a backup of your own until the new release has proved itself, with retention on ([Schedule and retention](#schedule-and-retention)), write it under a name of its own (`--output`), since retention counts the command's `tankstat-backup-...` files with the app's.

Run the command in the server's working directory too: the relative defaults (`tankstat.db`, `uploads`, `keys`, `backups`) are resolved from it. A SQLite database that is not there is refused, never created, and when the database lists pictures but neither storage folder is found, the log warns that none of their files is in the backup. A database a newer release has already migrated is refused (`backup.databaseNewer`): this release would leave out what it does not know, so back it up with that release. When the app's own settings file was left out at start (the server logs why), `backup` says so on the standard error and writes the backup without it.

## What is in the file

The backup is a zip (stored, not compressed), readable with any zip tool:

| Entry | Content |
| --- | --- |
| `data.age` (encrypted) or `data.zip` (plain) | the inner archive, see below |
| `settings.age` (encrypted) or `settings.json` (plain) | the app's own settings file, when the server has one: an entry of its own, so a restore can read it without unpacking the data. See below |
| `manifest.json` | in plain, always: the app version, the database provider and its last migration, when it was written, every table with its row count, which files and keys went in, the sizes, the SHA-256 of the inner archive, whether the settings file went in (with its SHA-256 and the names of the settings it left out), and for an encrypted backup the recipient, the salt and the Argon2id parameters. Nothing personal: no names, e-mails, paths or values |

**The settings file in the backup** is the file as it is on disk when the backup starts (so a setting saved on the *Server settings* page that still waits for a restart is in it), with what belongs to the instance: every setting of the *Server settings* page and the `Logging` section. What describes the machine stays out (a database connection, a folder, the keys folder, the settings file's own place, the backups folder, the first administrator's credentials, the prompt file), and so do the secrets in a plain backup (the OIDC client secret, the SMTP password, the model API key), as the keys do: an encrypted backup carries them. The manifest names what stayed out, never a value. A server without a settings file writes none, and one whose file the start left out writes none either (until a save on the *Server settings* page replaces it): the manifest says which. **Settings held by environment variables** are what `Backups:Environment` decides: `Record` (the default) names them in the manifest, by variable (`Auth__Mode`, a list once: `Auth__AdminEmails`), never a value; `Merge` also puts the values the server runs with into the backup's copy of the settings file (never into the server's own file; a list whole; a secret only into an encrypted backup), so a restore elsewhere brings them, and a server with variables but no file (or one its start left out) gets a file in its backup. Either way the manifest names the machine's own variables too (the database, the folders, the first administrator's), which never travel.

`unzip -p <file> manifest.json` prints the manifest. The inner archive holds:

| Folder | Content |
| --- | --- |
| `tables/<Table>.jsonl` | every table of the database as JSON Lines: one object per row, the column names as in the database, typed values (strings for ids and dates in ISO 8601 UTC, numbers, booleans, `null`, base64 for binary). Ids and versions are kept as they are, because devices with offline data refer to them; the sync ledger, tombstones, parked changes, sessions and notifications are tables like any other. `__EFMigrationsHistory.jsonl` records which migrations the database had |
| `files/pictures/...` | everything under `Storage:Path`: profile pictures, vehicle pictures, the files from older versions, and the photos of logs when they live there (the default). Never the `drafts` folders (photos of entries not saved yet, which live a day). A folder the app cannot read (the `lost+found` of a disk mounted there, say) is left out, with a warning in the log |
| `files/photos/...` | a photos root of its own (`Storage:PhotosPath`), only with `Backups:Photos=true` or `--photos`: the photos of refuellings and expenses grow without limit, so they are left out unless asked for. Back that folder up with a file tool (restic, rsync) on its own schedule otherwise |
| `keys/*.xml` | the Data Protection keys, **only in an encrypted backup**: the key files hold their key in plain, and with them the stored refresh secrets are readable. A plain backup leaves them out; restored from it, every device signs in again once |

A backup never holds the backups folder itself: `Backups:Path` must be a folder of its own, neither a storage root nor inside one nor holding one (the app refuses to start otherwise).

## Encryption

A backup should be encrypted: the file can then be kept anywhere (another machine, a cloud bucket) and a copy of it is not a copy of your data. The format is [age](https://age-encryption.org) exactly (version 1, one X25519 recipient, ChaCha20-Poly1305 in 64 KiB chunks), so the real tool opens the inner archive without Tankstat: `unzip -p <file> data.age | age -d -i identity.txt > data.zip`.

The key pair comes from a passphrase: Argon2id (64 MiB, 3 passes) of the passphrase and a random salt is the identity (the secret key), its public key the recipient. **The server keeps only the recipient and the salt**, so nothing on the server can read its own backups. Set it up once:

```sh
echo 'correct horse battery staple' | docker exec -i tankstat dotnet Tankstat.Api.dll backup keygen --passphrase-stdin
```

It prints two settings and the identity:

```text
Set these two settings (as environment variables or in the configuration), then every backup is encrypted for this passphrase:
  Backups__Encryption__Recipient=age1...
  Backups__Encryption__Salt=...
The identity below opens every backup made for this recipient, with age (age -d -i) or tankstat decrypt --identity; ...
Saved as it is, the next line is an identity file (age takes no space before the key):
AGE-SECRET-KEY-1...
```

Set the two settings (both, or neither, and both from the same key set) and restart, or save them on the *Server settings* page (or with **Use these keys for new backups** on the Backups page, [below](#on-the-administration-page)), which applies at once; from then on every `backup` is encrypted for that recipient and the manifest names it. Keep the passphrase: the identity is derived from it and the salt in every manifest, so the passphrase alone is enough. **Losing the passphrase (and the identity) loses the backups, by design**; nothing on the server can recover them. The passphrase is only ever read from the standard input, never taken as an argument (the process list and the shell history would keep it). A new passphrase (`keygen` again, new settings) applies to the backups written after it; the older files stay under their recipient, which their manifest says.

## Opening a backup

```sh
# with the passphrase (the manifest carries the salt and the parameters)
echo 'correct horse battery staple' | dotnet Tankstat.Api.dll decrypt tankstat-backup-20261011T020000Z.zip --output restored --passphrase-stdin

# with the identity keygen printed (a file holding the AGE-SECRET-KEY-1... line; lines starting with # are ignored)
dotnet Tankstat.Api.dll decrypt tankstat-backup-20261011T020000Z.zip --output restored --identity identity.txt

# a plain backup needs no key
dotnet Tankstat.Api.dll decrypt tankstat-backup-20261011T020000Z.zip --output restored
```

`decrypt` checks the manifest and the checksum, derives the identity and checks it against the recipient **before** anything is unpacked (a wrong passphrase is refused at once), then unpacks `tables/`, `files/` and `keys/` into the folder (which must be empty; one that `decrypt` creates is readable by you alone, since the data and the keys land in it in plain), and the settings file as `settings.json` beside them (readable by you alone too: an encrypted backup's holds the secrets). A backup of a newer format than this release reads is refused, and so is a zip that is not a Tankstat backup.

## Restoring a backup

A restore replaces the instance's data **as a whole**, never merges: every table, the pictures (and the photos when the file holds them), and the keys of an encrypted backup. It happens at a start of the app, after the database migrations and before anything else looks at the data, so it works into an empty database as well (a new volume after a disaster, or a move to another machine or database provider: set the new database up, put the backup and the marker in place, start).

**Asking for it.** Either from the app or from the command line; both leave a small marker, `restore.pending`, in the backups folder, and the next start applies it:

- From the app: an administrator (on the **Backups** page of the administration, or through the GraphQL mutation `restoreBackup(input: { file, passphrase | identity })`) names a backup of the folder and gives its passphrase (or the identity). The passphrase is checked against the backup's recipient **before** anything is written, so a wrong one is refused at once, and so is a backup made by a newer release, at a migration this release does not know (the start would refuse it anyway), and one that is no longer in the folder (deleted meanwhile); then the server restarts in its own process, as *Restart the server* on the settings page does (the container keeps running, no restart policy is needed), and the restore is applied as it starts. A restart the next start would refuse is refused as well, and nothing is written: with the settings file the backup brings, as the restore would leave it under this server's environment (an OIDC sign-in without its client secret, which a plain backup does not carry and this server does not set, say), or, from a backup without one, with this server's own file (changed by hand into one the app cannot start with). Until that start a notice says a restore is waiting. With sign-in off (`Auth:Mode=None`) there is no administrator, so the one operation that replaces everything is guarded by a **one-time restore code** (`XXXX-XXXX-XXXX`; case and hyphens do not matter), written to the server's log at every start (`docker logs tankstat`): whoever reads the log may restore, nobody else. The same code restores a backup into a new instance while it waits for its setup, in every mode, since no administrator exists yet; the setup page also uploads a backup into the folder with it (as *Upload a backup* below, the code in the `X-Setup-Code` header of `PUT /media/backups`), so moving to a new server needs no copy into its folder by hand.
- From the command line, with the server's environment: `dotnet Tankstat.Api.dll restore <file> [--yes] [--now] [--identity <file> | --passphrase-stdin]`. The file is named as it is in the backups folder. It says what the backup brings of its server's settings and what this server lacks of them; without `--yes` it says what it is about to replace and asks for `yes` on the standard input (before the passphrase line, when both come from there). Without `--now` it leaves the marker for the next start of the server; **with `--now` it applies the restore right away, which is only for a server that is not running** (two processes on one database would get in each other's way), and says whether it was applied, refused (the data is as it was) or failed after the data was replaced (the backup is still in the folder to try again; the data from before it is gone); the exit code is 0 only when it was applied. A backup made by a newer release is refused before the marker is written, as the app refuses it.

**What a backup's server set in its environment needs a value here.** A restore is refused, at the request and again at the start, when a setting the backup recorded (above) would have no value on this server: neither this server's environment sets it nor the settings file the restore leaves holds it (a `Merge` backup's does, but for the secrets of a plain one). The refusal names the variables; set them, then restore. Your server's own values run, as always: only a missing one stops it, so a moved server never comes up with another sign-in mode, or without its e-mail, because a variable was forgotten.

**What the start does.** A waiting restore comes first, before the database migrations and before anything else of the start (as `restore --now` applies it), and **writes no backup of the data it replaces**: the backup you restore is the one there is, and whatever changed on the server since it was made is gone for good. In order, each step logged: reads the manifest and checks the checksum; refuses a backup made by a **newer release** (at a migration this release does not know; the error names both); a backup made by an **older release** is restored and brought up to date, as described below. Migrations are compared by name, not by id: every database provider has its own copy of each migration, with its own timestamp, so a backup made on one provider is the same migration on another; checks the identity against the recipient; reads the settings file the backup brings and judges the file the restore would leave as this server would run with it (refused when it would not start with it); unpacks the file into a temporary folder; in `Standalone` mode (the sign-in that restored settings file gives here, else this server's) refuses a backup that holds no enabled local administrator when none can be created from `Auth:Standalone:AdminEmail` and `AdminPassword` (else no start could succeed afterwards: set the two and ask again), unless neither is set and the backup's own setup still waits (a backup of a new instance), whose restore then waits for its setup too; loads every table, in one transaction when the database is at the backup's migration already (the database is as it was if that fails), else as described below; replaces the contents of the pictures folder (what the app may not remove there, such as a disk's `lost+found`, stays), of the photos folder when the backup holds one, and the key files of the keys folder for an encrypted backup; writes the backup's settings file over this server's (the previous kept as `settings.json.bak`), keeping what no backup carries: this server's own machine settings and, restoring a plain backup, its secrets; then the migrations run, and the marker goes. When a settings file was written, the server restarts in its own process at once, before it serves anything, so it runs with the restored settings (environment variables still win, as always). A refused restore renames the marker to `restore.refused.<time>`, and the app starts with its data as it was, backing it up first when migrations are pending, as any upgrade does; a failure after the data was replaced (the files half copied, say) renames it to `restore.failed.<time>`, and the start goes on with no backup: the backup is still in the folder to try again. A renamed marker no longer holds the identity of an encrypted backup (it opens every backup of the folder). Nothing the start meets here stops the app: a marker or backup it may not read is refused like any other.

**A backup of an older release.** Each release knows every migration before its own, and how the database looked after each one. A backup made at another migration than the database is at (an older release's, or the database is the one still waiting for its upgrade) is restored the way the database got there: once the checks above passed (including, in `Standalone` mode, the administrator, and every row as the load will read it, its counts against the manifest's, all read from the backup's own files), every table is removed, the database is set up as that migration left it, the backup is loaded into it, the newer migrations run, and what follows them is done (the fuel consumption worked out, for one), as an upgrade would; the generation is renewed last. An empty database is set up the same way, with nothing to remove. The tables are removed in one transaction wherever the database allows it (all but MySQL): one it will not drop, because a view or a foreign key of your own refers to it, undoes the others, and the restore is refused with every table and row as they were. Once the tables are removed this cannot be undone: a failure from there on renames the marker to `restore.failed.<time>`, the migrations set the schema up to date again, and the data from before the restore is gone (no backup of it is written); restoring the same backup again is the way on (in `Standalone` mode, an emptied database needs the bootstrap credentials to start, or the backup restored with `restore --now`). The Backups page marks such a backup as holding the database as an older release left it, and its restore dialog says so; a safety net written before an upgrade is one too, though the new release wrote it, so the row's release is the one that wrote the file, not the one whose database it holds.

**Afterwards.** Everyone is signed out when the keys changed (a plain backup holds none, so restoring one signs everyone out once). The sign-in sessions of the backup work again with its keys, except those of a backup made before the instance recorded its sign-in mode (an older release's): nothing says which mode they were issued in, so they end, and everyone signs in again. **Photos the backup does not hold** stay on disk and keep matching their logs (they are never deleted by a restore, also where they live with the pictures); a photo of a log the backup does not know is left alone too. A missing photo shows a placeholder, never breaks a page.

**Devices with offline data.** Every device refers to the server's entries by their ids and versions; after a restore the server's history is another one (changes made after the backup are gone, versions moved back). The server tells every session which history its data belongs to (a *generation* that the restore renews), and a device that sees a new one sets what it holds aside, drops its downloaded data and kept screens, and downloads afresh. Its changes still waiting are sent as they are and apply or park by the normal rules, so nothing is silently lost; what it held and the server no longer has shows under **Found on this device** on Waiting to sync, where each entry can be sent to the server again or forgotten (see [Install as an app](install-as-an-app.md)).

## On the administration page

The **Backups** page of the administration (`/admin/backups`, in the menu's Administration group; administrators only; with sign-in off there is none, so the commands above are the way) shows:

- **This server**: the backups folder in full (where to copy a file in or out), the size of the database and the migration it is at, the size of the pictures and of the photos (when they have a folder of their own), whether backups are encrypted and for which recipient, whether they take the photos along, the schedule with the next run, what retention keeps, and what backups do with the settings from the environment (`Backups:Environment`).
- **Back up now**: the server writes a backup in the background, one at a time (a second press while one is being written waits for that one), with the settings above, so encrypted and with the photos exactly as the command would; the tab follows it and says when it is written or why it failed. Leaving the page does not stop it.
- **Upload a backup**: a backup file of another server, or one downloaded earlier, up to `Backups:MaxUploadMb` (1024 MB by default). It is streamed to disk, checked (its manifest and its checksum) and stored as `uploaded-<its name>.zip`, never over another file; anything that is not a backup, or is larger, is refused and leaves nothing behind (a larger file is refused on the page before anything is sent). A proxy in front of the server may have a limit of its own (nginx: `client_max_body_size`). A larger file can always be copied into the folder by hand; give it a name that does not start with `tankstat-backup-` (`uploaded-<its name>.zip`, say), or retention takes it for one of the app's own ([below](#schedule-and-retention)).
- **Backups in the folder**: every `*.zip` file in the folder whose manifest can be read (a hidden one, a name starting with a dot, is left out), newest first, also one copied in by hand: a column each for when it was made (and its file), its kind (a backup, the safety net of an upgrade, or an upload), the release and database that made it, how many rows, whether it is encrypted (for the current key or another one), whether it holds the photos, and its size; the kind, the encryption and the photos are icons whose meaning a tooltip says (on hover, or from the keyboard). **Download** saves it (nothing else in the folder is ever sent, the waiting restore's marker with its identity least of all); **Restore** says first what the backup brings of its server's settings (its settings file, or why there is none, and the variables its server's environment set) and, as a warning, which of those this server sets none of, so the restore will be refused until they are set (for an encrypted backup that only recorded them, as if its settings file held none: it is read only with the passphrase, and the restore itself then judges it); the setup page's restore says the same; then it asks for the passphrase (or the identity) of an encrypted backup and restores it as described above. **Delete** removes it from the folder for good, after a confirmation (any backup listed: an upload or a safety net too; nothing else in the folder); while a restore waits for the next start nothing is deleted, as retention prunes nothing then either. A backup made by a newer release has no Restore button: the row names the release that can restore it. One made at an older migration has one, and the row and its restore dialog say that it is brought up to date as it is restored. After a restore the tab waits for the server to come back and reloads the page once it serves the restored data; a server that comes back without the restore (it was refused) is said so, the log says why.
- **Make a key set**: the same as `backup keygen`, on the server: a passphrase you type (at least 12 characters) or one it makes up (five groups of four letters and digits), the identity, and the two settings it needs (`Backups:Encryption:Recipient`, `Backups:Encryption:Salt`). The passphrase and the identity are stored and logged nowhere (the log only says that an administrator made a key set): they are shown once, and the dialog does not close before you tick that the passphrase is kept, nor while the keys are being saved. **Use these keys for new backups** saves the recipient and the salt in the server settings, as the *Server settings* page does (its log line names the two settings, never their values), and every backup written after that is encrypted for them, without a restart; keep the passphrase before you use them, since from then on no new backup opens without it. Where the environment holds those settings the dialog says so, and the two variables it shows are the way instead (set them and restart).

## Schedule and retention

**The schedule.** With `Backups:Every` set to a time of day (`Backups__Every=02:00`), or several (`02:00, 14:00`), the app writes a backup at each of those times on every day of `Backups:Days` (every day unless it is set; `Backups__Days=Monday,Thursday`, the English names or their first three letters, and `None` for no day at all, which schedules nothing), with the settings above, exactly as **Back up now** does and through the same queue: a backup due while one is being written is that one, never a second. The time is the server's local time; a container runs in UTC unless it is given a time zone (`-e TZ=Europe/Budapest`). On the night the clocks skip that time (02:30 on the spring night in much of Europe), the backup is written the moment the clocks jump; on the night they repeat it, at the first of the two. Unset (the default), nothing is scheduled and the app says nothing about it. A time saved on the *Server settings* page is planned at once and logged as at the start, and clearing it there logs that backups are not scheduled any more; a save that leaves the time as it was never moves the backup it waits for, even when the clock already passed its time (a host that was suspended, say): that one is written at once.

**A missed backup.** When the app starts and the last due time passed without a backup since (it was down at 02:00), it writes that one at once, then goes on by the schedule. A new installation with a schedule writes its first backup at its first start that way (one that waits for its setup and holds nothing yet writes none until it does: the setup page would offer that empty backup as a restore point); that is this rule, not a fault. Only the app's own files in the folder count (safety nets and uploads do not), so a restore on the same server, whose folder still holds the night's backup, writes none at its start: the restored data gets its first backup at the next due time (press **Back up now** for one at once). For the same reason a backup moved out of the folder makes the next start write that night's again: copy backups elsewhere rather than moving them. A scheduled backup that fails is not tried again before the next due time, but a start in the meantime writes it as a missed one.

**Retention.** After every backup the app writes itself (scheduled or Back up now), `Backups:Keep` and `Backups:KeepDays` remove the old ones. Both are ceilings: a backup is removed when it is beyond the newest `Keep` or older than `KeepDays`, whichever are set; the newest one never goes, nor the one just written. The candidates are the files named `tankstat-backup-...` and written by Tankstat, whoever put them in the folder: the `backup` command's too (the command itself removes nothing), and one copied in by hand under that name. An upload (`uploaded-...`) or a file under another name is never one, so keep a backup you mean to keep, such as the one before an upgrade, under a name of its own (`backup --output /data/backups/before-upgrade.zip`) or outside the folder. While a restore waits for the next start, nothing is removed: the backup it names must still be there. The safety nets written before an upgrade are kept by a count of their own, the newest three, at the same moments (without a schedule, only when a backup is written on the page). With neither setting, nothing is ever removed, safety nets included; a schedule without either makes the app warn at every start, and when retention is cleared on the *Server settings* page while backups are scheduled, since the folder then grows until the disk is full. Retention runs once a backup is written, so the folder needs room for one backup more than it keeps; a backup that fails removes nothing, so one that fails for want of room fails again until room is made by hand.

**When a backup fails**, every administrator who is not disabled gets a notification (with sign-in off, the anonymous user, for whom there is no Backups page to follow it to: the log says more), once a day at most however often it fails that day; the administrator who pressed Back up now sees the reason on the page instead. The reason is also in the server's log, and the Backups page says why the last run failed (until the server restarts). A backup that the app's stop cuts short is no failure: the next start writes it as a missed one.

## Settings

Every one of them but the folder can be changed on the *Server settings* page too (its **Backups** tab, linked from the Backups page) and applies at once: a new time of day is planned as soon as it is saved, and the next backup takes the new encryption, photos and retention; a backup missed while the app was down is caught up only at its start. *Make a key set* on the Backups page saves its recipient and salt there with one button. The two are one pair: change them together, from one key set, or the passphrase no longer opens the backups written after the change (only the identity does). An environment variable wins over the page, which then shows the setting read-only. What the page saves goes into [the app's own settings file](configuration.md#the-apps-own-settings-file), which no backup holds: keep a copy of it with your backups, or a server set up again from a backup alone writes its backups in plain, and on no schedule, until they are set again. The folder itself is read once, at the start, like the storage folders.

| Setting | Environment variable | Meaning |
| --- | --- | --- |
| `Backups:Every` | `Backups__Every` | one or more times of day (`HH:mm`, the server's local time, commas between them) to write a backup; unset, nothing is scheduled |
| `Backups:Days` | `Backups__Days` | the days of the week those times apply to (`Monday,Thursday`); every day by default, `None` for no day (nothing is scheduled) |
| `Backups:Keep` | `Backups__Keep` | after each backup the app writes, keep only the newest this many of its own (at least 1); unset, no limit by count |
| `Backups:KeepDays` | `Backups__KeepDays` | after each backup the app writes, remove its own older than this many days (the newest stays); unset, no limit by age |
| `Backups:MaxUploadMb` | `Backups__MaxUploadMb` | the largest backup the Backups page (or the setup page, while the setup waits) uploads, in MB (default 1024); a larger one goes into the folder by hand, under a name that does not start with `tankstat-backup-` |
| `Backups:Path` | `Backups__Path` | where backups are written (default `backups`, relative to the working directory; the Docker image uses `/data/backups`, writable by its user). A folder of its own: not a storage root, not inside one, not holding one |
| `Backups:Environment` | `Backups__Environment` | `Record` (default) or `Merge`: what a backup does with the settings environment variables hold ([What is in the file](#what-is-in-the-file)); a restore where a recorded one has no value is refused |
| `Backups:Photos` | `Backups__Photos` | `true` takes a photos root of its own (`Storage:PhotosPath`) into every backup (default `false`: left out, as they grow without limit). No meaning while the photos live with the pictures: they are always in the file then |
| `Backups:Encryption:Recipient` | `Backups__Encryption__Recipient` | the age recipient backups are encrypted for, as `backup keygen` prints it; unset, backups are written in plain, without the keys |
| `Backups:Encryption:Salt` | `Backups__Encryption__Salt` | the salt the identity is derived with (printed with the recipient); set together with it, from the same key set, or neither |

## Moving an instance

A restore is also the move: on the new machine (or the new database provider, since the tables are loaded through the same typed path on every provider), set the same release up with its database, put the backup into its backups folder with the marker (`dotnet Tankstat.Api.dll restore <file> --yes --passphrase-stdin`, or `--now` before the first start), and start. The photos not in the backup go with a file tool. The settings file comes with the backup. What the old server set in its environment (its sign-in mode in a compose file, say) comes along only in a `Merge` backup, and its secrets only in an encrypted one; otherwise set them on the new server too (the same compose file does): the restore is refused until every setting the backup recorded has a value there. A backup written by a release before the settings file went in brings none, and a release before that one restores a newer backup's data and leaves its settings file out.

Every direction between SQLite, PostgreSQL, SQL Server and MySQL has been tried this way, with a database filled by the seeder (28 tables, nearly two thousand rows) and compared table by table after the move. What changes on the way: **timestamps are kept to the microsecond on PostgreSQL and MySQL** (SQLite and SQL Server keep a tenth of that, so the last digit of a timestamp moved to PostgreSQL or MySQL is dropped), and numbers keep their value but may get a different number of trailing zeros. A backup restores on the release that wrote it or any later one, whatever the provider on either side; a later release brings it up to date as it is restored.
