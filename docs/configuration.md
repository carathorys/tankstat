# Configuration

For operators: the database, uploaded files, defaults, notification limits, the app's own settings file and the log. Authentication has [a page of its own](authentication.md).

Every setting below can be given in `appsettings.json`, in [the app's own settings file](#the-apps-own-settings-file) or as an environment variable, where `:` becomes `__` (double underscore). The order is the standard ASP.NET Core one with that file added, lowest first: `appsettings.json` < `appsettings.{Environment}.json` < the app's own settings file (`Settings:Path`) < environment variables < command line; a setting given higher up wins, so an environment variable (`Section__Key`) always overrides both files. The same holds for the [authentication](authentication.md) and [photo reading](photo-reading.md) settings.

## Database

The database is chosen through the `Database` section. If nothing is configured, the app falls back to a SQLite file, `tankstat.db`, in the working directory.

| Setting | Environment variable | Values |
| --- | --- | --- |
| `Database:Provider` | `Database__Provider` | `Sqlite`, `PostgreSql`, `SqlServer`, `MySql` (Oracle provider; MariaDB is not a tested target) |
| `Database:ConnectionString` | `Database__ConnectionString` | provider-specific connection string |

```sh
Database__Provider=PostgreSql Database__ConnectionString="Host=db;Database=tankstat;Username=app;Password=..." \
  dotnet out/Tankstat.Api.dll
```

The connection string may be omitted only for `Sqlite`. The app refuses to start if it is missing for another provider, or if the provider is unknown.

## Files, defaults and notifications

Uploaded pictures (profile pictures, vehicle pictures, photos of refuelings and expenses) are stored as files; only metadata is in the database. By default they all live in one folder, `Storage:Path`. The **photos of logs** (the photos of refuellings and expenses, and the drafts of entries not saved yet) are the part that grows without limit; setting `Storage:PhotosPath` keeps them in a folder of their own, so a backup or a disk of their own can take them as a whole. Below each folder the layout is the same:

| What | Folder below it |
| --- | --- |
| profile pictures | `Storage:Path` / `users/<id>/` |
| vehicle pictures | `Storage:Path` / `vehicles/<id>/picture/` |
| files from older versions (no folder) | `Storage:Path` itself |
| photos of refuellings and expenses | `Storage:PhotosPath` (unset: `Storage:Path`) / `vehicles/<id>/refuelings/<log id>/`, `.../expenses/<log id>/` |
| photos picked for an entry not saved yet | `Storage:PhotosPath` (unset: `Storage:Path`) / `vehicles/<id>/drafts/` |


| Setting | Environment variable | Meaning |
| --- | --- | --- |
| `DataProtection:KeysPath` | `DataProtection__KeysPath` | folder of the keys that protect the sign-in cookies and the stored refresh secrets (default `keys`, relative to the working directory; the Docker image uses `/data/keys`). Keep it with the data and back it up with it: without it every restart signs everybody out. The framework warns at start that the keys are stored unencrypted, which is expected; protect the folder like the database |
| `Storage:Path` | `Storage__Path` | folder for the pictures (default `uploads`, relative to the working directory; the Docker image uses `/data/uploads`). Files are organised per owner (table above), so a vehicle's files are removed with it; files from older versions stay directly in the folder and keep working |
| `Storage:PhotosPath` | `Storage__PhotosPath` | a folder of their own for the photos of logs; **opt-in**: unset (or blank), they stay in `Storage:Path` with the pictures and nothing is ever moved. It may be a disk or volume of its own (the Docker image has `/data/photos` ready for one). Never one folder inside the other: the app refuses to start then. Once it is set, the photos already in `Storage:Path` are moved there at the next start (one by one, so it also works between two disks; one that cannot be moved stays where it was, is still shown, and is logged as a warning). Make sure the folder is kept (a volume, not the container's own disk) and writable by the app before that start. There is no move back: to undo it, move the files back into `Storage:Path` yourself and unset it |
| `Backups:Path`, `Backups:Photos`, `Backups:Environment`, `Backups:Encryption:*`, `Backups:MaxUploadMb`, `Backups:Every`, `Backups:Days`, `Backups:Keep`, `Backups:KeepDays` | `Backups__...` | where backups are written, whether a separate photos root goes in, whether the settings environment variables hold are only named in a backup or merged into its settings file, the recipient they are encrypted for, the largest upload on the administration page, the days and times of the schedule and what retention keeps: see [Backup and restore](backup-and-restore.md) |
| `Defaults:DistanceUnit`, `Defaults:VolumeUnit`, `Defaults:Currency` | `Defaults__...` | what a new vehicle / new log starts with (`Kilometers` / `Liters` / `EUR` unless changed) |
| `Defaults:RecurringWarnDays`, `Defaults:RecurringWarnDistance` | `Defaults__...` | how early a new recurring expense starts warning (`30` days / `500` in the vehicle's distance unit unless changed; every schedule can override it) |
| `Defaults:TimeFormat`, `Defaults:DateFormat` | `Defaults__...` | how times (`TwentyFourHour`, `TwelveHour`) and dates (`Iso`, `DayMonthYearDots`, `DayMonthYearSlashes`, `MonthDayYear`, `YearMonthDayDots`) are written for everyone who chose no format in the language menu; unset, as each person's language writes them |
| `Notifications:MaxPerHour` | `Notifications__MaxPerHour` | how many notifications about events (such as access changes) a user gets in an hour before further ones are only counted (default `20`, at least `1`; recurring-expense reminders do not count) |
| `Notifications:ReadRetentionDays` | `Notifications__ReadRetentionDays` | how many days a notification is kept after it was read, then it is removed (default `30`, at least `1`; unread ones are kept) |
| `Sync:RetentionDays` | `Sync__RetentionDays` | how many days the server remembers the changes devices sent and it applied, so a device that sends the same changes again (an answer it never got) is answered with what happened instead of applying them twice (default `30`, `1` to `3650`). Changes it could not apply (parked) are kept until someone decides |
| `Sync:TombstoneRetentionDays` | `Sync__TombstoneRetentionDays` | how many days the server remembers what was removed for good (an emptied trash, a deleted schedule, a purged vehicle), so devices that keep data for offline use drop it too (default `90`, `1` to `3650`). A device whose last download of a vehicle is older starts that vehicle afresh. Old entries are cleared at most once an hour, when a device downloads |
| `Settings:Path` | `Settings__Path` | the app's own settings file (default `settings.json`, relative to the working directory; the Docker image uses `/data/settings.json`, in the volume with the database). See the next section |

## The app's own settings file

Besides `appsettings.json` and the environment, the app reads one JSON file of its own at start: `Settings:Path`. It is the file the app itself writes, where the settings an administrator changes from inside the app are kept, so it lives with the data (the Docker image puts it in the `/data` volume), every backup carries it, and it is never part of the image or of the repository. You can also write it by hand. It has the shape of `appsettings.json`: the same names, nested, a list as an array:

```json
{
  "Auth": { "Mode": "Standalone", "PublicUrl": "https://tankstat.example.com" },
  "Smtp": { "Host": "mail.example.com", "From": "tankstat@example.com", "Password": "..." },
  "Defaults": { "Currency": "HUF" },
  "Logging": { "LogLevel": { "Tankstat": "Debug" } }
}
```

Switching an instance that has no administrator yet to `Standalone` also needs the first administrator for that start, `Auth__Standalone__AdminEmail` and `Auth__Standalone__AdminPassword` ([Authentication](authentication.md)); without them the app does not start, as when the mode comes from the environment on an instance that is set up. (A new instance, one still waiting for its setup, waits for its first administrator instead.)

What to know about it:

- **The environment wins.** The file sits below the environment variables and the command line and above the `appsettings` files, so a value you set in the environment (`Auth__Mode` in a compose file, say) is what runs, whatever the file says. That holds for the `Section__Key` variables; the `ASPNETCORE_`-prefixed ones rank below both files, as in any ASP.NET Core app (a `urls` key in the file would beat the image's `ASPNETCORE_URLS`). A list is merged item by item: `Auth__AdminEmails__0` in the environment replaces only the file's first address, and the file's other addresses still count (the same goes for `Auth__ProxyHeader__TrustedProxies__*`); to override a list from the environment, remove it from the file. Keep the database (`Database:*`), the folders (`Storage:*`), the key ring (`DataProtection:*`), the listen address (`urls`, `Kestrel:*`) and the file's own path in the environment: the app needs them before it can read anything, and the Docker image sets them there.
- **Backups carry it**, without the machine's own settings (the database, the folders) and, in a plain backup, without its secrets, and a restore writes it back over this file, keeping the previous as `settings.json.bak` ([Backup and restore](backup-and-restore.md#what-is-in-the-file)).
- **Secrets are stored in plain text** (an SMTP password, an OIDC client secret, a model API key). The app writes the file readable by its owner only (`0600`, the previous file is kept beside it as `settings.json.bak` with the same mode); keep a file you write yourself as private, and keep it out of version control.
- **A broken file does not stop the app.** Before the server starts, the app checks that it could start with the file: a file it cannot read (the app's user must be able to read it) or that is not valid JSON, a value of the wrong shape (`"Port": "abc"`), a rule broken (the OIDC mode without an authority, a log level that does not exist, a console logging option that cannot be read, a retention of `0` days) means the file is left out as a whole. The app then starts without it, writes one `Error` line naming the settings at fault (never the values written in them), and shows a warning notice (`SETTINGS_FILE_IGNORED`) to every visitor until the next start. Fix the file and restart. Everything in the file is left out with the mistake, an `Auth:Mode` set there too, so until then the app runs in the mode the environment or `appsettings.json` sets. One case is refused instead of left out: when that mode is `None` (the shipped one: no authentication, every visitor can see and change everything) while the file sets a sign-in mode, or cannot be read, the app does not start, and says why; fix the file, or set `Auth__Mode` in the environment, which wins over the file. Photo reading's settings never leave the file out (a wrong one turns photo reading off, as it does anywhere). This is deliberate and only for this file: a wrong environment variable stops the app at start as it always did, and what the environment gets wrong on its own is not held against the file, so a mistake in the file does not lock you out of an instance the environment runs. The check covers what the app checks before it starts, not what it only finds once running: a switch to `Standalone` without a first administrator (see above), or a database it cannot reach, still stops the start.
- **The file is not watched.** A change made to it by hand takes effect at the next start. A save on the *Server settings* page (below) reads the file afresh, after checking all of it, so the settings that apply at once take effect then, as they stand in the file.
- **Administrators change it from inside the app**, on the *Server settings* page (`/admin/settings`, administrators only, so not in mode `None`; `systemSettings` and `updateSystemSettings` at `/graphql` behind it): every setting of the tables on this page except the database and the folders, the [authentication and e-mail](authentication.md) settings except the first administrator's credentials, the [photo reading](photo-reading.md) settings except the prompt file, the [backup](backup-and-restore.md#settings) settings except their folder, and the shipped log levels, each with where its running value comes from (an environment variable, the file, the shipped `appsettings.json`, or the built-in default, which the page then shows as the value). A setting an environment variable holds is read-only there. A change is checked as a whole before anything is written, the same checks as the start (so, as there, a mistake the environment makes on its own that the app starts with anyway holds no change back) plus what only a running app can check (an OpenID Connect authority that answers with its issuer, an administrator to sign in with after a switch to `Standalone`), and it is written all or nothing, one save at a time (a file the app cannot read is replaced by a save only when the start left it out; otherwise fix it by hand first, since a save would drop everything in it, the sign-in mode too); `Logging:LogLevel:Microsoft.AspNetCore` and the categories below it are never set below `Warning`. A secret (an SMTP password, an OIDC client secret, a model API key) is written as typed and never shown back, only whether it is set; a blank leaves it as it is, *clear* removes it. The defaults (for new vehicles and schedules, and the time and date formats of everyone who chose none), the notifications, offline sync, the backups (a new time of day is planned at once) and the log levels take effect as soon as they are saved: the configuration is read afresh after the save, and these settings are read anew where they are used (per request; the log levels by the logging framework at once). The sign-in, e-mail and photo reading settings are read once at start, so a change of them waits for a restart, and only such a setting is marked as waiting on the page: *Restart server* on the page (`restartServer`) restarts the server in its own process (the container keeps running, the health check sees a few seconds without an answer; a `docker stop` during the restart still stops it). A start that fails ends the process, so a restart the next start would refuse is refused instead (`settings.restartWouldFail`: a settings file edited by hand since that it would not start with; or a switch to `Standalone` without a first administrator it could create); one that fails for a reason only the start finds, such as a database out of reach, still stops the server; several instances on one database each restart themselves, and each reads the file at its own start.

## Logging

The app writes its log to the console (`docker logs`, the terminal) with the standard .NET logger; there is nothing to install. The shipped `Logging` settings in `appsettings.json` keep the app's own lines (category `Tankstat`) at `Information` and silence what used to drown them: Entity Framework's SQL commands and the HTTP client's per-request lines.

| Level | What is logged |
| --- | --- |
| `Error` | an unexpected error, with its exception and stack trace (the client only sees "Unexpected Execution Error"); the app's own settings file left out at start, naming the settings at fault; a restore the start refused (the reason's key; the data is as it was) or that failed after the data was replaced (no backup of the data from before it is written; the backup is still in the folder to try again) |
| `Warning` | a refused request (no access), a failed sign-in, a failed password change, a lockout, a refused sign-in through an identity provider, a malformed or untrusted proxy header, a database or model server that cannot be used, a setup or reset link whose e-mail could not be sent (an administrator gets the link to hand over; a link a user asked for is taken back, so they can ask again), too many reset requests waiting to be sent, an upload folder that could not be removed, the app's own settings file that the system settings could not write, a photo of a log that could not be moved to the photos folder at start, a photo that could not be attached, a field the server answered with nothing although it must have a value (a bug of the server's: the request fails for the client), a folder below a storage root that a backup cannot read, a backup's read transaction that could not be rolled back (its connection broke), a backup whose database lists pictures while no storage folder is found, something below a storage root that a restore may not remove (it stays), the temporary folder a restore unpacked into that could not be removed (it is named: it holds the backup's data in plain), a backup (started on the administration page or by the schedule) that failed for a known reason (its key), a backup schedule with no retention set (at every start, and when retention is cleared on the settings page while backups are scheduled), backup settings that stop being usable while the app runs (an `appsettings.json` edited by hand reloads on its own: said once, naming the settings, and no backup is scheduled until they are fixed), a backup retention could not remove or a backups folder it could not read, and the one-time code while a new instance waits for its setup (the line starting `Setup is waiting`: a `Warning`, so a log kept to warnings still shows it) |
| `Information` | start-up (database migrations applied or up to date, the app's own settings file in use, every device signed out because the authentication mode changed, the photos of logs moved to their own folder, the first administrator), an administrator's change of the system settings (by the names of the settings) and restart of the server, sign-ins and sign-outs, password changes and reset requests, what an administrator does to users and to access, sharing a vehicle's logs, imports, emptied trashes, a backup a stopped run left half written that a start removed (its file name), a backup written (its file name, counts and whether it is encrypted), the backup schedule at start and whenever a new time is saved (its time and time zone), that backups are not scheduled any more once the time is cleared, a missed backup written at start, a backup retention removed (its file name) or retention held back while a restore waits, on the administration page a backup started, a key set for encrypted backups made (never the keys), a backup uploaded (its file name and size) or downloaded (its file name), each by user id, and a backup under way stopped with the app, a restore asked for and each step of one applied at start (the backup's file name, the tables and files loaded, the new generation), a backup that reads SQL Server under `SERIALIZABLE` (snapshot isolation is off, so writers wait while the tables are read), which model and server photo reading uses and where its system prompt comes from, a database or model server that is back, and the setup of a new instance: an instance that counts as set up because its database held data from before, a setup the environment completed (by the setting that did), the first administrator made or claimed on the setup page (by user id) or open access acknowledged there, a scheduled backup not written while the setup waits and nothing is stored yet |
| `Debug` | ordinary changes (a vehicle, refueling, expense, schedule, chart, picture or photo added, changed, trashed or restored), every GraphQL request with its time and operation, errors a client causes (a validation failure, something missing, a request the server turns down), sessions that are no longer valid and why, a database that would not say how large it is (the administration page shows its size as unknown), and the trail of each photo a model reads (see [Reading photos with an OpenAI-compatible model](photo-reading.md#following-a-photo-through-the-log)) |

**Only ids, counts and reasons are logged** by the app's own lines: users, vehicles, logs and pictures by id, never e-mail addresses, names, license plates, notes, amounts, odometer readings, passwords, reset links, API keys, the subject an identity provider sends, or values read from photos (why a value was dropped is logged as a code such as `OdometerBelowLatest`, never the value). There are two exceptions. One is opt-in: `Recognition__OpenAiCompatible__LogTraffic=true` also writes the prompts and what a model read, never the photo or the key, to debug a model ([details](photo-reading.md#seeing-what-is-sent-to-the-model)). The other is deliberate: while a new instance waits for its setup, and with sign-in off (`Auth__Mode=None`) at every start, the start writes the instance's **one-time code** to the log (`XXXX-XXXX-XXXX`, a new one at every start; while the setup waits as a `Warning`), because there is no administrator to guard the setup or a restore asked for from the app, so whoever may read the log may set the instance up or restore ([details](backup-and-restore.md#restoring-a-backup)). A backup's passphrase or identity is never logged. A failed sign-in names the account by its id (or says "unknown account"), not by the address that was typed. A settings file left out at start is described by the names of the settings at fault, never by what was written in them. Nothing a client sends is logged as it came: not GraphQL variables or documents, not the text of a request error, fields are named the way the schema names them, and the endpoints of the picture and import uploads appear as their route pattern, not as the path that was asked for.

That promise has an edge. The text of an unexpected error is written as the framework or the database wrote it, and a database server can quote the values of a failed statement in it (for a duplicate key, for example). Lines of the framework and its libraries (`Microsoft.*`, `System.*`) are written as they come, such as an identity provider's error description. And **do not lower `Microsoft.AspNetCore` below `Warning`**: its request lines hold the whole address of a request, which includes the token of a password reset link.

Change what is shown with the usual settings (`Logging:LogLevel:...` in `appsettings.json`, or environment variables):

```sh
Logging__LogLevel__Tankstat=Debug      # every Debug line of the app (the default when running with mise run dev:api)
Logging__LogLevel__Tankstat=Warning    # quieter: only warnings and errors of the app ("Default" is for the framework's own categories)

# How it looks: name the formatter first, its options only apply to the formatter that is named.
Logging__Console__FormatterName=json   # one JSON object per line, for a log collector
Logging__Console__FormatterName=simple # or the readable one, which these options adjust:
Logging__Console__FormatterOptions__SingleLine=true                         #   one line per entry
Logging__Console__FormatterOptions__TimestampFormat="yyyy-MM-dd HH:mm:ss "  #   with the time (there is none by default)
Logging__Console__FormatterOptions__UseUtcTimestamp=true
Logging__Console__FormatterOptions__IncludeScopes=true                      #   the scopes of a request, see below
```

With scopes on, each line of a signed-in user's request carries `UserId: <id>`, next to the framework's own scopes (trace and connection ids and the **request path**, which is what the client asked for). Prefer the `json` formatter with scopes: it escapes the path. A narrower category works like the first line, for example `Logging__LogLevel__Tankstat.Application.Users=Debug` for sign-ins and user administration only (a name with dots can be set through Docker or `env`, not through the shell's `export`). The browser has a log of its own: a failed request or a crashed page is written to the browser's console, and nothing is sent to the server.
