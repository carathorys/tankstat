# Install as an app

For people who want Tankstat on their home screen or dock, and operators who want to know what the service worker does.

Tankstat is a progressive web app: served over **HTTPS** (or from `localhost`), it can be installed and opened from the home screen or the dock like any app, full screen, with its own icon.

- **Android (Chrome, Edge, ...)**: the navigation menu shows **Install app** as soon as the browser allows it (Chromium decides when to make the offer; the browser's own menu has the same entry).
- **iPhone and iPad (Safari)**: Safari makes no offer from the page, so **Install app** in the menu shows the steps instead: open the page in Safari, then Share → *Add to Home Screen* → *Add* (other browsers on iOS cannot add to the Home Screen). The installed app has its own cookies: sign in once more there; it then stays signed in as long as it is used at least every 90 days (see [Sessions](authentication.md#sessions-standalone-and-oidc)).
- **Desktop (Chrome, Edge)**: the icon in the address bar or **Install app** in the menu. Firefox has no equivalent, and Safari on macOS adds the page to the Dock from its own menu (File → Add to Dock) without telling the page, so the menu entry is missing in both; that is normal.

## What the service worker does

A service worker keeps the built pages, scripts, styles and icons, so the app starts at once and still opens without the network (you then see the shell with the footer saying the server cannot be reached: data, pictures and sign-in need the server, see below). Nothing from `/graphql`, `/auth`, `/media` or `/imports` is ever cached, and those paths are never answered with `index.html` by the worker. Updates: the worker looks for a new version at every start, every hour while the app stays open, and when you come back to its tab. When there is one, a message "A new version of Tankstat is available" with a *Reload* button appears above the page; nothing reloads by itself, so you choose the moment (open dialogs and half-filled forms are not lost until you do). The server sends `/assets/*` (content-hashed names) as immutable and everything with a fixed name (`index.html`, `sw.js`, `manifest.webmanifest`, icons) as `no-cache`, so a release reaches every browser on its next start. The HTTPS it needs is the job of the reverse proxy in front of the server, see [Self-hosting](self-hosting.md).

## When the server is out of reach

The app does not rely on the browser's online flag alone: a server on your home network is out of reach from a phone on mobile data that is perfectly online. Every request reports how it went; one that gets no answer (or only a reverse proxy's 502, 503 or 504, which it sends while the server behind it is down) marks the server unreachable, and any answer marks it reachable again.

While it is unreachable:

- The top bar shows **Offline** (on a phone only its icon, a crossed-out cloud) and the footer says *You are offline* (no network at all) or *The server cannot be reached*, with a **Try again** button, in place of the API's status and version; the app's own version (*App v1.2.3*) stays. A screen reader hears it once when it happens and *Back online* when it is over.
- What was downloaded or opened while online opens again, after a restart of the app too: the home page, a vehicle's page, its refuelling and expense lists in any order and page, an entry's details, the trash, the dashboard you opened, your notifications and settings. Figures (consumption, totals, a schedule's status) are the server's as of the download; nothing is worked out on the device. Something neither downloaded nor opened says it is not on this device yet, and screens that only make sense with the server (administration, the vehicles' trash, sharing, importing, signed-in devices) say they need a connection. An administrator's full vehicle list shows, offline, the vehicles kept on this device (it says so), in any order. A vehicle added online is downloaded right away, so it can be used offline at once; one this device has not downloaded yet (added on another device since the last download, say) still takes new entries offline, with nothing to start from (no last odometer).
- **Refuellings, expenses, vehicles and recurring expenses can still be added, edited, moved to the trash (recurring expenses: deleted) and restored, and recurring expenses marked done**: the change is kept on this device (a note in the dialog says so, and the message after saving reads *Saved on this device · syncs when online*). It shows at once where it belongs, marked *New*, *Changed*, *To be removed*, *Restored* or *Done · not synced* (on the home cards and the vehicle's banner in words; in the lists by an icon in a narrow first column, which is there only while something on the page waits: a green plus, a blue pencil, an amber bin, a blue arrow back, a green tick, and a red warning for a change the server could not apply. Tap the icon for what it means, why it waits or the reason the server gave, and a link to Waiting to sync), and the top bar counts the changes waiting (on a phone only the number shows); the count opens **Waiting to sync** (also in the navigation while something waits), which lists them per vehicle with what each does, its values and when it was saved. **Remove the change** there takes one back: it is never sent, and what it changed shows as the server has it (a vehicle added here takes its entries along). An entry waiting to be moved to the trash has **Keep** instead of Edit and Delete. Signing out with changes waiting asks first; they stay on the device for that account. A vehicle added offline gets its card, its page and logs of its own (its figures and charts come once the server has it); a recurring expense added offline shows as upcoming (the server works out when it is due), and one marked done cannot be done again until the server has the visit; a visit with an amount shows its expense. Changes of one entry fold into one (an entry added and then edited is one new entry; one added and then removed is nothing, and a vehicle added and removed takes everything made to it along), they survive closing the app, and they stay with the account that made them. While a vehicle has changes waiting, its lists are answered by the device even when the server is back, so they keep showing. **When the server can be reached again** (and at the start, every hour, soon after a change is kept while it is reachable, or with **Sync now** on Waiting to sync), they are sent in the order they were made, the vehicles added here first; the server applies each with the same rules as online, from the version it was made from, so a change made meanwhile by someone else is not overwritten. What it cannot apply (changed meanwhile, removed meanwhile, a rule it breaks) it keeps with the reason until someone decides; what was made on a vehicle or recurring expense added here that the server could not take waits on the device. Then the download brings the server's rows (ids, consumption, figures), and the marks go. The full vehicle list of administrators keeps its changes the same way. Other changes (settings, sharing, pictures, emptying the trash) still need the server.
- **Photos work offline too.** A photo picked for a new refuelling, expense or service visit, or added to a saved one, while the server cannot be reached (or while that vehicle has changes waiting) is kept on this device: its thumbnail carries a small crossed-out cloud, a note under the photos says what that means (*Photos with this mark are kept on this device and uploaded when it syncs.*), and the entry is kept with it. Removing a photo of a saved entry waits on the device the same way (the photo is hidden until then). When the changes are sent, each kept photo goes up right before its entry, so the server attaches it as it would online; afterwards it leaves the device. With photo reading on (as the server last said), a new entry's photos are read once it reaches the server: the values they would give may be left empty, the dialog says so, and they are filled in then, with a notification, as for an entry saved online before its photos were read. The odometer the reading is checked against is the vehicle's latest when it syncs. Photos added offline to a saved entry are not read. A photo the server will not take is left out and its entry is sent without it.
- **Changes the server could not apply** are not lost: whoever sent one, and everyone who may see the vehicle, finds it under **Not applied** on Waiting to sync (online; the top bar and the navigation say how many, and each of them gets a notification) with what it does, why it was not applied in the same words as online, and who sent it when. Whoever sent it, or may change the vehicle's entries, decides: **Apply anyway** applies it as if they saved it themselves (every rule still applies, only not that it was changed meanwhile; photos that were waiting with it are not attached), **Discard** drops it for good. Apply is not offered when what it changes is gone. A change that is still refused stays, with the new reason. **Edit and apply** (for an added or edited entry, vehicle or recurring expense) opens the entry's dialog with the values the change carries: apply them as changed, and a refusal shows in the dialog, which stays open. An entry that was saved without its values (waiting for a photo) gets them this way, since applying it again does not bring the photo back.
- **A change still waiting on this device can be edited too** (Waiting to sync → **Edit**, for an added or edited entry, vehicle or recurring expense): the same dialog with the change's values; saving keeps one change (an entry added here stays one new entry, with its photos). Moving to the trash, restoring, a service visit and photo changes can only be removed.
- Anything else that changes data says at once that it works again once you are back online, instead of waiting for a server that does not answer (a server that is down can leave a request hanging for a long time). Grids, the notification bell and the photo readings stop polling.
- The app asks the server again after 2, 5, 15 and 30 seconds, then once a minute, and at once when the device comes back online, when you return to the app, or when you press **Try again**. When it answers, everything on the screen is loaded again.

What the device keeps, per account, in the browser's storage for this site (IndexedDB; a database per account, so another account signing in on the same device never sees it):

- **Your vehicles and their recent logs, downloaded ahead.** Once the server says who you are, the app downloads your vehicles and, for each, the refuellings and expenses of your offline window (the last two months unless you choose otherwise, see below), the trash included. Offline, a vehicle's refuelling and expense lists then page and sort like online, their entries open, and the trash shows. Who may edit an entry follows the vehicle's sharing as of the last download.
- **The answers of the screens you opened**, for everything else (the dashboard and its charts, settings, notifications); every download also keeps the home page and each vehicle's page and schedules. At most 300 such answers per account are kept, the oldest go first.

How much travels: the first download of a vehicle brings the logs of its window in pages of up to 200; every later one (at the start, when the server is back, every hour while the app is open) asks each vehicle only for what changed since the last one, usually nothing, and for what was removed for good meanwhile. A window that grows downloads that vehicle again; one that shrinks only removes the older logs from the device. A vehicle you no longer see (trashed, removed, or not shared with you any more) goes from the device with its logs. A device that has not downloaded for longer than the server remembers removals (`Sync:TombstoneRetentionDays`, 90 days) downloads its window afresh.

**Choosing the window** (Account → **Offline data**): one window for every vehicle and, with **Change**, another one for a vehicle: *Nothing (online only)*, *Everything*, *This year*, *This year and last year*, *Since a date*, or *A timespan back from now* in years, months, days, hours, minutes and seconds in any combination (at most 100 years; hours and smaller round down to the whole day). Each vehicle shows about how many entries its window brings, the trash included. The choice is kept with your account, so every device you use downloads the same; each works out the dates on its own clock. **Save** sends it and this device downloads at once; choosing needs the server. The same section shows how much the site stores on this device, when it last downloaded, **Download now**, and **Remove offline data from this device** (after a confirmation; the next download brings the window again, so choose *Nothing* to keep the device empty; changes waiting for the server are kept).

Signing out leaves the data on the device but closes it: the next start without the server opens nobody's, and it opens again when the same account signs in. Clearing the site's data in the browser removes it. A browser that offers no storage (some private windows) keeps nothing and works online only.

Signing in and signing out need the server (signing out clears a cookie only the server can clear). With several tabs of the app open, only one of them syncs on its own at a time; the app also asks the browser to keep its storage when space runs low, since changes waiting for the server live there. Vehicle pictures, avatars and the photos of saved entries are not kept for offline use: they show again when the server can be reached.
