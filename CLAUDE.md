# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Tankstat is a self-hosted web app: React + TypeScript frontend (Vite) and a .NET 10 backend. Kestrel serves both the API and the built SPA in production. See `README.md` for user-facing docs.

## Toolchain and commands

All tooling is managed by `mise` (`mise.toml`: Node LTS, .NET 10). Prefer `mise run <task>` over calling tools directly.

- `mise run install` - `npm ci` + `dotnet restore`
- `mise run dev:api` / `mise run dev:web` - API on :5080 with hot reload; Vite dev server proxying `/graphql`, `/auth` and `/media` to it
- `mise run test` - typecheck, lint, then every test layer (run this before finishing a change)
- `mise run test:unit`, `test:integration`, `test:api` - single layers
- `mise run build` - self-hostable output in `out/` (published API + SPA in `wwwroot`)

Single tests:
- Frontend: `npx vitest run tests/frontend/<file>` (add `-t "<name>"` to filter)
- Backend: `dotnet test tests/backend/<Project> --filter "FullyQualifiedName~<Name>"`

## Project structure rules

- All source lives under `src/`, all tests under `tests/`. Each is split into `backend/` and `frontend/`.
- Frontend tooling (`package.json`, `vite.config.ts`, `tsconfig*`) lives at the repo root so `src/frontend` and `tests/frontend` share one `node_modules`. Vite's `root` is `src/frontend`; build output goes to `dist/`.
- Backend follows clean architecture, dependencies pointing inward only: `Api -> Application, Infrastructure`; `Infrastructure -> Application`; `Application -> Domain`. Application and Domain must not reference EF Core or HotChocolate. Application defines ports (interfaces such as `IDatabaseProbe`); Infrastructure implements them. Each layer registers itself through an `AddApplication` / `AddInfrastructure` extension.
- Add new .NET projects to `Tankstat.slnx`.
- Domain: fuel log. `Vehicle` and `Refueling` entities have private setters and `Create` factories that enforce the rules (throwing `DomainException`); Application services (`VehicleService`, `RefuelingService`, `ResourceSharingService`, `ImageService`) use repository ports; the GraphQL error filter maps `DomainException` / `NotFoundException` to `VALIDATION_FAILED` / `NOT_FOUND` errors.
- Fuel consumption (`Refueling.Consumption`, fuel per 100 distance units between full fill-ups) is stored, not computed on read: `ConsumptionCalculator` (pure, Domain) recomputes a vehicle's whole chain and returns only the logs whose value changed; `RefuelingService` calls it after every log/update/delete/restore (`RecalculateConsumptionAsync`; imports pass `recalculateConsumption: false` and recalculate once; the seeder applies it directly) and `DatabaseMigrator` backfills once after the `AddRefuelingConsumption` migration. Anything that changes logs, odometers, volumes or full-tank flags must go through that path.
- Statistics (`Application/Stats`): `StatsCalculator` (pure) turns a vehicle's live records (`IStatsRepository.LoadAsync`) into chart data and key figures; costs are always per currency. A chart is a `ChartConfig` (metric, grouping, kind, range incl. custom from-to, stacked) that `Validated()` normalises (dates dropped for presets); saved ones are `VehicleChart` rows (typed columns, personal or shared, managed by `ChartService`). Presets live in the frontend (`dashboard/DashboardPanel.tsx`) and use the same `vehicleChartData` query. Add a metric = enum value + calculator case + i18n (`charts.metrics.*`) + builder rules in `dashboard/chartFormat.ts` (`normalise` mirrors `ChartConfig.Validated`).
- Expenses (`Expense`, `ExpenseService`) are non-fuel costs of a vehicle (free-text category, optional odometer reading); they use the vehicle's *logs* access rules and trash like refuelings. Importing (`Application/Imports`): one `IImportParser` per format turns a file into an `ImportBatch` (`FuelioCsvParser` first); `ImportService` keeps the batch under a token in `ImportSessionStore` (in memory, 30 minutes, per user), previews duplicates and commits row by row through `RefuelingService`/`ExpenseService`/`RecurringExpenseService` (schedules last, so a distance schedule without a known odometer starts from the imported readings), so all rules apply and bad rows are reported, not fatal; repeating Fuelio reminder templates become `ImportedRecurring` (duplicates: same title). A new format = a new parser + its tests; the UI (`pages/ImportPage.tsx`) lists formats in `FORMATS`.
- Recurring expenses (`Domain/Recurring`, `Application/Recurring`): `RecurringExpense` is a schedule of a vehicle (kind Time, Odometer or Combined = whichever is reached first; interval in months and/or distance; baseline = last done date and odometer; per-item warn days/distance). It is not a cost (no `Cost`) and its baseline odometer is a plain number, not an `OdometerReading`, so it never takes part in neighbour validation. `RecurrenceCalculator` (pure) turns it plus today and the vehicle's latest reading into a `RecurrenceStatus` (Upcoming/DueSoon/Overdue, which limit decides, days and distance left); the service computes it on every read, nothing is stored (`Vehicle.recurring` goes through `RecurringByVehicleLoader` -> `ListForVehiclesAsync`, so a list of vehicle cards costs a fixed number of queries, not several per card). `RecurringExpenseService` uses the vehicle's *logs* access rules through `LogAccessGuard` (like expenses and photos); `MarkDoneAsync` checks the schedule's rules (`CheckDone`), logs a normal `Expense` through `ExpenseService` (all expense/odometer rules apply) and then moves the baseline. Schedules are hard-deleted (no trash); the table cascades with the vehicle and `UserDataRepository` moves or purges them. GraphQL: `Vehicle.recurring`, `add/update/deleteRecurringExpense`, `markRecurringExpenseDone`. UI: the vehicle page's Recurring tab (`RecurringPanel`, `RecurringFormDialog`, `RecurringDoneDialog`) and attention badges on the home cards (`useDueText`, `RecurringStatusBadge`).
- Notifications (`Domain/Notifications`, `Application/Notifications`): a `Notification` belongs to its recipient only (not `IOwned`; every query filters by `RecipientId`, admins included) and is attached to a subject and an optional context by `NotificationRef` (entity type + id, no foreign key; a new source adds a `NotificationEntityType`). Its identity (unique index) is recipient + topic + subject + context id (`Guid.Empty` when none) + `Occurrence`. Every producer goes through `Notifier.NotifyAsync(actorId, drafts)` (the actor is never notified); the pure `NotificationPolicy` decides: *derived* drafts (with an occurrence, worked out from current state) are added once and only raised to a more urgent kind (reopened); *events* are folded into the unread one of the same topic/subject/context (`Count`), removed when undone (`After == Before`), and past `Notifications:MaxPerHour` become one `MoreActivity` digest. Sources: `ResourceSharingService` and `AccessAdminService` (events built with `NotificationArgs.AccessChange`, `Before`/`After` = access levels), and `RecurringNotificationSync`, which runs lazily once per request from `NotificationService` (no background job) over `AccessService.PersonalLogScopeAsync` (an admin's blanket rights do not count; anonymous keeps everything), one occurrence per schedule cycle (last done date + odometer). Arguments are display-ready snapshots; the frontend words them per kind (`notifications/useNotificationText.ts`, `notifications.kinds.*`). Users never delete notifications (deliberate): they only mark them read (`ReadAt`; `markNotificationsRead` returns the changed rows so Apollo updates loaded lists in place), and `NotificationService` purges the ones read more than `Notifications:ReadRetentionDays` ago on the same lazy path, keeping reminders of schedules that are still due (else the sync would re-add them). UI: `shell/NotificationBell.tsx` (polls the unread count every minute; tests get an empty-inbox default handler from `tests/frontend/server.ts`, override with `fakeNotificationBackend`) and `pages/NotificationsPage.tsx`. User deletion purges the inbox; actions go through `notifications/useNotificationActions.ts`.
- Photos (`Application/Photos`, `Domain/Photos/LogPhoto`): up to 10 photos per refueling or expense, one `LogPhoto` table for both kinds (log id without a foreign key, like `ResourceGrant`; cascading foreign key to the vehicle). `LogPhotoAccess` applies the vehicle's *logs* rules through `LogAccessGuard`, the one place (shared with `RefuelingService`/`ExpenseService`) that decides who may see or edit a vehicle's logs (View to see and to GET `/media/{id}`, Edit to add/remove; trashed logs hide their photos); `LogPhotoService` adds/removes; `IExpenseRepository`/`IRefuelingRepository.PurgeAsync` return `PurgedLogs`, delete the photo rows in the same save, and the services then remove the folders. Upload is `PUT /media/expenses|refuelings/{logId}/photos`, remove is `DELETE .../photos/{imageId}`; GraphQL only has the read field `photos { id url }` (batched per response by `ExpensePhotosLoader`/`RefuelingPhotosLoader`, which trust the already authorised parent log). Photos picked for a log that is not saved yet are uploaded at once as `PhotoDraft`s (`PhotoDraftService`; `PUT /media/vehicles/{id}/photo-drafts`, `DELETE /media/photo-drafts/{id}`; id = the image id, folder `vehicles/<id>/drafts`, visible to the uploader only, Edit on the vehicle's logs to upload, at most 20 per user and vehicle, expired after a day and removed whenever anyone uploads a draft, so no background job); `logRefueling`/`addExpense` take `photoIds`, which `LogPhotoService.RequireDraftsAsync` checks before the log is saved and `AttachDraftsAsync` turns into its photos afterwards (the file moves into the log's folder; a draft that cannot be attached goes back and never fails the save, the response's `photos` tell the UI). The frontend `PhotoGallery` (+ `usePhotoQueue`/`usePhotoSession`: per-photo uploading/uploaded/failed with retry, Save waits for uploads, closing the dialog deletes its drafts, `PhotosLeftOut` when the server attached fewer) has a camera input (`capture="environment"`) and a library input; photos are resized to 1600 px in the browser.
- Upload folders: `StoredImage.Folder` (null = legacy file directly in `Storage:Path`) built only from ids by `ImageFolders` (`users/<id>`, `vehicles/<id>/picture`, `vehicles/<id>/drafts`, `vehicles/<id>/expenses|refuelings/<logId>`); `FileSystemImageStore` re-validates the folder. Purging a vehicle removes `vehicles/<id>` with everything below it (`ImageService.DeleteVehicleFilesAsync`). New kinds of uploads belong in a folder below their owner. Deleting a user (`UserDataRepository`) moves `LogPhoto` (and `PhotoDraft`) owner/creator along with the logs, or purges the vehicles; `UserService` then removes the purged vehicles' folders and `users/<id>`.
- Reusable building blocks (use them for new entities, do not add raw numbers): `OdometerReading` (all readings of a vehicle in one table, no maximum, unit per vehicle; neighbour validation across sources), `Cost` (amount + currency), `MeasurementUnits` (per-vehicle distance/volume units, locked once logs exist, never converted). Entities own their reading/cost; trash/restore/purge cascade in code.
- Photo reading in the app (`Domain/Recognition`, `Application/Recognition`, `Infrastructure/Recognition`; optional, off by default): photos picked in the add dialogs (refueling, expense, recurring "done") are uploaded as drafts with `?form=refueling|expense&locale=xx`; with a form, `RecognitionService.QueueForDraftAsync` queues a `PhotoReading` (id = the image id; the purpose decides the allowed kinds; the hints Locale/LastOdometer/Currency/Today are taken right then because the worker has no user). Queueing never fails the upload. `RecognitionWorker` (the app's only background job; registered always, returns at once when not set up) wakes on `IRecognitionSignal` or every 10 s; `PhotoReadingProcessor` claims due readings atomically (repository `ExecuteUpdate`), claims nothing while the provider is unavailable (`RecognitionAvailability`, 30 s cache), retries unavailable providers (5 attempts, 10 s x 3^n), fails refused photos, requeues attempts cut short by a restart (stale after 5 min, or longer than `Recognition:OpenAiCompatible:TimeoutSeconds` + 1 min: `PhotoReadingProcessor.StaleAfter(options)`) and normalises values with `ReadingNormaliser` (a blank beats a wrong value). Values are a JSON column; the table has a cascading foreign key to `Images`, so a reading goes with its picture on every path. `RecognitionOptions` are bound but never validated on start: `RecognitionSetup` turns unusable settings (even unbindable ones) into "off" plus a warning logged by the worker; never let a recognition setting stop the app. The provider is `OpenAiCompatibleRecognitionProvider`, over a named HttpClient without a timeout of its own, for any OpenAI-compatible chat completions API (`Recognition:OpenAiCompatible:*`: `BaseUrl` including `/v1`, `Model` required, `ApiKey` optional as a Bearer token, `SystemPrompt`/`SystemPromptFile` replacing `OpenAiCompatiblePrompt.DefaultSystemPrompt` (printed in the README, pinned by a test) while the contract (allowed kinds and fields, formats, locale conventions, JSON schema per `ResponseFormat`) is always sent and the latest odometer, currency and today never are; answers are read tolerantly (think blocks, code fences, text parts), a refusal is Rejected, non-JSON is Unavailable, and the values go through the pure `ReadingChecks.Check` in Application (fields per kind, odometer window against `LastOdometer`, litres × price ≈ total, date window, ranges; the model's confidence only ever lowers the result; it returns `CheckedValues(Kept, Issues)`: every drop or doubt carries a `ReadingIssue(Field?, ReadingIssueCode)` from `Domain/Recognition/ReadingIssue.cs`, codes only, never the value, and the provider adds `Unrecognised`/`NothingLegible`; a missing rating reaches the checks as NaN and becomes `NoConfidence`); exception messages carry a status and a snake_case code at most, never server or model text; fixtures in `tests/backend/contracts/openai-compatible`), `NullRecognitionProvider` otherwise. A cloud `BaseUrl` is the operator's explicit choice (it sends photos off-site). The photo's trail is in the log at Debug, tied together by the reading's id (`RecognitionRequest.ReadingId`, set by the processor, never sent to the model): the provider's "Asking {Model} at {Server} to read photo {PhotoId}" and "{Model} answered photo ... said {Said}, listed {Listed}, kept [Field@confidence], issues [Field:Code]" (or "did not read photo ... after {ElapsedMs} ms"), then the worker's "Read photo {Id}: it shows {Kind}, {Sure} of {Values} values are sure enough" (`ProcessedReading.Summary`; `RecognitionSetup.IsSureEnough` is the one rule for what is sure enough, shared by `UsableValues` and `LogPhotoFiller`); at start the worker says at Information which model and server (`ServerAddress.Of`: no user info or query) and where the system prompt comes from, never its text (`RecognitionSetup.SystemPromptSetting`). The README prints the full request (system prompt, contracts for both dialogs, schema), pinned to the code by `OpenAiCompatiblePromptTests`. `Recognition:OpenAiCompatible:LogTraffic` (default off; the worker warns at start while on) puts `OpenAiTrafficHandler`, a `DelegatingHandler`, to work in the named client's pipeline: every request and answer (also the health check) is written at Information, one entry each, pretty-printed, numbered so the two pair up, with prompts and what the model read in them: the one place the app logs those, so keep it that way (the photo only as its size, the key masked in the header and wherever a server echoes it, bodies cut at 16 000 characters, a server's text escaped so only the layout breaks lines); the provider hands it the photo through `HttpRequestOptions` (`OpenAiTrafficHandler.Photo`). Drafts picked for reading are uploaded as JPEG while the server says reading is on (`usePhotoQueue` asks `recognitionStatus`, the dialog's own question; `resizeImage` `format: 'jpeg'`), since not every model server decodes WebP; `RecognitionNames` holds the kind and field names the prompt and the answer share. GraphQL: `recognitionStatus { available }` and `photoDrafts(ids)` (own drafts only; `UsableValues`: confidence >= `MinConfidence`, hints left out); `markRecurringExpenseDone` takes `photoIds`. Logs never contain read values.
- Logs saved before their photos are read (`Domain/Vehicles/LogReview.cs`): a refuelling may be saved without odometer, volume or total, an expense without amount (its odometer is optional anyway), but only while one of its photos is still being read (`LogPhotoFiller.MayWaitForDraftsAsync`: queued/reading, or uploaded less than `JustRead` ago; updates: a pending reading of an attached photo); otherwise `log.valuesRequired`. So `Refueling.OdometerReadingId`/`CostId`/`Volume` and `Expense.CostId` are nullable (no row until known; `Update` returns `LinkedChanges` for the repository). `ReviewState`: AwaitingPhotos -> NeedsReview (values filled, `FilledFromPhoto` flags) / Incomplete (still missing) / None; a person's full save sets None (and marks the log's `LogReview` notifications read). `LogPhotoFiller.FillAsync` (no user) fills only empty values with sure values (like `UsableValues`; a total without a currency takes the reading's hint), never checks odometer neighbours (user decision: the review catches it), recalculates consumption, logs a Debug line with ids and the names of the values (never what was read) and notifies the creator (`LogFilledFromPhoto`/`LogNotFilled`, derived, topic `LogReview`, subject `Refueling`/`Expense`). It runs after `LogAsync`/`AddAsync` attach the drafts, after a restore, and from `PhotoReadingProcessor` once per log after a round, for readings that finished (Read/Failed) of photos that belong to a log. Stats leave out logs still missing values; `ConsumptionCalculator` makes an interval with an unknown volume/odometer unknown. UI: in the add dialogs those fields stop being required while `drafts.pending` is non-empty (`ReadNote` `waiting`), grids show `ReviewBadge` in the date column and poll (`DataGrid` `pollWhile`) while a row awaits its photos, edit dialogs show `ReviewCallout` and mark `filledFromPhoto` fields. The recurring "done" dialog still requires its values. Frontend (`recognition/`): `useDraftReadings` (status on open and, while it reads "off", again every 3 s for a minute after each upload; polls every 1.5 s while readings are pending, at most a minute after each upload), the pure fill rules in `readValues.ts` (fill fields the user has not changed, starting values count as unchanged; offer, never overwrite, what they typed), `useReadFill` (controlled fillable fields), `ReadNote` in `Field`'s `extra` slot ("Read from the photo" / "The photo shows X · Use it"), a `role="status"` announcement, "Reading…" under thumbnails. Tests: `tests/frontend/server.ts` answers `RecognitionStatus` with unavailable by default; use `fakeRecognition` from `mocks.tsx` to turn it on.

## Stack decisions

- **API:** GraphQL (HotChocolate 16 at `/graphql`); the only REST endpoints are the picture endpoints in `Api/Media` (`PUT/DELETE /media/me/avatar`, `PUT/DELETE /media/vehicles/{id}/picture`, `PUT/DELETE /media/expenses|refuelings/{logId}/photos[/{imageId}]`, `PUT /media/vehicles/{id}/photo-drafts`, `DELETE /media/photo-drafts/{id}`, `GET /media/{id}`), because files do not fit GraphQL. The same goes for `POST /imports/{format}` (`Api/Media/ImportEndpoints.cs`; named `/imports` so it does not collide with the SPA route `/import`). Frontend uses Apollo Client 4 and Radix Themes (`@radix-ui/themes`, `@radix-ui/react-form`, icons from `@radix-ui/react-icons`); use the Themes components directly (no custom wrapper layer, hand-written CSS only in `main.css` for the glass look, nav links and skip link; otherwise use their layout/style props), and keep the app wrapped in `<Theme>` (`main.tsx`, and `renderWithApollo` in tests). jsdom lacks some browser APIs Radix needs; `tests/frontend/setup.ts` stubs them. Radix portals (Select options, dialogs) render outside the component: query with `screen`, not `within`; a Themes Tabs trigger has its label twice in the DOM, so match tab names with a regex.
- **Persistence:** EF Core 10. Provider is chosen at runtime from the `Database` config section: `Provider` (`Sqlite`, `PostgreSql`, `SqlServer`, `MySql`) and `ConnectionString`. With nothing configured it falls back to SQLite (`Data Source=tankstat.db`, working directory); only Sqlite may omit the connection string. MySQL uses Oracle's provider (Pomelo has no EF Core 10 release); MariaDB is not a tested target.
- **Configuration precedence** is standard ASP.NET Core: `appsettings.json` < `appsettings.{Environment}.json` < environment variables (`Database__Provider`, `Database__ConnectionString`) < command line. Environment variables must always be able to override the file; keep new settings in typed, validated options classes bound the same way as `DatabaseOptions`.
- **Migrations:** one project per provider (`src/backend/Tankstat.Migrations.<Provider>`, selected through `MigrationsAssembly`), applied at startup by `DatabaseMigrator`. After changing an entity or its mapping, run `mise run db:migration <Name>` so all four stay in sync (`MigrationsTests` fails otherwise). In-memory SQLite does not work for the app/integration tests because every pooled context gets its own database; use a temp file.
- **Authentication** (`Auth:Mode`: None, Standalone, Oidc, ProxyHeader; default None) is selected lazily at runtime, so all schemes are registered and `ModeAwareSchemeProvider` hides OIDC unless it is the mode. Sign-in only produces a cookie/proxy identity that names a user; `HttpCurrentUser` always reloads the user (admin flag, disabled, session version) from the database. Users live in the `Users` table for every mode. Standalone passwords use the framework PBKDF2 hasher; reset tokens are random, stored hashed, single use. Never expose `User` entities directly in GraphQL (password hash): use the DTOs in `Api/GraphQL/Dtos.cs`.
- **Access layer:** every user-owned entity implements `IOwned`. Use cases never compare owners themselves; they call `AccessService` (`ScopeAsync` for lists, `LevelAsync`/`CanAsync` for single items), and repositories filter lists with `InScope(scope)`. Levels are `None<View<Edit<Delete>`: Edit creates/changes/trashes/restores, only Delete (implicit for owner/admin, or granted) purges. Rules live in the pure `AccessPolicy` (admin/owner full; others get the larger of the instance default and any grant). Per-vehicle log sharing uses generic `ResourceGrant`s resolved by `OwnerScope` (owners + granted resource ids) and `InScope(scope, resourceIdSelector)`; granting never gives more than the granter holds. Invisible items look non-existent (null / `NOT_FOUND`), not `FORBIDDEN`. With `Auth:Mode=None` the actor is `Principal.Anonymous` (full access) and admin features are unavailable. The full, paged vehicle list (`vehicles`/`vehicleCount`, `/vehicles`) is such an admin feature; everyone else uses `myVehicles`/`myVehicleCount` (owned + shared, by name, `search` on name/license plate done in the database, `skip`/`take`), which the home page pages with infinite scroll (`fetchMore` + an `IntersectionObserver` sentinel + a Show more button).
- **Soft delete:** deletable entities implement `ISoftDeletable` (`DeletedAt`). Vehicles have an EF global query filter hiding trashed rows, so normal queries are safe by default; trash/restore/purge code must use `IgnoreQueryFilters()` (see `VehicleRepository`). Trashing and restoring need Edit access, emptying the trash needs Delete access and only purges what the user may delete (the UI gets `...DeletableCount`); `PurgeAsync` returns the picture ids so the files are removed too. `DeletedAt` is stored as a UTC date-time so comparisons translate on every provider. There is deliberately no scheduled purge job yet (user decision), only the user-initiated "empty trash".
- **UI structure:** `react-router` pages in `src/frontend/pages` (vehicle page tabs in `pages/vehicle`), shell (top bar, docked/overlay navigation, health footer) in `src/frontend/shell`; shared bits: `forms.tsx` (`FieldForm`, `Field`: labelled controls on `@radix-ui/react-form` with linked hint/error messages), `messages.tsx` (error/success callouts) and `components/` (`ConfirmDialog`, `ImagePicker`, `UserAvatar`, `VehiclePicture`, `OdometerField`, `LabeledSelect`). The sidebar is docked and open by default on desktop (`tankstat.nav.open` in localStorage), an overlay on phones. Pictures: resize in the browser (`pictures/resizeImage.ts`), upload raw with `pictures/upload.ts`. Look: translucent blurred panels (`.glass` in `main.css`), soft shadows, dim palette. Dialogs are uncontrolled where possible: `Dialog.Trigger` / `AlertDialog.Trigger` wrap the button that opens them, no open-state in the page. Tests render with `renderWithApollo(ui, route)` (MemoryRouter) and the in-memory `fakeVehicleBackend` from `tests/frontend/mocks.tsx`; the footer's status badge also has `role="status"`, so query status messages by text.
- **GraphQL codegen (graphql 17):** no hand-written GraphQL types. `schema.graphql` (exported from the API) + `src/frontend/graphql/*.graphql` generate `src/frontend/gql/generated.ts` (typed documents, enums as string unions). After changing the schema or a document run `mise run codegen` and commit both generated files; `SchemaSnapshotTests` and `mise run codegen:check` fail otherwise. Optional grid columns use `@include(if: $withX)` variables so hidden columns are never fetched; because of that a row may lack fields, so anything that edits an entity must load it (see `VehicleDetails`), never trust grid rows.
- **Grids:** sorting/paging/column selection are server-side only (`VehicleQuery`/`RefuelingQuery`: orderBy/direction/skip/take; count queries for paging). `DataGrid` runs on TanStack Table v9 (feature-based `tableFeatures`/`useTable`, `manualSorting`/`manualPagination`; columns need an accessor to be sortable; v9 has no `getCoreRowModel` option). `DataGrid` + `useGridSettings` (localStorage `tankstat.grid.<id>`, validated against current columns) are generic; add a column by adding a `GridColumn` (and the `@include` variable). Repositories always end the order with the id so pages are stable. Queries use `cache-and-network` so every visit refetches.
- **i18n:** every user-visible string goes through `t('...')` with typed keys from `en.json`; add the Hungarian text too (a unit test enforces equal keys/placeholders). Domain/Application errors derive from `KeyedException` (stable `key` + camelCase `args`) and `BusinessErrorFilter` puts them in the GraphQL error extensions; the frontend translates `errors.<key>` (`useErrorText`) and falls back to the server message. New user-facing errors need a key, an English entry and a Hungarian entry. Format dates/numbers with `Intl` (`useFormat`, `Pager`), never by hand.
- **Accessibility is a requirement for all UI:** landmarks, skip link, labelled controls (`Field`), table semantics, live regions for async status, 44 px touch targets, no information by colour alone, reduced motion. `tests/frontend/Accessibility.integration.test.tsx` runs axe (vitest-axe) on the pages and dialogs; add new screens to it.
- **Bundle size:** every page in `App.tsx` is `React.lazy` (its own chunk), the dashboard is lazy inside the vehicle page and sparklines through `LazySparkline`, so Recharts (~430 kB) is only downloaded when a chart is shown; the entry chunk is the shell, Radix, Apollo and i18n. Keep new pages lazy, and do not import `dashboard/*` (except `chartFormat.ts`) from eagerly loaded code. In tests lazy content appears asynchronously: use `findBy*`.
- **Charts:** Recharts, always inside `ChartView` (the picture is `aria-hidden`; the same data is a table behind a toggle: keep it that way for accessibility, tests read the table because jsdom cannot lay out SVG). Vehicle pictures are drawn by `CoverLayers` (the picture as a CSS `background-image` with `cover` sizing, so it is cropped and never stretched, plus a dark scrim) behind white text on cards and the vehicle banner.
- **Frontend libraries:** Recharts, TanStack Table (grids; other TanStack libraries are welcome), icons from `lucide-react`, animations from `motion` (`motion/react`; keep them short, entry-only, `MotionConfig reducedMotion="user"`). Build mobile-first and check desktop too.
- **Seeder:** `src/backend/Tankstat.Seeder` (`mise run seed`) is a test-only standalone tool: it deletes, creates, migrates and seeds a database through the domain factories (so domain rules apply), creates no users, uses the no-auth owner, and refuses unless `Auth:Mode` is None. Keep it that way: no users, no auth modes. It asks for confirmation unless `--yes`. It also seeds recurring expenses (mixed states, so the app derives reminders) and access-change notifications for the anonymous user (made-up people, `DataGenerator.Notifications`); each part uses its own `Random` from the seed so adding one does not change the others. New entities/rules: keep the generated data consistent (see `DataGenerator`) and its tests green.
- **CI and tests vs. appsettings.json:** `.github/workflows/ci.yml` runs frontend, backend, smoke and codegen jobs in parallel (via mise), then a build job; keep it in step with `mise run test`. Tests must never depend on the `Auth:Mode` (or admin settings) that `appsettings.json` happens to contain: every host/process started by a test sets the mode (and clears the bootstrap admin when it matters) itself; the smoke processes also drop `Recognition__` variables from the developer's environment. `Tankstat.Api.SmokeTests` start the real app as a process per mode; one test deliberately runs with only the shipped `appsettings.json`.
- **Docker:** the root `Dockerfile` builds one image (Node stage: `vite build` only; SDK stage: RID-specific, framework-dependent `dotnet publish` with `-p:Version`; Alpine ASP.NET runtime with ICU, non-root, `/data` volume, GraphQL health check). The SPA is copied to `wwwroot` and served by the API. `.dockerignore` excludes tests, so the image build must not need them (that is why it runs `vite build`, not `npm run build`). It builds from the working tree, so uncommitted `appsettings.json` ends up in the image; release builds come from CI checkouts.
- **Release workflow:** `.github/workflows/release.yml` (on a published release `vX.Y.Z[-pre]`, or manually) calls `ci.yml` (which therefore has `workflow_call`), builds the image for amd64, runs `scripts/docker-smoke.sh` against it, then pushes amd64+arm64 to `ghcr.io/<owner>/<repo>` with provenance/SBOM; the image's `VERSION` build argument comes from the tag. Changing the Dockerfile means keeping `docker-smoke.sh` and this workflow in step.
- **Logging:** the standard `ILogger<T>` on the console, nothing else installed (no Serilog); Application uses `Microsoft.Extensions.Logging.Abstractions` (the layering rule only forbids EF Core and HotChocolate there). Style: `logger.LogX("... {Placeholder}", id)` with named placeholders, no `[LoggerMessage]`; the field is called `logger`, never `log` (a "log" here is a refueling or expense). Levels: *Information* for what an operator looks for (sign-ins and sign-outs, password changes, administration, access changes, sharing, imports, emptied trashes, migrations, reachability coming back), *Debug* for ordinary changes (with entity ids), *Warning* for refusals, failed sign-ins and failures that used to be swallowed (a `catch` that swallows something an operator would want to know about logs its exception; a provider that is not healthy says why by throwing, see `IRecognitionProvider.IsHealthyAsync`), *Error* only for unexpected exceptions, which `Api/GraphQL/GraphQLLoggingListener` logs once (HotChocolate has no logging of its own; it dedupes by exception instance; a request the engine turns down, such as a missing variable, is the client's doing and only Debug; `MediaEndpoints.TranslateErrors` logs the keyed errors of the REST side, an unexpected REST exception is logged by the framework as it always was). Ids only in the app's own lines: never e-mails, names, plates, notes, amounts, passwords, reset tokens or links, API keys, OIDC subjects or read values (one opt-in exception: `Recognition:OpenAiCompatible:LogTraffic`, see Photo reading in the app), and nothing a client sent (variables, documents, request-error text; an operation name only when it is a valid GraphQL name; a field by its schema name `Type.field`, not by the alias a client gave it; REST lines name the route pattern, not the path: a line break in client text would forge a log line). The edge, which the README states: the text of an unexpected exception and the framework's own lines are written as they come (a database can quote values in its error), and `Microsoft.AspNetCore` must stay at Warning or above (its request lines hold reset-link tokens). A lasting condition is logged when it changes, not on every check (`RecognitionAvailability`, `EfDatabaseProbe`); `SmtpEmailSender` throws an `EmailSendException` that keeps only the status of a refused command (a mail server's answer quotes the recipient). The shipped `appsettings.json` silences EF Core's SQL and the HttpClient's per-request lines, keeps `Tankstat` at Information (Debug in Development); smoke tests start the app in Production and expect "database migrations" and "up to date" in its output and nothing with "Photo reading" by default, so those texts are a contract. Console options such as `IncludeScopes` or `TimestampFormat` only apply when `Logging:Console:FormatterName` is set (`simple` or `json`); a scope must be a message with a placeholder (`BeginScope("UserId: {UserId}", id)`), since the console prints a dictionary as its type name (the smoke test reads the real output). Tests: `TestSupport/CapturedLog` (`World.Log` in the Application tests, `TestApp.Log` in the API tests, `TestDatabase.Log`) and canary tests that run a broad flow and assert that no typed value or secret reaches a line (`LoggingTests` in Application and in the API integration tests); find a line by its class (`log.From<T>()`) and level and read the values of its placeholders (`entry.Values["UserId"]`), do not assert the wording of a message. Frontend: `apolloClient.ts` (`reportOperationError`, an Apollo `ErrorLink`) and `ErrorBoundary` write unexpected request failures and crashed pages to the browser console and send nothing; an error with a `key` is expected (the screen shows it) and not reported.
- **Notices:** the server sends public `notices` (currently the `AUTH_DISABLED` warning); the UI renders them generically in `NoticeBanner`.
- HotChocolate schema introspection only works in the Development environment, which is why `scripts/test-api.sh` sets it.

## Testing requirements

Every change must keep all three layers covering behavior, so breaking changes are caught:
- **Unit:** `tests/backend/Tankstat.Application.UnitTests` (pure logic, fakes for ports), `tests/backend/Tankstat.Infrastructure.UnitTests` (config binding, EF adapters on in-memory SQLite), `tests/frontend/*.unit.test.*`.
- **Integration:** `tests/backend/Tankstat.Api.IntegrationTests` (`WebApplicationFactory<Program>`, real DI/GraphQL/EF) and `tests/frontend/*.integration.test.*` (Apollo against msw-mocked GraphQL over HTTP).
- **API:** `tests/backend/Tankstat.Api.ApiTests` are black-box GraphQL contract tests against a running server (`TANKSTAT_API_URL`); `scripts/test-api.sh` starts one on a throwaway port with an in-memory database. A schema change the frontend depends on must fail here.

Frontend test files must be named `*.unit.test.ts(x)` or `*.integration.test.ts(x)` to be picked up by `vite.config.ts`.

## Scope

Besides health, auth and administration, the app covers vehicles and their refuelling logs (create/edit/trash/restore/purge, sharing a vehicle's logs, pictures) and recurring expenses (schedules by time, distance or both, shown on the home page), and per-user notifications (access changes, due schedules); there are no statistics or consumption reports yet. The OIDC token-validated provisioning path is covered by unit tests only, not against a real provider. Data created with auth off is owned by the anonymous user (id all zeros) and is only visible to administrators after switching modes. Photos picked in the add dialogs can be read by a vision model behind any OpenAI-compatible API (a server the operator runs, or a paid one at their choice) to fill in the form, or the saved log later (marked for review); it is off by default and nothing changes without it. Do not invent domain features or add infrastructure (CI, Docker, codegen) that was not asked for.
