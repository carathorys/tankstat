# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Tankstat is a self-hosted web app: React + TypeScript frontend (Vite) and a .NET 10 backend. Kestrel serves both the API and the built SPA in production.

The README is short on purpose (what it is, the features by name, a quick start, the development commands, links). The user and operator documentation is in `docs/`, one file per topic: `configuration.md` (database, files, defaults, notifications, logging), `authentication.md` (modes, settings, access control), `user-guide.md`, `importing.md`, `install-as-an-app.md`, `photo-reading.md`, `self-hosting.md` and `development.md`. When a change alters behaviour or a setting that a docs file describes, update that file (and the README only when a feature's one-line summary changes). `docs/photo-reading.md` prints the built-in system prompt, both contracts and the JSON schema, pinned to the code by `OpenAiCompatiblePromptTests`.

Pull request descriptions never carry the claude.ai session link (no `https://claude.ai/code/session_...` line); the "Generated with Claude Code" line stays. Commit trailers are unchanged.

Issue workflow (`.claude/skills/`, usable by any agent): `/triage N` claims an issue with the `triaging` label (and skips issues carrying it unless named), analyses, reproduces and plans it, posts the handoff on it, labels it `triaged` and removes `triaging`, never fixes; `/dev N` implements a `triaged` issue (refuses one that is not; on one another agent has `in progress` it stops and asks whether to take it over; claims it with `in progress` first) in a git worktree of its own on a branch off the freshly pulled `main` (the previous task's finished worktree is removed when the next task starts; an unrelated request asks first): targeted tests while working, the full suite before every commit and/or push, a draft PR labelled `WIP` until finished, then ready to merge without waiting for CI; `/review N` (or `next`: the oldest open non-draft PR) reviews only a PR that carries neither `reviewing` nor `reviewed` (on one being reviewed it asks whether to take it over, on a reviewed one it reviews again only on request), claims it with `reviewing` first, runs the built-in `code-review` with `--comment` (its levels `low`..`max`, `--max-findings` and `--fix` passed on; not `ultra`) plus a summary comment on the PR, then labels it `reviewed` and removes `reviewing`; only with `--fix` does it change the PR's code: in a worktree of its own on a `review/<N>` branch off the PR's head, the full suite before committing, pushed to the PR's branch without force.

## Toolchain and commands

All tooling is managed by `mise` (`mise.toml`: Node LTS, .NET 10). Prefer `mise run <task>` over calling tools directly.

- `mise run install` - `npm ci` + `dotnet restore`
- `mise run dev:api` / `mise run dev:web` - API on :5080 with hot reload; Vite dev server proxying `/graphql`, `/auth/oidc/`, `/auth/token/`, `/media` and `/imports` to it (only those two of `/auth`: `src/frontend/auth/` modules are served at `/auth/...`, so no module may live in `src/frontend/auth/oidc/` or `src/frontend/auth/token/`)
- `mise run test` - typecheck, lint, then every test layer (run this before finishing a change)
- `mise run test:unit`, `test:integration`, `test:api` - single layers
- `mise run build` - self-hostable output in `out/` (published API + SPA in `wwwroot`)

Single tests:
- Frontend: `npx vitest run tests/frontend/<area>/<file>` (add `-t "<name>"` to filter)
- Backend: `dotnet test tests/backend/<Project> --filter "FullyQualifiedName~<Name>"`

## Project structure rules

### Layout and layers

- All source lives under `src/`, all tests under `tests/`. Each is split into `backend/` and `frontend/`.
- Frontend tooling (`package.json`, `vite.config.ts`, `tsconfig*`) lives at the repo root so `src/frontend` and `tests/frontend` share one `node_modules`. Vite's `root` is `src/frontend`; build output goes to `dist/`.
- Backend follows clean architecture, dependencies pointing inward only: `Api -> Application, Infrastructure`; `Infrastructure -> Application`; `Application -> Domain`. Application and Domain must not reference EF Core or HotChocolate. Application defines ports (interfaces such as `IDatabaseProbe`); Infrastructure implements them. Each layer registers itself through an `AddApplication` / `AddInfrastructure` extension.
- Add new .NET projects to `Tankstat.slnx`.

### Fuel log and statistics

- Domain: fuel log. `Vehicle` and `Refueling` entities have private setters and `Create` factories that enforce the rules (throwing `DomainException`); Application services (`VehicleService`, `RefuelingService`, `ResourceSharingService`, `ImageService`) use repository ports; the GraphQL error filter maps `DomainException` / `NotFoundException` to `VALIDATION_FAILED` / `NOT_FOUND` errors.
- Fuel consumption (`Refueling.Consumption`, fuel per 100 distance units between full fill-ups) is stored, not computed on read: `ConsumptionCalculator` (pure, Domain) recomputes a vehicle's whole chain and returns only the logs whose value changed; `RefuelingService` calls it after every log/update/delete/restore (`RecalculateConsumptionAsync`; imports pass `recalculateConsumption: false` and recalculate once; the seeder applies it directly) and `DatabaseMigrator` backfills once after the `AddRefuelingConsumption` migration. A log with `MissedPreviousFillUp` (a fill-up before it was not logged; GraphQL `missedPreviousFillUp`, omitted on update = kept) breaks the chain: its interval has no consumption and the next one starts from it. Anything that changes logs, odometers, volumes, full-tank or missed flags must go through that path.
- Statistics (`Application/Stats`): `StatsCalculator` (pure) turns a vehicle's live records (`IStatsRepository.LoadAsync`) into chart data and key figures; costs are always per currency, never converted. The vehicle summary (card and dashboard key figures) has a main currency (most spent in over the last year) for `thisMonthSpend`/`lastMonthSpend`/`spendTrend`, plus `spending` (`CurrencySpend` per currency used this month or last, main first), which the UI shows joined (`spending.ts` `spentText`: "52,000 Ft · €73.90") so nothing spent in another currency goes unshown. A chart is a `ChartConfig` (metric, grouping, kind, range incl. custom from-to, stacked) that `Validated()` normalises (dates dropped for presets); saved ones are `VehicleChart` rows (typed columns, personal or shared, managed by `ChartService`). Presets live in the frontend (`dashboard/DashboardPanel.tsx`) and use the same `vehicleChartData` query. Add a metric = enum value + calculator case + i18n (`charts.metrics.*`) + builder rules in `dashboard/chartFormat.ts` (`normalise` mirrors `ChartConfig.Validated`).

### Expenses, imports and recurring expenses

- Expenses (`Expense`, `ExpenseService`) are non-fuel costs of a vehicle (free-text category, optional odometer reading); they use the vehicle's *logs* access rules and trash like refuelings. Importing (`Application/Imports`): one `IImportParser` per format turns a file into an `ImportBatch` (`FuelioCsvParser` first); `ImportService` keeps the batch under a token in `ImportSessionStore` (in memory, 30 minutes, per user), previews duplicates and commits row by row through `RefuelingService`/`ExpenseService`/`RecurringExpenseService` (schedules last, so a distance schedule without a known odometer starts from the imported readings), so all rules apply and bad rows are reported, not fatal; repeating Fuelio reminder templates become `ImportedRecurring` (duplicates: same title). A new format = a new parser + its tests; the UI (`pages/ImportPage.tsx`) lists formats in `FORMATS`.
- Recurring expenses (`Domain/Recurring`, `Application/Recurring`): `RecurringExpense` is a schedule of a vehicle (kind Time, Odometer or Combined = whichever is reached first; interval in months and/or distance; baseline = last done date and odometer; per-item warn days/distance). It is not a cost (no `Cost`) and its baseline odometer is a plain number, not an `OdometerReading`, so it never takes part in neighbour validation. `RecurrenceCalculator` (pure) turns it plus today and the vehicle's latest reading into a `RecurrenceStatus` (Upcoming/DueSoon/Overdue, which limit decides, days and distance left); the service computes it on every read, nothing is stored (`Vehicle.recurring` goes through `RecurringByVehicleLoader` -> `ListForVehiclesAsync`, so a list of vehicle cards costs a fixed number of queries, not several per card). `RecurringExpenseService` uses the vehicle's *logs* access rules through `LogAccessGuard` (like expenses and photos); `MarkDoneAsync(ids, input)` marks a service visit: schedules of one vehicle (another vehicle's or an unknown id is `recurring.notFound`; ids deduped; none is `recurring.noneSelected`), one Edit check, `CheckDone` on every one first (its errors carry the schedule's `title`: `doneBeforeLast`, `doneOdometerRequired`, `odometerBelowLast`; `Apply` keeps `recurring.odometerRequired`), then, when an amount or photos came, ONE `Expense` through `ExpenseService` (all expense/odometer/photo rules; title/category default to `RecurringDoneDefaults`: titles joined and cut at 120, common or first category, the note only for a single schedule), then `CompleteAsync` saves the moved baselines and the `RecurringCompletion` links (expense id + schedule id) in one save; a failure trashes the expense (`TryTrashAsync`). All or nothing; the amount is never split. `RecurringCompletions` has one foreign key, cascading from the schedule; the expense side has none (expenses and schedules both cascade from the vehicle, and SQL Server refuses two cascade paths), so `ExpenseRepository.PurgeAsync` removes the links in code like photo rows. `Expense.schedules { id title }` comes through `ExpenseSchedulesLoader` (the Expenses grid's `schedules` column, `defaultHidden`). Schedules are hard-deleted (no trash); the table cascades with the vehicle and `UserDataRepository` moves or purges them. GraphQL: `Vehicle.recurring`, `add/update/deleteRecurringExpense`, `markRecurringExpensesDone` (`{ schedules, expense }`), `Expense.schedules`. UI: the vehicle page's Recurring tab (`RecurringPanel` with a selection column and *Mark selected as done*, `RecurringFormDialog`, `RecurringDoneDialog`: the vehicle's schedules as labelled checkboxes, `recurringDone.ts` `preselect` ticks the clicked one plus everything not `UPCOMING`, optional amount, prefilled title/category) and, on the home cards, attention badges (`useDueText`, `RecurringStatusBadge`) each with a Done button that opens `RecurringDoneDialog` right there (see Home cards).

### Notifications

- Notifications (`Domain/Notifications`, `Application/Notifications`): a `Notification` belongs to its recipient only (not `IOwned`; every query filters by `RecipientId`, admins included) and is attached to a subject and an optional context by `NotificationRef` (entity type + id, no foreign key; a new source adds a `NotificationEntityType`). Its identity (unique index) is recipient + topic + subject + context id (`Guid.Empty` when none) + `Occurrence`. Every producer goes through `Notifier.NotifyAsync(actorId, drafts)` (the actor is never notified); the pure `NotificationPolicy` decides: *derived* drafts (with an occurrence, worked out from current state) are added once and only raised to a more urgent kind (reopened); *events* are folded into the unread one of the same topic/subject/context (`Count`), removed when undone (`After == Before`), and past `Notifications:MaxPerHour` become one `MoreActivity` digest. Sources: `ResourceSharingService` and `AccessAdminService` (events built with `NotificationArgs.AccessChange`, `Before`/`After` = access levels), `SyncNotificationSync` (`SyncChangeParked`, topic `Sync`, subject `SyncChange`, context the vehicle, occurrence `parked`: every parked change the reader may see as themselves or sent; args `change` (kind in API spelling), `vehicleName`, `submitterName`, `reason`, `reasonArgs` as JSON), and `RecurringNotificationSync`, which, like `SyncNotificationSync`, runs lazily once per request from `NotificationService` (no background job) over `AccessService.PersonalLogScopeAsync` (an admin's blanket rights do not count; anonymous keeps everything), one occurrence per schedule cycle (last done date + odometer). Arguments are display-ready snapshots; the frontend words them per kind (`notifications/useNotificationText.ts`, `notifications.kinds.*`). Users never delete notifications (deliberate): they only mark them read (`ReadAt`; `markNotificationsRead` returns the changed rows so Apollo updates loaded lists in place), and `NotificationService` purges the ones read more than `Notifications:ReadRetentionDays` ago on the same lazy path, keeping reminders of schedules that are still due and of changes still parked (else the sync would re-add them). UI: `shell/NotificationBell.tsx` (polls the unread count every minute; tests get an empty-inbox default handler from `tests/frontend/support/server.ts`, override with `fakeNotificationBackend`) and `pages/NotificationsPage.tsx`. User deletion purges the inbox; actions go through `notifications/useNotificationActions.ts`.

### Photos, uploads and shared building blocks

- Photos (`Application/Photos`, `Domain/Photos/LogPhoto`): up to 10 photos per refueling or expense, one `LogPhoto` table for both kinds (log id without a foreign key, like `ResourceGrant`; cascading foreign key to the vehicle). `LogPhotoAccess` applies the vehicle's *logs* rules through `LogAccessGuard`, the one place (shared with `RefuelingService`/`ExpenseService`) that decides who may see or edit a vehicle's logs (View to see and to GET `/media/{id}`, Edit to add/remove; trashed logs hide their photos); `LogPhotoService` adds/removes; `IExpenseRepository`/`IRefuelingRepository.PurgeAsync` return `PurgedLogs`, delete the photo rows in the same save, and the services then remove the folders. Upload is `PUT /media/expenses|refuelings/{logId}/photos`, remove is `DELETE .../photos/{imageId}`; GraphQL only has the read field `photos { id url }` (batched per response by `ExpensePhotosLoader`/`RefuelingPhotosLoader`, which trust the already authorised parent log). Photos picked for a log that is not saved yet are uploaded at once as `PhotoDraft`s (`PhotoDraftService`; `PUT /media/vehicles/{id}/photo-drafts`, `DELETE /media/photo-drafts/{id}`; id = the image id, folder `vehicles/<id>/drafts`, visible to the uploader only, Edit on the vehicle's logs to upload, at most 20 per user and vehicle, expired after a day and removed whenever anyone uploads a draft, so no background job; only a picture still in the draft folder is deleted with its row (`ImageService.DeleteDraftPicturesAsync`): one moved out is a photo or a vehicle's picture, even when a failure left its row behind); `logRefueling`/`addExpense` take `photoIds`, which `LogPhotoService.RequireDraftsAsync` checks before the log is saved and `AttachDraftsAsync` turns into its photos afterwards (the file moves into the log's folder; a draft that cannot be attached goes back and never fails the save, the response's `photos` tell the UI). The frontend `PhotoGallery` (+ `usePhotoQueue`/`usePhotoSession`: per-photo uploading/uploaded/failed with retry, Save waits for uploads, closing the dialog deletes its drafts, `PhotosLeftOut` when the server attached fewer) has a camera input (`capture="environment"`) and a library input; photos are resized to 1600 px in the browser.
- Upload folders: `StoredImage.Folder` (null = legacy file directly in `Storage:Path`) built only from ids by `ImageFolders` (`users/<id>`, `vehicles/<id>/picture`, `vehicles/<id>/drafts`, `vehicles/<id>/expenses|refuelings/<logId>`); `FileSystemImageStore` re-validates the folder. Two roots with the same layout below them (`ImageFolders.RootsOf`): the pictures (`Storage:Path`: avatars, vehicle pictures, legacy files) and the photos of logs (`Storage:PhotosPath`, **opt-in**: drafts and log photos, which grow without limit; unset or blank = the very folder of `Storage:Path`, so nothing moves on upgrade, `StorageOptions.PhotosRoot`; the Docker image does not set it but makes `/data/photos` owned by the app's user, so a volume of its own there is writable (`docker-smoke.sh` mounts one with `Storage__PhotosPath=/data/photos`); the two may be one folder, never nested, `StorageOptionsValidator` refuses that at start); the store resolves a folder against its root, a draft made a vehicle's picture moves between them (`File.Move`, which copies between disks; never `Directory.Move`), and a photo still in the pictures root is read, moved and deleted there, because `Infrastructure/Storage/PhotosMove` (a hosted service right after `DatabaseMigrator`) moves those file by file at every start (counts at Information, a file it cannot move is a Warning, and so is a folder it cannot read, after which the rest moves; a part of a photo that a copy between disks cut short left at the target is removed, since the store looks there first; it never stops the app); the Seeder deletes the photos folder too when one is set (`--photos`, else `Storage:PhotosPath`). Purging a vehicle removes `vehicles/<id>` with everything below it under both roots (`ImageService.DeleteVehicleFilesAsync`). New kinds of uploads belong in a folder below their owner. Deleting a user (`UserDataRepository`) moves `LogPhoto` (and `PhotoDraft`) owner/creator along with the logs, or purges the vehicles; `UserService` then removes the purged vehicles' folders and `users/<id>`.
- Client ids and versions (the base of offline sync): `Vehicle`, `Refueling`, `Expense` and `RecurringExpense` take an optional client-chosen id in their `Create` factory (`EntityId.OrNew`; `Guid.Empty` is `id.empty`) and count their saves in `Version` (from 1; bumped by `Update`, `MarkDeleted`, `Restore`, `FillFromPhoto` when it filled something, `MarkDone`; **not** by `SetConsumption` (derived, saved by `ExecuteUpdate`), `Vehicle.SetPicture`, `FinishReading` alone or photo rows). Every bump also records what it did and who did it (`LastChange`: `EntityChange` Created/Edited/Trashed/Restored/Done/FilledFromPhoto; `ChangedById`, passed to the mutators by the services, null for a photo), and `SyncInterceptor` sets `ChangedAt` when a save carries a new version (the interceptor is built once for the pooled factory, so it knows no user); GraphQL `changedAt`/`changedBy`/`lastChange` on the four types, `changedBy` through `UserRefLoader` like `createdBy`; a moved user's `ChangedById` moves with the data. It is a plain column, not an EF concurrency token (the repositories save detached graphs with `db.Update`; `SaveLogAsync` saves twice). Adds with an id are idempotent (`Application/Sync/ClientIds`): the services look the id up (trash included) right after the access check and before any rule, answer an add of the same creator and vehicle (vehicles: owner) with what it created, and refuse anyone else's with `sync.idTaken`; for a log not in the trash the repeat also runs the steps after the save again (`FinishRepeatedAsync`: drafts still waiting via `LogPhotoService.DraftsStillWaitingAsync`, the photo fill, the consumption), because a first try can fail after saving; two identical adds at once both insert, and the repositories' `AddOnceAsync` turns the loser's key violation into `false` so it is answered the same way. `MarkDoneInput.ExpenseId` makes a visit idempotent: when `RecurringCompletion`s already link that expense to every requested schedule nothing moves (checked before `CheckDone`; links to other schedules are `sync.idTaken`); a retry after a failed first try restores the expense the failure trashed (only reachable without links, so never one a person trashed after the visit); the dialog sends it only when the visit logs an expense. Updates, trashes and restores take `int? expectedVersion` (`VersionCheck`, `sync.versionMismatch` with `expected`/`actual`, after the access check so it reveals nothing), and every save is conditional on the loaded version: `Version` is a concurrency token, entities remember the version they were loaded with (`SavedVersion`, bumped through `Bump()`), `SyncInterceptor` sets it as the original value of every Modified/Deleted `ISynced` entry, and `AppDbContext.SaveChanges` turns a lost race on one of them into `sync.versionMismatch` (other entities' `DbUpdateConcurrencyException`s stay theirs); `SavedVersion` is ignored by EF and GraphQL. The add dialogs send an id per opening (`dialogs/useClientId.ts` over `offline/uuid.ts`, `crypto.getRandomValues` because `randomUUID` needs a secure context), the same for every Save of that opening, so a retried Save never logs twice; test fakes use the browser's id like the server (`tests/frontend/support/ids.ts` `UUID` to match one).
- Offline download (the server side): `Vehicle`, `Refueling`, `Expense` and `RecurringExpense` are `ISynced` (`Domain/Sync`): `UpdatedAt` marks what a device must download again (`Version` only counts what a writer can conflict with), set on every save by `Infrastructure/Persistence/SyncInterceptor` (Added/Modified), which also writes a `Tombstone` (own id, entity type + id, vehicle id, `PurgedAt`; no foreign key) for every tracked removal, so a removal must go through the change tracker (`UserDataRepository` removes other people's schedules with `RemoveRange` for that); writes that bypass it set the column themselves (`SyncTouch`: `SaveConsumptionsAsync` (only the logs whose consumption changed), `LogPhotoRepository` add/remove (the log), `RecurringExpenseRepository` complete/update/remove (the expenses that list the schedule), `UserDataRepository.MoveAsync`). Default for older rows: `SyncMapping.Epoch` (2000-01-01). `OfflineFeedService.ChangesAsync` (`offlineChanges`): View on the logs (`LogAccessGuard`), first download by `from` (logs only; trash included for Edit, below it a trashed log is sent as `removed`, never its values), later ones by `since` - `Overlap` (2 min) whatever the date, plus `removed` (tombstones since then whose entity does not exist again; a purged or trashed vehicle never gets that far, it is `vehicle.notFound`, so a device drops a vehicle when `myVehicles` stops listing it); refuelings and expenses paged each by its own `(UpdatedAt, Id)` key in the database's order (`OfflineFeedRepository.RefuelingRows`/`ExpenseRows`, `Guid.CompareTo` translated on all four providers: `OfflineFeedTranslationTests`) inside the opaque `OfflineCursor` (`sync.cursorInvalid`, bound to the vehicle; it carries the watermark); schedules all on the first page via `RecurringExpenseService.ListAsync`; `resync` past `Sync:TombstoneRetentionDays` (`SyncOptions`), swept lazily at most hourly. `OfflineSettingsService` (`offlineSettings`/`updateOfflineSettings`, tables `OfflineSettings` (user key, no FK) and `OfflineVehicleSettings` (FK cascade to the vehicle), replaced as a whole, every vehicle in the View scope, deleted with the user) stores `OfflineWindow` rules (`settings.offlineWindowInvalid`); `Vehicle.logCountSince(from)` through `LogCountSinceLoader`. Log rows' `canEdit`/`canDelete` follow the vehicle's `logAccess` only, so a device can work them out from the vehicle.
- Reusable building blocks (use them for new entities, do not add raw numbers): `OdometerReading` (all readings of a vehicle in one table, no maximum, unit per vehicle; neighbour validation across sources), `Cost` (amount + currency), `MeasurementUnits` (per-vehicle distance/volume units, locked once logs exist, never converted). Entities own their reading/cost; trash/restore/purge cascade in code.

### Photo reading

- Photo reading in the app (`Domain/Recognition`, `Application/Recognition`, `Infrastructure/Recognition`; optional, off by default): photos picked in the add dialogs (refueling, expense, recurring "done") are uploaded as drafts with `?form=refueling|expense&locale=xx`; photos added to a saved log in its edit dialog go to `PUT /media/expenses|refuelings/{logId}/photos` with the same query and are queued by `RecognitionService.QueueForLogPhotoAsync` (only the uploader's photo of that log; hints from the log, not the vehicle today: the odometer before the log's day via `OdometerService.PreviousAsync`, the log's own currency); `LogPhotoInfo.reading` (batched by `PhotoReadingsLoader`) gives the edit dialog its readings; with a form, `RecognitionService.QueueForDraftAsync` queues a `PhotoReading` (id = the image id; the purpose decides the allowed kinds; the hints Locale/LastOdometer/Currency/Today are taken right then because the worker has no user). Queueing never fails the upload. `RecognitionWorker` (the app's only background job; registered always, returns at once when not set up) wakes on `IRecognitionSignal` or every 10 s; `PhotoReadingProcessor` claims due readings atomically (repository `ExecuteUpdate`), claims nothing while the provider is unavailable (`RecognitionAvailability`, 30 s cache), retries unavailable providers (5 attempts, 10 s x 3^n), fails refused photos, requeues attempts cut short by a restart (stale after 5 min, or longer than `Recognition:OpenAiCompatible:TimeoutSeconds` + 1 min: `PhotoReadingProcessor.StaleAfter(options)`) and normalises values with `ReadingNormaliser` (a blank beats a wrong value). Values are a JSON column; the table has a cascading foreign key to `Images`, so a reading goes with its picture on every path. `RecognitionOptions` are bound but never validated on start: `RecognitionSetup` turns unusable settings (even unbindable ones) into "off" plus a warning logged by the worker; never let a recognition setting stop the app. The provider is `OpenAiCompatibleRecognitionProvider`, over a named HttpClient without a timeout of its own, for any OpenAI-compatible chat completions API (`Recognition:OpenAiCompatible:*`: `BaseUrl` including `/v1`, `Model` required, `ApiKey` optional as a Bearer token, `SystemPrompt`/`SystemPromptFile` replacing `OpenAiCompatiblePrompt.DefaultSystemPrompt` (printed in `docs/photo-reading.md`, pinned by a test) while the contract (allowed kinds and fields, formats, locale conventions, JSON schema per `ResponseFormat`) is always sent and the latest odometer, currency and today never are; answers are read tolerantly (think blocks, code fences, text parts), a refusal is Rejected, non-JSON is Unavailable, and the values go through the pure `ReadingChecks.Check` in Application (fields per kind, odometer window against `LastOdometer`, litres × price ≈ total, date window, ranges; the model's confidence only ever lowers the result; it returns `CheckedValues(Kept, Issues)`: every drop or doubt carries a `ReadingIssue(Field?, ReadingIssueCode)` from `Domain/Recognition/ReadingIssue.cs`, codes only, never the value, and the provider adds `Unrecognised`/`NothingLegible`; a missing rating reaches the checks as NaN and becomes `NoConfidence`); exception messages carry a status and a snake_case code at most, never server or model text; fixtures in `tests/backend/contracts/openai-compatible`), `NullRecognitionProvider` otherwise. A cloud `BaseUrl` is the operator's explicit choice (it sends photos off-site). The photo's trail is in the log at Debug, tied together by the reading's id (`RecognitionRequest.ReadingId`, set by the processor, never sent to the model): the provider's "Asking {Model} at {Server} to read photo {PhotoId}" and "{Model} answered photo ... said {Said}, listed {Listed}, kept [Field@confidence], issues [Field:Code]" (or "did not read photo ... after {ElapsedMs} ms"), then the worker's "Read photo {Id}: it shows {Kind}, {Sure} of {Values} values are sure enough" (`ProcessedReading.Summary`; `RecognitionSetup.IsSureEnough` is the one rule for what is sure enough, shared by `UsableValues` and `LogPhotoFiller`); at start the worker says at Information which model and server (`ServerAddress.Of`: no user info or query) and where the system prompt comes from, never its text (`RecognitionSetup.SystemPromptSetting`). `docs/photo-reading.md` prints the full request (system prompt, contracts for both dialogs, schema), pinned to the code by `OpenAiCompatiblePromptTests`. `Recognition:OpenAiCompatible:LogTraffic` (default off; the worker warns at start while on) puts `OpenAiTrafficHandler`, a `DelegatingHandler`, to work in the named client's pipeline: every request and answer (also the health check) is written at Information, one entry each, pretty-printed, numbered so the two pair up, with prompts and what the model read in them: the one place the app logs those, so keep it that way (the photo only as its size, the key masked in the header and wherever a server echoes it, bodies cut at 16 000 characters, a server's text escaped so only the layout breaks lines); the provider hands it the photo through `HttpRequestOptions` (`OpenAiTrafficHandler.Photo`). Drafts picked for reading are uploaded as JPEG while the server says reading is on (`usePhotoQueue` asks `recognitionStatus`, the dialog's own question; `resizeImage` `format: 'jpeg'`), since not every model server decodes WebP; `RecognitionNames` holds the kind and field names the prompt and the answer share. GraphQL: `recognitionStatus { available }` and `photoDrafts(ids)` (own drafts only; `UsableValues`: confidence >= `MinConfidence`, hints left out); `markRecurringExpensesDone` takes `photoIds`. Logs never contain read values.
- Logs saved before their photos are read (`Domain/Vehicles/LogReview.cs`): a refuelling may be saved without odometer, volume or total, an expense without amount (its odometer is optional anyway), but only while one of its photos is still being read (`LogPhotoFiller.MayWaitForDraftsAsync`: queued/reading, or uploaded less than `JustRead` ago; updates: `MayWaitForLogPhotosAsync`, a reading of one of its photos that is pending or was just read, the same window); otherwise `log.valuesRequired`. So `Refueling.OdometerReadingId`/`CostId`/`Volume` and `Expense.CostId` are nullable (no row until known; `Update` returns `LinkedChanges` for the repository, which saves the log first and deletes the let-go reading/cost in a second save of one transaction (`LinkedChangesExtensions.SaveLogAsync`: EF never saw the log point at them, so one save could delete a row the log still refers to)). `ReviewState`: AwaitingPhotos -> NeedsReview (values filled, `FilledFromPhoto` flags) / Incomplete (still missing) / None; a person's full save sets None (and marks the log's `LogReview` notifications read). `LogPhotoFiller.FillAsync` (no user) fills only empty values with sure values (like `UsableValues`; the currency only ever comes from a photo, never from the reading's hint: a total without a legible currency is left empty, so the log stays incomplete for the person, instead of a foreign receipt being stored in the vehicle's usual currency), never checks odometer neighbours (user decision: the review catches it), recalculates consumption, logs a Debug line with ids and the names of the values (never what was read) and notifies the creator (`LogFilledFromPhoto`/`LogNotFilled`, derived, topic `LogReview`, subject `Refueling`/`Expense`). It runs after `LogAsync`/`AddAsync` attach the drafts, after an update that leaves the log waiting (a reading may have finished before the save), after a restore, and from `PhotoReadingProcessor` once per log after a round, for readings that finished (Read/Failed) of photos that belong to a log. Stats leave out logs still missing values; `ConsumptionCalculator` makes an interval with an unknown volume/odometer unknown. UI: in the add dialogs those fields stop being required while `drafts.pending` is non-empty (`ReadNote` `waiting`), grids show `ReviewBadge` in the date column and poll (`ServerGrid` `pollWhile`) while a row awaits its photos, edit dialogs show `ReviewCallout` and mark `filledFromPhoto` fields. The recurring "done" dialog has no required amount: an expense is logged exactly when an amount is given or a picked photo is still being read (`ReadNote` `waiting` on the amount); otherwise its photos are not sent and are deleted on close (`recurring.photosNotKept`). Frontend (`recognition/`): `useDraftReadings(uploads, enabled, log?)` (drafts, or with `log` the photos added to that saved log in this dialog session, asked with `fetchPolicy: 'no-cache'` because the answer holds photos without urls; status on open and, while it reads "off", again every 3 s for a minute after each upload; polls every 1.5 s while readings are pending, at most `READING_WAIT_MS` (110 s, just under the server's `JustRead`, so the dialog never offers to save while the server would refuse) after each upload), the pure fill rules in `readValues.ts` (fill fields the user has not changed, starting values count as unchanged, and fields left empty; offer, never overwrite, what they typed; an edit dialog's saved values are `kept`: only offered while not empty, kept apart from `touched`, whose order decides which amount gives way), `useReadFill` (controlled fillable fields), `ReadNote` in `Field`'s `extra` slot ("Read from the photo" / "The photo shows X · Use it"), a `role="status"` announcement, "Reading…" under thumbnails. Tests: `tests/frontend/support/server.ts` answers `RecognitionStatus` with unavailable by default; use `fakeRecognition` from `mocks.tsx` to turn it on.
- Refuelling amounts: the refuelling dialog has a unit price field that is never saved (the server keeps computing `pricePerUnit`); volume, unit price and total follow each other through `keepAmountsInStep` (`src/frontend/refuelingAmounts.ts`, pure): after a change, the least recently typed other amount is worked out (untyped ones first: unit price, then total, then volume), a change that is not the user's (a photo, the starting values) never moves a typed one, and a calculated amount that can no longer be worked out is emptied. It runs as `useReadFill`'s generic `keepInStep` hook (after typing, "Use", a photo and on the starting values); `FillState` keeps `touched` in typing order and the `calculated` fields (`calculateField`/`clearCalculated`), where a photo only offers its value. A calculated amount is worked out again before any other, and gets no reason why a photo did not give it; `problemsToTell` tells a reason about several values (`AMOUNTS_DO_NOT_ADD`) once.
- Why a photo gave less than it might have (`Domain/Recognition/ReadingIssue.cs`, `recognition/readingIssues.ts`): the reasons are kept with the reading (`PhotoReading.Issues`, a JSON column of `ReadingIssue`s, codes only: `Complete(..., issues)`, which also says `Unrecognised` for a kind the dialog does not take), `RecognitionService.IssuesOf` adds the derived `Unsure` (a kept value under `MinConfidence` that no stored reason explains) and GraphQL has `PhotoReadingInfo.issues { code field }`; the add dialogs word them (`recognition/readingIssues.ts`: `mergeIssues` per dialog, `problemsToTell`: a reason about a field the dialog has and no photo filled, one per field, a whole-photo reason only when nothing was filled; `useDraftReadings.explanation`, `useReadFill` `problems` and its `last`, the vehicle's latest reading already formatted; `ReadingProblems` inside the `role="status"` region; texts `reading.issues.<CODE>` in English and Hungarian). A new reason = an enum value in `ReadingIssueCode` + where it arises + the text + the table in `docs/photo-reading.md`.

## Stack decisions

### API and persistence

- **API:** GraphQL (HotChocolate 16 at `/graphql`); the only REST endpoints are the picture endpoints in `Api/Media` (`PUT/DELETE /media/me/avatar`, `PUT/DELETE /media/vehicles/{id}/picture`, `PUT/DELETE /media/expenses|refuelings/{logId}/photos[/{imageId}]`, `PUT /media/vehicles/{id}/photo-drafts`, `DELETE /media/photo-drafts/{id}`, `GET /media/{id}`), because files do not fit GraphQL. The same goes for `POST /imports/{format}` (`Api/Media/ImportEndpoints.cs`; named `/imports` so it does not collide with the SPA route `/import`). Frontend uses Apollo Client 4 and MUI v9 (`@mui/material`, Emotion) with MUI X (`@mui/x-data-grid`, `@mui/x-charts`, `@mui/x-date-pickers`; MIT editions only: Data Grid page size at most 100, no column drag-and-drop or saved resizing), icons from `lucide-react`. Use the MUI components directly, styled through the theme (`theme/`) and `sx`; there is no stylesheet of our own. The app is wrapped in `ThemeRoot` (`main.tsx`, and `renderWithApollo` in tests). **MUI rules learned**: Popover, Menu, Dialog and Drawer are modal, so the page behind them is `aria-hidden` while they are open: tests read it with `{ hidden: true }` or close the layer first, and axe-check a popup menu on its own element, not the whole body; options of a Select/Autocomplete render in a portal, so query with `screen`, not `within`; an `Autocomplete` rendered with a bare `OutlinedInput` must pass the autocomplete's input props through `inputProps` (`slotProps.input` drops their `onChange`); every model handed to the Data Grid (`sortModel`, `paginationModel`, column visibility) must keep its identity between renders, or server mode resets to the first page; jsdom lays nothing out, so heights, hover reveals and charts are checked in a real browser, and tests read the table behind a chart. The breakpoints are the old Radix pixels under MUI's names plus `xxl` (xs 0, sm 520, md 768, lg 1024, xl 1280, xxl 1640): Radix `initial/xs/sm/md/lg/xl` = MUI `xs/sm/md/lg/xl/xxl`; spacing is MUI's 8 px unit (Radix space 1..9 = 0.5, 1, 1.5, 2, 3, 4, 5, 6, 8); JS media checks use `theme/media.ts`.
- **Persistence:** EF Core 10. Provider is chosen at runtime from the `Database` config section: `Provider` (`Sqlite`, `PostgreSql`, `SqlServer`, `MySql`) and `ConnectionString`. With nothing configured it falls back to SQLite (`Data Source=tankstat.db`, working directory); only Sqlite may omit the connection string. MySQL uses Oracle's provider (Pomelo has no EF Core 10 release); MariaDB is not a tested target.
- **Configuration precedence** is standard ASP.NET Core: `appsettings.json` < `appsettings.{Environment}.json` < environment variables (`Database__Provider`, `Database__ConnectionString`) < command line. Environment variables must always be able to override the file; keep new settings in typed, validated options classes bound the same way as `DatabaseOptions`.
- **Migrations:** one project per provider (`src/backend/Tankstat.Migrations.<Provider>`, selected through `MigrationsAssembly`), applied at startup by `DatabaseMigrator`. After changing an entity or its mapping, run `mise run db:migration <Name>` so all four stay in sync (`MigrationsTests` fails otherwise). In-memory SQLite does not work for the app/integration tests because every pooled context gets its own database; use a temp file.

### Authentication, access and deletion

- **Authentication** (`Auth:Mode`: None, Standalone, Oidc, ProxyHeader; default None) is selected lazily at runtime, so all schemes are registered and `ModeAwareSchemeProvider` hides OIDC unless it is the mode; the default scheme follows the mode too (`AuthExtensions`: the proxy's in ProxyHeader, the cookie in Standalone and OIDC, none in mode None, so a cookie left over from another mode never names a user in mode None, and nothing may authenticate or challenge without naming its scheme). Sign-in only produces a cookie/proxy identity that names a user; `HttpCurrentUser` always reloads the user (admin flag, disabled, session version) from the database. Users live in the `Users` table for every mode. Standalone passwords use the framework PBKDF2 hasher; reset tokens are random, stored hashed, single use, one live link per user (every issue, the administrator's too, replaces the earlier ones and lazily purges the rows whose lifetime ended over a day ago, by `IssuedAt` and the current `ResetTokenMinutes`); a self-service request (`PasswordResetService.IssueUnlessCoolingDownAsync`) issues nothing without SMTP or while the user's latest link is younger than `Auth:Standalone:ResetCooldownMinutes` (5, 0 = off) and still valid, answered the same way and logged by user id. The look at the latest link and the replacement run under a per-user `StripedLocks` lock (so a burst of requests sends one mail), the e-mail after it; a link whose e-mail failed is taken back, so it holds no request back. Never expose `User` entities directly in GraphQL (password hash): use the DTOs in `Api/GraphQL/Dtos.cs`. The OIDC browser flow: `auth/OidcSignIn.tsx` sends a fresh visitor to `/auth/oidc/login?returnUrl=<path+query>` through the `navigation.replace` seam (`src/frontend/navigation.ts`; spy it in tests, jsdom cannot navigate), shows a signed-out screen while `auth/oidc.ts`'s `signedOut` flag is set (sessionStorage `tankstat.auth.signedOut`, set by `NavList`'s sign-out in OIDC mode, so the provider's live session does not sign the user straight back in) and a failed screen for `?signIn=failed&reason=<code>`; on the server `OnRemoteFailure`/`OnAccessDenied` redirect there through `Api/Auth/OidcFailures.cs` (`OidcFailure` codes classified by exception type, a nonce or state mismatch counting as ours; `ProvisionOidcUser` refuses with `OidcSignInRefusedException` or the `ForbiddenException` itself, never a message; `LocalPathOrRoot` accepts one leading slash and printable ASCII only) and log one Warning with the code and the exception type, never the provider's text. `OidcProviderFlowTests` runs the whole flow against a stubbed token endpoint with a test-signed id_token. **Sessions (Standalone and OIDC):** a short access cookie (`tankstat.session`, `Auth:AccessTokenMinutes` 15, not sliding, always persistent: `SessionCookies.SignInAsync`; OIDC sets `IsPersistent` in `ProvisionOidcUser`, which must only call `IssueRefreshAsync` because the remote handler signs the principal in itself) carrying a `sid` claim, plus a refresh cookie (`tankstat.refresh`, `Path=/auth/token`, HttpOnly, `SameSite=Lax`) holding the refresh token of a `UserSession` row (`UserSessionService`, the `PasswordResetService` stack: `"{id:N}.{secret}"`, SHA-256 hash, fixed-time compare; plus the secret encrypted by `ISecretProtector` = the Data Protection key ring). `POST /auth/token/refresh` (`TokenEndpoints`, needs `X-Requested-With: fetch`, 404 in None/ProxyHeader) rotates the secret and slides the expiry (`Auth:RefreshTokenDays` 90; session rows are only written by conditional `ExecuteUpdate`s: a rotation only while the presented secret is current and the session not revoked, the loser of two at once answered like the grace, a revoke only where `RevokedAt` is null, never a whole-row save); the previous secret within `Auth:RefreshRotationGraceSeconds` (60) gets the *current* secret back (no new rotation, so racing tabs converge), later it is reuse: the session ends with a Warning. Every refusal is `UnauthenticatedException` (401 + both cookies cleared). Password change: `AdoptVersionAsync` on the asking session *before* `RevokeOthersAsync`; reset, admin set-password and disabling revoke all; `HttpCurrentUser`'s per-request reload stays the immediate revocation, and it also refuses an access cookie whose `sid` session ended. `POST /auth/token/logout` (what the app uses, works after the access cookie ran out) and the `logout` mutation (by `sid`) end the session; the Account page lists the user's devices (`mySessions` with `current` from the `sid`, `revokeSession(id)`, which also clears the cookies when it is this device, `revokeOtherSessions`; `UserSessionService.ListMineAsync`/`RevokeMineAsync`/`RevokeMyOthersAsync`, `auth.modeUnavailable` outside Standalone/OIDC; UI `pages/account/SessionsPanel.tsx`, this device's Sign out is the normal sign-out through `auth/useSignOut.ts`, shared with `NavList`; `ClientLabel` turns the User-Agent into "Firefox on Linux" and only that is stored; tests get one device by default from `support/server.ts`); stale rows go a week later, lazily on refresh. The key ring is persisted (`DataProtection:KeysPath`, `KeyRingOptions`, Docker `/data/keys`; `TestApp` gives each host its own folder; `SharedData` in `TestApp.cs` gives several hosts in turn one database, key ring and upload folders, an instance restarted with other settings, and its `StandaloneAdminCookiesAsync` hands back a Standalone administrator's cookies for it). Frontend: `auth/refresh.ts` (`refreshSession` single flight per tab, `fetchSignedIn` for REST: one retry after a 401, `signOutDevice`), `refreshLink` in `apolloClient.ts` (UNAUTHENTICATED → refresh → the operation once more; when the device has to sign in the `Session` query is asked again so the sign-in screen appears, a refresh that did not get through leaves the answer alone; never for the sign-in operations, except that a `Session` answer of nobody in STANDALONE/OIDC tries one refresh first, so a reopened app with only its refresh cookie left stays signed in); test fakes default to a refused refresh and a working sign-out (`support/server.ts`).
- **Access layer:** every user-owned entity implements `IOwned`. Use cases never compare owners themselves; they call `AccessService` (`ScopeAsync` for lists, `LevelAsync`/`CanAsync` for single items), and repositories filter lists with `InScope(scope)`. Levels are `None<View<Edit<Delete>`: Edit creates/changes/trashes/restores, only Delete (implicit for owner/admin, or granted) purges. Rules live in the pure `AccessPolicy` (admin/owner full; others get the larger of the instance default and any grant). Per-vehicle log sharing uses generic `ResourceGrant`s resolved by `OwnerScope` (owners + granted resource ids) and `InScope(scope, resourceIdSelector)`; granting never gives more than the granter holds. Invisible items look non-existent (null / `NOT_FOUND`), not `FORBIDDEN`. With `Auth:Mode=None` the actor is `Principal.Anonymous` (full access) and admin features are unavailable. The full, paged vehicle list (`vehicles`/`vehicleCount`, `/vehicles`) is such an admin feature; everyone else uses `myVehicles`/`myVehicleCount` (owned + shared, by name, `search` on name/license plate done in the database, `skip`/`take`), which the home page pages with infinite scroll (`fetchMore` + an `IntersectionObserver` sentinel + a Show more button).
- **Soft delete:** deletable entities implement `ISoftDeletable` (`DeletedAt`). Vehicles have an EF global query filter hiding trashed rows, so normal queries are safe by default; trash/restore/purge code must use `IgnoreQueryFilters()` (see `VehicleRepository`). Trashing and restoring need Edit access, emptying the trash needs Delete access and only purges what the user may delete (the UI gets `...DeletableCount`); `PurgeAsync` returns the picture ids so the files are removed too. `DeletedAt` is stored as a UTC date-time so comparisons translate on every provider. There is deliberately no scheduled purge job yet (user decision), only the user-initiated "empty trash".

### Tooling, CI and delivery

### Offline sync (frontend)

The server side is under Photos, uploads and shared building blocks (client ids and versions, the offline download) and Notifications (`SyncNotificationSync`); the contracts are in `docs/development.md`, what a user sees in `docs/install-as-an-app.md`.

- **Connectivity** (`src/frontend/offline/`): `connectivity` is a store of the server's reachability (`unknown` counts as reachable), fed by request outcomes, not `navigator.onLine` (a LAN server is out of reach from an online phone): `createOfflineLink` (first link after the error link in `apolloClient.ts`) and `trackedFetch` (the REST calls, `auth/refresh.ts`) mark it unreachable on no answer, a `ServerParseError` or a gateway 502/503/504 (`classifyFailure`), reachable on any answer, and while unreachable send nothing and fail at once with `OfflineError` (`errors.offline`, an info alert with `role="status"`; `reportOperationError` does not log it). `startOfflineRuntime` (main.tsx) probes with `Health` under `context: { offline: 'bypass' }` (`watchConnectivity`: `PROBE_DELAYS` 2/5/15/30/60 s, at once on `online` and when the tab is shown; `offline` marks it unreachable) and refetches the active queries when the server is back. UI: `shell/ConnectivityIndicator.tsx` (top bar chip + one live region announcing changes; the top bar must never be wider than the screen, or the whole page scrolls sideways: below `MEDIA.narrow` its chips go `compact` (Offline as an icon with the word visually hidden, the pending chip as its number with the sentence as its `aria-label`), the admin badge hides, the colour mode and language menus move into the drawer (`DrawerSettings`) while there is one, the title is the only thing that shrinks, and the header clips as a last resort), `HealthFooter` (Try again = `probeServer`), `ServerGrid`/`NotificationBell`/`useDraftReadings` poll only while reachable.

Visits, trashes, restores and photo changes have no Edit.
- **The server's side of sending**: `SyncMutations.SyncChanges` (`Api/GraphQL/SyncGraphQL.cs`: `ChangeInput` with exactly one of 22 operations (`setVehiclePicture`/`removeVehiclePicture` set a vehicle's picture from one of the sender's drafts, `ImageService.SetVehiclePictureFromDraftAsync`: idempotent (a draft row a first try left behind goes), a per-vehicle lock that uploads and removals take too (`StripedLocks`; the picture is not versioned), the draft's file moved into the picture folder, the old picture deleted; or remove it; the four before them add or remove a saved log's photo: `LogPhotoService.AttachDraftAsync` turns one of the sender's drafts into its photo, idempotently; the services come through the scoped `SyncChangeServices`), `sync.oneOperationRequired`, adds need an id `sync.entityIdRequired`; each becomes a `SyncChangeRequest` whose `Apply` calls the same service as the mutation with `expectedVersion`, and whose `VehicleOf` finds the vehicle without access checks) → `SyncService.SyncAsync` (batch checks `sync.tooManyChanges`/`sync.duplicateChange`/`sync.payloadTooLarge`, a striped per-user lock, a known id of another user is `sync.idTaken`, a known id of the same user is answered from the ledger, a `KeyedException` parks with key + args as text (filed under its vehicle and that vehicle's owner, or with the sender alone when the vehicle does not exist: the ledger's vehicle has a foreign key), anything else stops the batch with earlier rows recorded; a row is recorded with `CancellationToken.None` once applied, and one another server recorded first (`AddOnceAsync` false) is answered from the ledger; applied rows older than `Sync:RetentionDays` purged after each batch) → `SyncChange` rows (`SyncChanges` table: id = the device's change id, payload JSON ≤ 4000, FK cascade to the vehicle, deleted or moved with the user). A change may carry `base` (JSON of the values it was made from; kept apart from the payload in `SyncChange.Base`, only on parked rows, never read by the server) and `SyncChangeInfo` answers it with `current` (`SyncCurrent`: LIVE/TRASHED, version, `changedAt`/`changedBy`/`lastChange`, exactly one of `vehicle`/`refueling`/`expense`/`schedule`) through `SyncCurrentLoader` over `SyncTargetService.CurrentAsync` (re-checks access whoever sent it: View for what is live, Edit for what is in the trash, nothing for a log of a trashed vehicle or what is gone). `resolveSyncChange` keeps the `expectedVersion` of an edited change (a merge against the version the person saw parks again when it moved), applies a photo or picture change with its sender's draft whoever applies it (`uploadedBy`, the change's `SubmittedById`), and takes `restoreFirst` (an edit of a log or vehicle in the trash: restore, then edit, back to the trash when the edit is refused; `sync.cannotRestoreFirst`); a trash of what is already in the trash is applied on the sync path only (`TrashOnce` + the services' `InTrashAsync`).
- **Offline data** (Account page, `pages/account/OfflineDataPanel.tsx`, shown when signed in or in mode None): `WindowPicker` (a kind select, `FieldDate` for a start date, six number fields for a timespan; reports the rule or null) for the default and, in a dialog per vehicle (`withDefault`), an override; `describeWindow` words a rule; `Estimate` asks `OfflineEstimates(from)` (one request per start date, `onlineOnly`); Save = `updateOfflineSettings` (the whole set) then a download; choosing is hidden while unreachable. The device side: storage (`navigator.storage.estimate`), last download (`LAST_PULL_KEY` kept by the engine), Download now (`offlineDownload()`, progress from the engine's state in a `role="status"` line) and Remove (`deviceData.removeAll()` after a `ConfirmDialog`). Tests: `support/server.ts` answers `OfflineSettings`/`OfflineVehicles`/`OfflineEstimates`/`UpdateOfflineSettings` by default; `provideOfflineDownload(engine)` gives the screens an engine without starting the runtime.
- **Tests**: `setup.ts` resets connectivity and `deviceData` (fresh memory storage) after each test; `deviceData.settled()` waits for pending writes; `fake-indexeddb` for the IndexedDB storage; `support/offlineFeed.ts` is the feed in memory.

### Logging

- **Logging:** the standard `ILogger<T>` on the console, nothing else installed (no Serilog); Application uses `Microsoft.Extensions.Logging.Abstractions` (the layering rule only forbids EF Core and HotChocolate there). Style: `logger.LogX("... {Placeholder}", id)` with named placeholders, no `[LoggerMessage]`; the field is called `logger`, never `log` (a "log" here is a refueling or expense). Levels: *Information* for what an operator looks for (sign-ins and sign-outs, password changes, administration, access changes, sharing, imports, emptied trashes, migrations, reachability coming back), *Debug* for ordinary changes (with entity ids), *Warning* for refusals, failed sign-ins and failures that used to be swallowed (a `catch` that swallows something an operator would want to know about logs its exception; a provider that is not healthy says why by throwing, see `IRecognitionProvider.IsHealthyAsync`), *Error* only for unexpected exceptions, which `Api/GraphQL/GraphQLLoggingListener` logs once (HotChocolate has no logging of its own; it dedupes by exception instance; a non-null field that was null (`ErrorCodes.Execution.NonNullViolation` at a field path; without a path the same code is a required variable the client left out) is a server bug no hook tells about, so `RequestScope.Dispose` finds it in the result and logs a Warning naming the field the way the schema does (`SchemaField` walks the operation's selections by the path's response names); a request the engine turns down, such as a missing variable, is the client's doing and only Debug; `MediaEndpoints.TranslateErrors` logs the keyed errors of the REST side, an unexpected REST exception is logged by the framework as it always was). Ids only in the app's own lines: never e-mails, names, plates, notes, amounts, passwords, reset tokens or links, API keys, OIDC subjects or read values (one opt-in exception: `Recognition:OpenAiCompatible:LogTraffic`, see Photo reading in the app), and nothing a client sent (variables, documents, request-error text; an operation name only when it is a valid GraphQL name, a grid id only after it passed `GridSettings.CheckGridId`; a field by its schema name `Type.field`, not by the alias a client gave it; REST lines name the route pattern, not the path: a line break in client text would forge a log line). The edge, which `docs/configuration.md` states: the text of an unexpected exception and the framework's own lines are written as they come (a database can quote values in its error), and `Microsoft.AspNetCore` must stay at Warning or above (its request lines hold reset-link tokens). A lasting condition is logged when it changes, not on every check (`RecognitionAvailability`, `EfDatabaseProbe`); `SmtpEmailSender` throws an `EmailSendException` that keeps only the status of a refused command (a mail server's answer quotes the recipient). The shipped `appsettings.json` silences EF Core's SQL and the HttpClient's per-request lines, keeps `Tankstat` at Information (Debug in Development); smoke tests start the app in Production and expect "database migrations" and "up to date" in its output and nothing with "Photo reading" by default, so those texts are a contract. Console options such as `IncludeScopes` or `TimestampFormat` only apply when `Logging:Console:FormatterName` is set (`simple` or `json`); a scope must be a message with a placeholder (`BeginScope("UserId: {UserId}", id)`), since the console prints a dictionary as its type name (the smoke test reads the real output). Tests: `TestSupport/CapturedLog` (`World.Log` in the Application tests, `TestApp.Log` in the API tests, `TestDatabase.Log`) and canary tests that run a broad flow and assert that no typed value or secret reaches a line (`LoggingTests` in Application and in the API integration tests); find a line by its class (`log.From<T>()`) and level and read the values of its placeholders (`entry.Values["UserId"]`), do not assert the wording of a message. Frontend: `apolloClient.ts` (`reportOperationError`, an Apollo `ErrorLink`) and `ErrorBoundary` write unexpected request failures and crashed pages to the browser console and send nothing; an error with a `key` is expected (the screen shows it) and not reported.

### Settings, home cards and notices

- **Settings (`Domain/Settings`, `Application/Settings`):** what the UI remembers for a user follows them to every device. Three tables keyed by the user id with **no** foreign key to `Users` (the anonymous user of `Auth:Mode=None` has no row and shares them with every visitor; `UserDataRepository` deletes them with the user, never moves them): `UiSettings` (`NavOpen`, `Language`, `ColorMode`: Light/Dark/System, stored by name, null = Dark; `Surface`: Glossy/Transparent/Opaque, stored by name, null = Glossy, `settings.surfaceInvalid`), `GridSettings` (per grid id: `Order`/`Hidden` as JSON text, `PageSize`, `SortColumn`, `SortDirection`, which now lives in `Tankstat.Domain`) and `VehicleOrders` (per vehicle: `Position`; FK cascade to `Vehicles`). ## Testing requirements

Every change must keep all three layers covering behavior, so breaking changes are caught:
- **Unit:** `tests/backend/Tankstat.Application.UnitTests` (pure logic, fakes for ports), `tests/backend/Tankstat.Infrastructure.UnitTests` (config binding, EF adapters on in-memory SQLite), `tests/frontend/*.unit.test.*`.
- **Integration:** `tests/backend/Tankstat.Api.IntegrationTests` (`WebApplicationFactory<Program>`, real DI/GraphQL/EF) and `tests/frontend/*.integration.test.*` (Apollo against msw-mocked GraphQL over HTTP).
- **API:** `tests/backend/Tankstat.Api.ApiTests` are black-box GraphQL contract tests against a running server (`TANKSTAT_API_URL`); `scripts/test-api.sh` starts one on a throwaway port with an in-memory database. A schema change the frontend depends on must fail here.

Frontend test files must be named `*.unit.test.ts(x)` or `*.integration.test.ts(x)` to be picked up by `vitest.config.ts`. They live in a folder per feature area, nested where an area has parts (`app/` with `apollo/` and `i18n/`, `auth/`, `pwa/`, `offline/` (connectivity and device data), `home/`, `vehicles/` with `logs/`, `recurring/` and `dashboard/`, `recognition/`, `pictures/`, `trash/`, `grid/`, `settings/`, `notifications/`, `admin/`, `import/`, `ui/` for the theme, forms, dialogs, toast and other shared building blocks); unit and integration tests of an area sit side by side, and the shared helpers (`mocks.tsx`, `server.ts`, `setup.ts`, `dates.ts` for the date pickers' fields) are in `tests/frontend/support/`. `stubViewport(kind, { scheme })` answers real media queries (widths, hover, pointer, `prefers-color-scheme`), and `renderWithApollo` uses the instant theme (no transitions), so a closed dialog is gone at once. A new test goes into the folder of the feature it covers.

## Scope

Besides health, auth and administration, the app covers vehicles and their refuelling logs (create/edit/trash/restore/purge, sharing a vehicle's logs, pictures) and recurring expenses (schedules by time, distance or both, shown on the home page), per-user notifications (access changes, due schedules), and per-vehicle statistics (the dashboard's key figures, the preset and saved charts, consumption between full fill-ups); there are no cross-vehicle reports. The OIDC token-validated provisioning path is covered by unit tests only, not against a real provider. Data created with auth off is owned by the anonymous user (id all zeros) and is only visible to administrators after switching modes. Photos picked in the add dialogs can be read by a vision model behind any OpenAI-compatible API (a server the operator runs, or a paid one at their choice) to fill in the form, or the saved log later (marked for review); it is off by default and nothing changes without it. Do not invent domain features or add infrastructure (CI, Docker, codegen) that was not asked for.
