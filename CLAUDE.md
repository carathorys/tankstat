# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Tankstat is a self-hosted web app: React + TypeScript frontend (Vite) and a .NET 10 backend. Kestrel serves both the API and the built SPA in production.

The README is short on purpose (what it is, the features by name, a quick start, the development commands, links). The user and operator documentation is in `docs/`, one file per topic: `configuration.md` (database, files, defaults, notifications, the app's own settings file, logging), `authentication.md` (modes, settings, access control), `user-guide.md`, `importing.md`, `install-as-an-app.md`, `photo-reading.md`, `backup-and-restore.md`, `self-hosting.md` and `development.md`. When a change alters behaviour or a setting that a docs file describes, update that file (and the README only when a feature's one-line summary changes). `docs/photo-reading.md` prints the built-in system prompt, both contracts and the JSON schema, pinned to the code by `OpenAiCompatiblePromptTests`.

Pull request descriptions never carry the claude.ai session link (no `https://claude.ai/code/session_...` line); the "Generated with Claude Code" line stays. Commit trailers are unchanged.

Issue workflow (`.claude/skills/`, usable by any agent): `/triage N` claims an issue with the `triaging` label (and skips issues carrying it unless named), analyses, reproduces and plans it, posts the handoff on it, labels it `triaged` and removes `triaging`, never fixes; `/dev N` implements a `triaged` issue (refuses one that is not; on one another agent has `in progress` it stops and asks whether to take it over; claims it with `in progress` first) in a git worktree of its own on a branch off the freshly pulled `main` (the previous task's finished worktree is removed when the next task starts; an unrelated request asks first): targeted tests while working, the full suite before every commit and/or push, a draft PR labelled `WIP` until finished, then ready to merge without waiting for CI; `/review N` (or `next`: the oldest open non-draft PR) reviews only a PR that carries neither `reviewing` nor `reviewed` (on one being reviewed it asks whether to take it over, on a reviewed one it reviews again only on request), claims it with `reviewing` first, runs the built-in `code-review` (its levels `low`..`max`, `--max-findings`, `--fix` and `--comment` passed on; not `ultra`) and reports the findings in the session; it posts on the PR only when asked: `--comment` for an inline comment per finding, `--summarize` for one summary comment; then it labels it `reviewed` and removes `reviewing`; only with `--fix` does it change the PR's code: in a worktree of its own on a `review/<N>` branch off the PR's head, the full suite before committing, pushed to the PR's branch without force.

## Toolchain and commands

All tooling is managed by `mise` (`mise.toml`: Node LTS, .NET 10). Prefer `mise run <task>` over calling tools directly.

- `mise run install` - `npm ci` + `dotnet restore`
- `mise run dev:api` / `mise run dev:web` - API on :5080 with hot reload; Vite dev server proxying `/graphql`, `/auth/oidc/`, `/auth/token/`, `/media` and `/imports` to it (only those two of `/auth`: `src/frontend/auth/` modules are served at `/auth/...`, so no module may live in `src/frontend/auth/oidc/` or `src/frontend/auth/token/`)
- `mise run test` - typecheck, lint, then every test layer (run this before finishing a change)
- `mise run test:unit`, `test:integration`, `test:api` - single layers
- `mise run build` - self-hostable output in `out/` (published API + SPA in `wwwroot`)

Single tests:
- Frontend: `npx vitest run tests/frontend/<area>/<file>` (add `-t "<name>"` to filter)
- Backend: `dotnet test tests/backend/<Project> --filter "FullyQualifiedName~<Name>"`

Code lookups (who uses a symbol, where it is defined, a file's symbols) go through the LSP tool (csharp-ls, typescript-language-server), with grep as the fallback. Check first that it answers for a symbol you know: csharp-ls can index a stale copy of the solution or answer nothing once its worktree is gone, and the TypeScript server's first `findReferences` after it starts can return only the declaration (ask once more before believing "no references"). When the LSP does not work, say so to the user: when it first fails, and again now and then while it stays broken, not on every call.

## Project structure rules

### Layout and layers

- All source lives under `src/`, all tests under `tests/`. Each is split into `backend/` and `frontend/`.
- Frontend tooling (`package.json`, `vite.config.ts`, `tsconfig*`) lives at the repo root so `src/frontend` and `tests/frontend` share one `node_modules`. Vite's `root` is `src/frontend`; build output goes to `dist/`.
- Backend follows clean architecture, dependencies pointing inward only: `Api -> Application, Infrastructure`; `Infrastructure -> Application`; `Application -> Domain`. Application and Domain must not reference EF Core or HotChocolate. Application defines ports (interfaces such as `IDatabaseProbe`); Infrastructure implements them. Each layer registers itself through an `AddApplication` / `AddInfrastructure` extension.
- Add new .NET projects to `Tankstat.slnx`.

### Fuel log and statistics

- Domain: fuel log. `Vehicle` and `Refueling` entities have private setters and `Create` factories that enforce the rules (throwing `DomainException`); Application services (`VehicleService`, `RefuelingService`, `ResourceSharingService`, `ImageService`) use repository ports; the GraphQL error filter maps `DomainException` / `NotFoundException` to `VALIDATION_FAILED` / `NOT_FOUND` errors.
- Fuel consumption (`Refueling.Consumption`, fuel per 100 distance units between full fill-ups) is stored, not computed on read: `ConsumptionCalculator` (pure, Domain) recomputes a vehicle's whole chain and returns only the logs whose value changed; `RefuelingService` calls it after every log/update/delete/restore (`RecalculateConsumptionAsync`; imports pass `recalculateConsumption: false` and recalculate once; the seeder applies it directly) and `DatabaseMigrator` backfills once after the `AddRefuelingConsumption` migration. A log with `MissedPreviousFillUp` (a fill-up before it was not logged; GraphQL `missedPreviousFillUp`, omitted on update = kept) breaks the chain: its interval has no consumption and the next one starts from it. Anything that changes logs, odometers, volumes, full-tank or missed flags must go through that path.
- Statistics (`Application/Stats`): `StatsCalculator` (pure) turns a vehicle's live records (`IStatsRepository.LoadAsync`) into chart data and key figures; costs are always per currency, never converted. The vehicle summary (card and dashboard key figures) has a main currency (most spent in over the last year) for `thisMonthSpend`/`lastMonthSpend`/`spendTrend`, plus `spending` (`CurrencySpend` per currency used this month or last, main first), which the UI shows joined (`spending.ts` `spentText`: "52,000 Ft · €73.90") so nothing spent in another currency goes unshown. A chart is a `ChartConfig` (metric, grouping, kind, range incl. custom from-to, stacked) that `Validated()` normalises (dates dropped for presets); saved ones are `VehicleChart` rows (typed columns, personal or shared, managed by `ChartService`). Presets live in the frontend (`dashboard/DashboardPanel.tsx`) and use the same `vehicleChartData` query. Add a metric = enum value + calculator case + i18n (`charts.metrics.*`) + builder rules in `dashboard/chartFormat.ts` (`normalise` mirrors `ChartConfig.Validated`).

### Expenses, imports and recurring expenses

- Expenses (`Expense`, `ExpenseService`) are non-fuel costs of a vehicle (free-text category, optional odometer reading); they use the vehicle's *logs* access rules and trash like refuelings. Importing (`Application/Imports`): one `IImportParser` per format turns a file into an `ImportBatch` (`FuelioCsvParser` first); `ImportService` keeps the batch under a token in `ImportSessionStore` (in memory, 30 minutes, per user), previews duplicates and commits row by row through `RefuelingService`/`ExpenseService`/`RecurringExpenseService` (schedules last, so a distance schedule without a known odometer starts from the imported readings), so all rules apply and bad rows are reported, not fatal; repeating Fuelio reminder templates become `ImportedRecurring` (duplicates: same title). A new format = a new parser + its tests; the UI (`pages/ImportPage.tsx`) lists formats in `FORMATS`.
- Recurring expenses (`Domain/Recurring`, `Application/Recurring`): `RecurringExpense` is a schedule of a vehicle (kind Time, Odometer or Combined = whichever is reached first; interval in months and/or distance; baseline = last done date and odometer; per-item warn days/distance). It is not a cost (no `Cost`) and its baseline odometer is a plain number, not an `OdometerReading`, so it never takes part in neighbour validation. `RecurrenceCalculator` (pure) turns it plus today and the vehicle's latest reading into a `RecurrenceStatus` (Upcoming/DueSoon/Overdue, which limit decides, days and distance left); the service computes it on every read, nothing is stored (`Vehicle.recurring` goes through `RecurringByVehicleLoader` -> `ListForVehiclesAsync`, so a list of vehicle cards costs a fixed number of queries, not several per card). `RecurringExpenseService` uses the vehicle's *logs* access rules through `LogAccessGuard` (like expenses and photos); `MarkDoneAsync(ids, input)` marks a service visit: schedules of one vehicle (another vehicle's or an unknown id is `recurring.notFound`; ids deduped; none is `recurring.noneSelected`), one Edit check, `CheckDone` on every one first (its errors carry the schedule's `title`: `doneBeforeLast`, `doneOdometerRequired`, `odometerBelowLast`; `Apply` keeps `recurring.odometerRequired`), then, when an amount or photos came, ONE `Expense` through `ExpenseService` (all expense/odometer/photo rules; title/category default to `RecurringDoneDefaults`: titles joined and cut at 120, common or first category, the note only for a single schedule), then `CompleteAsync` saves the moved baselines and the `RecurringCompletion` links (expense id + schedule id) in one save; a failure trashes the expense (`TryTrashAsync`). All or nothing; the amount is never split. `RecurringCompletions` has one foreign key, cascading from the schedule; the expense side has none (expenses and schedules both cascade from the vehicle, and SQL Server refuses two cascade paths), so `ExpenseRepository.PurgeAsync` removes the links in code like photo rows. `Expense.schedules { id title }` comes through `ExpenseSchedulesLoader` (the Expenses grid's `schedules` column, `defaultHidden`). Schedules are hard-deleted (no trash); the table cascades with the vehicle and `UserDataRepository` moves or purges them. GraphQL: `Vehicle.recurring`, `add/update/deleteRecurringExpense`, `markRecurringExpensesDone` (`{ schedules, expense }`), `Expense.schedules`. UI: the vehicle page's Recurring tab (`RecurringPanel` with a selection column and *Mark selected as done*, `RecurringFormDialog`, `RecurringDoneDialog`: the vehicle's schedules as labelled checkboxes, `recurringDone.ts` `preselect` ticks the clicked one plus everything not `UPCOMING`, optional amount, prefilled title/category) and, on the home cards, attention badges (`useDueText`, `RecurringStatusBadge`) each with a Done button that opens `RecurringDoneDialog` right there (see Home cards).

### Notifications

- Notifications (`Domain/Notifications`, `Application/Notifications`): a `Notification` belongs to its recipient only (not `IOwned`; every query filters by `RecipientId`, admins included) and is attached to a subject and an optional context by `NotificationRef` (entity type + id, no foreign key; a new source adds a `NotificationEntityType`). Its identity (unique index) is recipient + topic + subject + context id (`Guid.Empty` when none) + `Occurrence`. Every producer goes through `Notifier.NotifyAsync(actorId, drafts)` (the actor is never notified); the pure `NotificationPolicy` decides: *derived* drafts (with an occurrence, worked out from current state) are added once and only raised to a more urgent kind (reopened); *events* are folded into the unread one of the same topic/subject/context (`Count`), removed when undone (`After == Before`), and past `Notifications:MaxPerHour` become one `MoreActivity` digest. Sources: `ResourceSharingService` and `AccessAdminService` (events built with `NotificationArgs.AccessChange`, `Before`/`After` = access levels), `SyncNotificationSync` (`SyncChangeParked`, topic `Sync`, subject `SyncChange`, context the vehicle, occurrence `parked`: every parked change the reader may see as themselves or sent; args `change` (kind in API spelling), `vehicleName`, `submitterName`, `reason`, `reasonArgs` as JSON), `BackupFailureNotifier` (`BackupFailed`, topic `Backup`, derived, subject `Instance`, occurrence the server's local date of the run: every enabled administrator, the anonymous user in mode None, args `error` (a key), `errorArgs` (its arguments as JSON, like `reasonArgs`) and `startedAt`; see Backups), and `RecurringNotificationSync`, which, like `SyncNotificationSync`, runs lazily once per request from `NotificationService` (no background job) over `AccessService.PersonalLogScopeAsync` (an admin's blanket rights do not count; anonymous keeps everything), one occurrence per schedule cycle (last done date + odometer). Arguments are display-ready snapshots; the frontend words them per kind (`notifications/useNotificationText.ts`, `notifications.kinds.*`; a kind the bundle does not know, from a newer server while an older tab waits for its update, is `notifications.unknownKind` without a link, never a crash: the bell is outside the error boundary). Users never delete notifications (deliberate): they only mark them read (`ReadAt`; `markNotificationsRead` returns the changed rows so Apollo updates loaded lists in place), and `NotificationService` purges the ones read more than `Notifications:ReadRetentionDays` ago on the same lazy path, keeping reminders of schedules that are still due and of changes still parked (else the sync would re-add them). UI: `shell/NotificationBell.tsx` (polls the unread count every minute; tests get an empty-inbox default handler from `tests/frontend/support/server.ts`, override with `fakeNotificationBackend`) and `pages/NotificationsPage.tsx`. User deletion purges the inbox; actions go through `notifications/useNotificationActions.ts`.

### Photos, uploads and shared building blocks

- Photos (`Application/Photos`, `Domain/Photos/LogPhoto`): up to 10 photos per refueling or expense, one `LogPhoto` table for both kinds (log id without a foreign key, like `ResourceGrant`; cascading foreign key to the vehicle). `LogPhotoAccess` applies the vehicle's *logs* rules through `LogAccessGuard`, the one place (shared with `RefuelingService`/`ExpenseService`) that decides who may see or edit a vehicle's logs (View to see and to GET `/media/{id}`, Edit to add/remove; trashed logs hide their photos); `LogPhotoService` adds/removes; `IExpenseRepository`/`IRefuelingRepository.PurgeAsync` return `PurgedLogs`, delete the photo rows in the same save, and the services then remove the folders. Upload is `PUT /media/expenses|refuelings/{logId}/photos`, remove is `DELETE .../photos/{imageId}`; GraphQL only has the read field `photos { id url }` (batched per response by `ExpensePhotosLoader`/`RefuelingPhotosLoader`, which trust the already authorised parent log). Photos picked for a log that is not saved yet are uploaded at once as `PhotoDraft`s (`PhotoDraftService`; `PUT /media/vehicles/{id}/photo-drafts`, `DELETE /media/photo-drafts/{id}`; id = the image id, folder `vehicles/<id>/drafts`, visible to the uploader only, Edit on the vehicle's logs to upload, at most 20 per user and vehicle, expired after a day and removed whenever anyone uploads a draft, so no background job; only a picture still in the draft folder is deleted with its row (`ImageService.DeleteDraftPicturesAsync`): one moved out is a photo or a vehicle's picture, even when a failure left its row behind); `logRefueling`/`addExpense` take `photoIds`, which `LogPhotoService.RequireDraftsAsync` checks before the log is saved and `AttachDraftsAsync` turns into its photos afterwards (the file moves into the log's folder; a draft that cannot be attached goes back and never fails the save, the response's `photos` tell the UI). The frontend `PhotoGallery` (+ `usePhotoQueue`/`usePhotoSession`: per-photo uploading/uploaded/failed with retry, Save waits for uploads, closing the dialog deletes its drafts, `PhotosLeftOut` when the server attached fewer) has a camera input (`capture="environment"`) and a library input; photos are resized to 1600 px in the browser.
- Upload folders: `StoredImage.Folder` (null = legacy file directly in `Storage:Path`) built only from ids by `ImageFolders` (`users/<id>`, `vehicles/<id>/picture`, `vehicles/<id>/drafts`, `vehicles/<id>/expenses|refuelings/<logId>`); `FileSystemImageStore` re-validates the folder. Two roots with the same layout below them (`ImageFolders.RootsOf`): the pictures (`Storage:Path`: avatars, vehicle pictures, legacy files) and the photos of logs (`Storage:PhotosPath`, **opt-in**: drafts and log photos, which grow without limit; unset or blank = the very folder of `Storage:Path`, so nothing moves on upgrade, `StorageOptions.PhotosRoot`; the Docker image does not set it but makes `/data/photos` owned by the app's user, so a volume of its own there is writable (`docker-smoke.sh` mounts one with `Storage__PhotosPath=/data/photos`); the two may be one folder, never nested, `StorageOptionsValidator` refuses that at start); the store resolves a folder against its root, a draft made a vehicle's picture moves between them (`File.Move`, which copies between disks; never `Directory.Move`), and a photo still in the pictures root is read, moved and deleted there, because `Infrastructure/Storage/PhotosMove` (a hosted service right after `DatabaseMigrator`) moves those file by file at every start (counts at Information, a file it cannot move is a Warning, and so is a folder it cannot read, after which the rest moves; a part of a photo that a copy between disks cut short left at the target is removed, since the store looks there first; it never stops the app); the Seeder deletes the photos folder too when one is set (`--photos`, else `Storage:PhotosPath`). Purging a vehicle removes `vehicles/<id>` with everything below it under both roots (`ImageService.DeleteVehicleFilesAsync`). New kinds of uploads belong in a folder below their owner. Deleting a user (`UserDataRepository`) moves `LogPhoto` (and `PhotoDraft`) owner/creator along with the logs, or purges the vehicles; `UserService` then removes the purged vehicles' folders and `users/<id>`.
- Client ids and versions (the base of offline sync): `Vehicle`, `Refueling`, `Expense` and `RecurringExpense` take an optional client-chosen id in their `Create` factory (`EntityId.OrNew`; `Guid.Empty` is `id.empty`) and count their saves in `Version` (from 1; bumped by `Update`, `MarkDeleted`, `Restore`, `FillFromPhoto` when it filled something, `MarkDone`; **not** by `SetConsumption` (derived, saved by `ExecuteUpdate`), `Vehicle.SetPicture`, `FinishReading` alone or photo rows). Every bump also records what it did and who did it (`LastChange`: `EntityChange` Created/Edited/Trashed/Restored/Done/FilledFromPhoto; `ChangedById`, passed to the mutators by the services, null for a photo), and `SyncInterceptor` sets `ChangedAt` when a save carries a new version (the interceptor is built once for the pooled factory, so it knows no user); GraphQL `changedAt`/`changedBy`/`lastChange` on the four types, `changedBy` through `UserRefLoader` like `createdBy`; a moved user's `ChangedById` moves with the data. It is a plain column, not an EF concurrency token (the repositories save detached graphs with `db.Update`; `SaveLogAsync` saves twice). Adds with an id are idempotent (`Application/Sync/ClientIds`): the services look the id up (trash included) right after the access check and before any rule, answer an add of the same creator and vehicle (vehicles: owner) with what it created, and refuse anyone else's with `sync.idTaken`; for a log not in the trash the repeat also runs the steps after the save again (`FinishRepeatedAsync`: drafts still waiting via `LogPhotoService.DraftsStillWaitingAsync`, the photo fill, the consumption), because a first try can fail after saving; two identical adds at once both insert, and the repositories' `AddOnceAsync` turns the loser's key violation into `false` so it is answered the same way. `MarkDoneInput.ExpenseId` makes a visit idempotent: when `RecurringCompletion`s already link that expense to every requested schedule nothing moves (checked before `CheckDone`; links to other schedules are `sync.idTaken`); a retry after a failed first try restores the expense the failure trashed (only reachable without links, so never one a person trashed after the visit); the dialog sends it only when the visit logs an expense. Updates, trashes and restores take `int? expectedVersion` (`VersionCheck`, `sync.versionMismatch` with `expected`/`actual`, after the access check so it reveals nothing), and every save is conditional on the loaded version: `Version` is a concurrency token, entities remember the version they were loaded with (`SavedVersion`, bumped through `Bump()`), `SyncInterceptor` sets it as the original value of every Modified/Deleted `ISynced` entry, and `AppDbContext.SaveChanges` turns a lost race on one of them into `sync.versionMismatch` (other entities' `DbUpdateConcurrencyException`s stay theirs); `SavedVersion` is ignored by EF and GraphQL. The add dialogs send an id per opening (`dialogs/useClientId.ts` over `offline/uuid.ts`, `crypto.getRandomValues` because `randomUUID` needs a secure context), the same for every Save of that opening, so a retried Save never logs twice; test fakes use the browser's id like the server (`tests/frontend/support/ids.ts` `UUID` to match one).
- Offline download (the server side): `Vehicle`, `Refueling`, `Expense` and `RecurringExpense` are `ISynced` (`Domain/Sync`): `UpdatedAt` marks what a device must download again (`Version` only counts what a writer can conflict with), set on every save by `Infrastructure/Persistence/SyncInterceptor` (Added/Modified), which also writes a `Tombstone` (own id, entity type + id, vehicle id, `PurgedAt`; no foreign key) for every tracked removal, so a removal must go through the change tracker (`UserDataRepository` removes other people's schedules with `RemoveRange` for that); writes that bypass it set the column themselves (`SyncTouch`: `SaveConsumptionsAsync` (only the logs whose consumption changed), `LogPhotoRepository` add/remove (the log), `RecurringExpenseRepository` complete/update/remove (the expenses that list the schedule), `UserDataRepository.MoveAsync`). Default for older rows: `SyncMapping.Epoch` (2000-01-01). `OfflineFeedService.ChangesAsync` (`offlineChanges`): View on the logs (`LogAccessGuard`), first download by `from` (logs only; trash included for Edit, below it a trashed log is sent as `removed`, never its values), later ones by `since` - `Overlap` (2 min) whatever the date, plus `removed` (tombstones since then whose entity does not exist again; a purged or trashed vehicle never gets that far, it is `vehicle.notFound`, so a device drops a vehicle when `myVehicles` stops listing it); refuelings and expenses paged each by its own `(UpdatedAt, Id)` key in the database's order (`OfflineFeedRepository.RefuelingRows`/`ExpenseRows`, `Guid.CompareTo` translated on all four providers: `OfflineFeedTranslationTests`) inside the opaque `OfflineCursor` (`sync.cursorInvalid`, bound to the vehicle; it carries the watermark); schedules all on the first page via `RecurringExpenseService.ListAsync`; `resync` past `Sync:TombstoneRetentionDays` (`SyncOptions`), swept lazily at most hourly. `OfflineSettingsService` (`offlineSettings`/`updateOfflineSettings`, tables `OfflineSettings` (user key, no FK) and `OfflineVehicleSettings` (FK cascade to the vehicle), replaced as a whole, every vehicle in the View scope, deleted with the user) stores `OfflineWindow` rules (`settings.offlineWindowInvalid`); `Vehicle.logCountSince(from)` through `LogCountSinceLoader`. Log rows' `canEdit`/`canDelete` follow the vehicle's `logAccess` only, so a device can work them out from the vehicle.
- Reusable building blocks (use them for new entities, do not add raw numbers): `OdometerReading` (all readings of a vehicle in one table, no maximum, unit per vehicle; neighbour validation across sources), `Cost` (amount + currency), `MeasurementUnits` (per-vehicle distance/volume units, locked once logs exist, never converted). Entities own their reading/cost; trash/restore/purge cascade in code.

### Backups

- Backups (`Domain/Backups`, `Application/Backups`, `Infrastructure/Backups`, `Api/Backups`; `docs/backup-and-restore.md`): one file per run, written by `BackupWriter` (`IBackupWriter`, the port in Application; `BackupRequest`/`BackupResult`): an outer **stored** zip holding `data.age` (encrypted) or `data.zip` (plain) and, **after it**, `manifest.json` in plain (`BackupManifest`, camelCase JSON, found by name, never by position: the sizes, row counts and the SHA-256 of the inner archive are only known once that is written; nothing personal in it, pinned by a canary test). The inner zip holds `tables/<Table>.jsonl` (`TableDump`: every table of the EF model by `GetTableName()`, an owned type with its owner, plus `__EFMigrationsHistory`; one row per line, column names as in the database, each value read with the type mapping's `GetDataReaderMethod()` (a `DateOnly` column through `GetValue` first: Oracle's MySQL connector returns a `date` as a `DateTime` and throws on `GetFieldValue<DateOnly>`, which also keeps the app itself from reading logs there) and written typed, whatever the process's culture (the custom date patterns with `CultureInfo.InvariantCulture`: th-TH would write the year 2569, fi-FI `12.34.56`): GUIDs and ISO 8601 UTC date-times as strings, numbers, booleans, null, base64 for bytes; ordered by the key; an unknown value type fails the backup rather than guessing), from **one consistent read** that ends before the files are copied (`BackupSource`, scoped to the table loop: `Serializable` locks would otherwise hold the app's writes up through the whole copy, and an idle snapshot would meet a server's idle-in-transaction timeout; SQLite = `BackupDatabase` from the live file, opened `ReadWrite` so a missing one is never created, to a copy in a temporary folder of its own (`Directory.CreateTempSubdirectory`, never the backups folder), dumped from the copy; PostgreSQL/MySQL `RepeatableRead`; SQL Server `Snapshot` where `sys.databases.snapshot_isolation_state` is ON, else `Serializable` with an Information line: asked first, because a database that does not allow snapshots only says so at the first statement inside the transaction, not at `BEGIN`; a rollback the clean-up cannot do, on a broken connection, is a Warning, never the backup's failure), `files/pictures/...` (everything under `Storage:Path`, `BackupFiles.Walk`: never a `vehicles/<id>/drafts` folder; a folder the app cannot list, a disk's lost+found, is left out with a Warning; a database that lists `Images` while neither root exists is a Warning), `files/photos/...` (a photos root of its own, only with `Backups:Photos` or `--photos`; on one root the photos are in `files/pictures` anyway, `BackupPhotos.WithPictures`) and `keys/*.xml` (`KeyRingOptions`, now in Application, bound by `AddApplication`; **encrypted backups only**: the key files hold their key in plain; the manifest's `keys` is true only when key files went in). Streamed end to end (`HashingStream` counts and hashes the inner archive), written as `<name>.partial`, created new (`FileMode.CreateNew`: two runs never share one, and a run deletes only its own), flushed to disk and renamed; a dated name (invariant culture), with `-2`, `-3` when the second already has one; an existing `--output` is refused before any work. A database whose last applied migration this release does not know (a newer release migrated it) is refused, `backup.databaseNewer`: the model would leave its new tables and columns out. **Encryption is the age format exactly** (`AgeFormat` in Domain: the header, stanzas, MAC input, STREAM chunk nonces, strict unpadded base64; `AgeKeys`/`Bech32`: `age1...` recipients and `AGE-SECRET-KEY-1...` identities; `AgeStream` in Infrastructure: `Encrypt`/`Decrypt` streams, 64 KiB ChaCha20-Poly1305 chunks, `AgeX25519` wraps the file key on BouncyCastle's X25519, the version MailKit already brings), so `age -d -i` opens `data.age`; age's own passphrase mode (an scrypt stanza) is refused (`backup.passphraseEncrypted`), a wrong identity is `backup.wrongKey`, any damage `backup.corrupt`; fixtures written by age 1.3.2 in `tests/backend/contracts/age/`, and `AgeStreamTests` runs the real tool on the writer's file when it is there (else says it skipped). The identity is Argon2id of a passphrase and a 16-byte salt (`BackupKeys`, `Argon2idParameters.Default` 64 MiB/3/1, pinned with a vector; the manifest carries recipient, salt and parameters, so a passphrase is enough to open an older file); the server keeps only `Backups:Encryption:Recipient` + `Salt` (`BackupOptions`, both or neither; `Backups:Path` default `backups`, Docker `/data/backups`, must not be a storage root, inside one or hold one: `BackupOptionsValidator`), never an identity, and no passphrase, identity or path of a user is ever logged (the Information line names the file, counts and "encrypted"/"in plain"). ### Authentication, access and deletion

- **Authentication** (`Auth:Mode`: None, Standalone, Oidc, ProxyHeader; default None) is selected lazily at runtime, so all schemes are registered and `ModeAwareSchemeProvider` hides OIDC unless it is the mode; the default scheme follows the mode too (`AuthExtensions`: the proxy's in ProxyHeader, the cookie in Standalone and OIDC, none in mode None, so a cookie left over from another mode never names a user in mode None, and nothing may authenticate or challenge without naming its scheme). Sign-in only produces a cookie/proxy identity that names a user; `HttpCurrentUser` always reloads the user (admin flag, disabled, session version) from the database. Users live in the `Users` table for every mode. - **Access layer:** every user-owned entity implements `IOwned`. Use cases never compare owners themselves; they call `AccessService` (`ScopeAsync` for lists, `LevelAsync`/`CanAsync` for single items), and repositories filter lists with `InScope(scope)`. Levels are `None<View<Edit<Delete>`: Edit creates/changes/trashes/restores, only Delete (implicit for owner/admin, or granted) purges. Rules live in the pure `AccessPolicy` (admin/owner full; others get the larger of the instance default and any grant). Per-vehicle log sharing uses generic `ResourceGrant`s resolved by `OwnerScope` (owners + granted resource ids) and `InScope(scope, resourceIdSelector)`; granting never gives more than the granter holds. Invisible items look non-existent (null / `NOT_FOUND`), not `FORBIDDEN`. With `Auth:Mode=None` the actor is `Principal.Anonymous` (full access) and admin features are unavailable. The full, paged vehicle list (`vehicles`/`vehicleCount`, `/admin/vehicles`; the old `/vehicles` redirects) is such an admin feature; everyone else uses `myVehicles`/`myVehicleCount` (owned + shared, by name, `search` on name/license plate done in the database, `skip`/`take`), which the home page pages with infinite scroll (`fetchMore` + an `IntersectionObserver` sentinel + a Show more button).
- **Soft delete:** deletable entities implement `ISoftDeletable` (`DeletedAt`). Vehicles have an EF global query filter hiding trashed rows, so normal queries are safe by default; trash/restore/purge code must use `IgnoreQueryFilters()` (see `VehicleRepository`). Trashing and restoring need Edit access, emptying the trash needs Delete access and only purges what the user may delete (the UI gets `...DeletableCount`); `PurgeAsync` returns the picture ids so the files are removed too. `DeletedAt` is stored as a UTC date-time so comparisons translate on every provider. There is deliberately no scheduled purge job yet (user decision), only the user-initiated "empty trash".

### Offline sync (frontend)

The server side is under Photos, uploads and shared building blocks (client ids and versions, the offline download) and Notifications (`SyncNotificationSync`); the contracts are in `docs/development.md`, what a user sees in `docs/install-as-an-app.md`.

- **Connectivity** (`src/frontend/offline/`): `connectivity` is a store of the server's reachability (`unknown` counts as reachable), fed by request outcomes, not `navigator.onLine` (a LAN server is out of reach from an online phone): `createOfflineLink` (first link after the error link in `apolloClient.ts`) and `trackedFetch` (the REST calls, `auth/refresh.ts`) mark it unreachable on no answer, a `ServerParseError` or a gateway 502/503/504 (`classifyFailure`), reachable on any answer, and while unreachable send nothing and fail at once with `OfflineError` (`errors.offline`, an info alert with `role="status"`; `reportOperationError` does not log it). `startOfflineRuntime` (main.tsx) probes with `Health` under `context: { offline: 'bypass' }` (`watchConnectivity`: `PROBE_DELAYS` 2/5/15/30/60 s, at once on `online` and when the tab is shown; `offline` marks it unreachable) and refetches the active queries when the server is back. UI: `shell/ConnectivityIndicator.tsx` (top bar chip + one live region announcing changes; the top bar must never be wider than the screen, or the whole page scrolls sideways: below `MEDIA.narrow` its chips go `compact` (Offline as an icon with the word visually hidden, the pending chip as its number with the sentence as its `aria-label`), the admin badge hides, the colour mode and language menus move into the drawer (`DrawerSettings`) while there is one, the title is the only thing that shrinks, and the header clips as a last resort), `HealthFooter` (Try again = `probeServer`), `ServerGrid`/`NotificationBell`/`useDraftReadings` poll only while reachable.
- **The generation** (`Session.instance.generation`, see Backups): `offlineLink.ts` `generationOf` hands every `Session` answer to `deviceData.generationSeen` after `signedIn` and before that answer is kept (the wipe empties the snapshots, the `Session:` key included): the first generation is kept under `GENERATION_KEY` (`meta:generation`, spared from pruning) without a wipe; another one means a restore: the `onGenerationChange` listeners run `'before'` (`runtime.ts`: `foundRows.setAside` into the `found` store, IndexedDB v6, additive, which `store.clear()` spares like the changes and photos), then the snapshots and rows go, the new generation is kept, and `'after'` downloads; `generationSeen` takes its turn (a promise chain in the tab, the Web Lock `tankstat-generation` across tabs, like the outbox's `exclusive`) and reads the kept generation inside it, so a second answer, in this tab or another, finds the new one kept and does nothing (but drops that tab's copies of the logs in memory, `RowStore.forget`, when it last saw another generation), and never wipes what the first just downloaded; a `'before'` listener that cannot set aside (nobody's data open) throws, and nothing goes; a sign-in or sign-out meanwhile drops nothing either; the link keeps the `Session` answer even when the check failed. Every download asks the server first (`ServerGeneration`, policy `never`: a tab whose requests all went through the restart gets no `Session` answer) and waits for `generationSeen` before it writes anything, and its cursors carry the generation they were written in (`PullCursor.generation`): one of another history counts as none, and a run that finds the kept generation changed at its end (another tab started afresh meanwhile) is followed by another at once; tests get an inert `ServerGeneration` (an empty generation) from `support/server.ts`. `offline/foundRows.ts`: `setAside` (what this account may make again: its own vehicles with their schedules from the kept `RecurringExpenses` answer, the logs it created, not in the trash, read from the store, never a tab's copies; `values` = `valuesOf` in the input's shape), `reconcile` after every download (`pull.ts`, a failure there costs no download; pure `compare`: a row a download covers (`covered`: the vehicle no longer listed, or downloaded in full and, for a log, dated inside its window, for a schedule with its answer kept) is judged (`checked`): the server has it at the same or a newer version and it leaves, or it lacks or holds it older and it stays with `serverVersion`; the rest waits unjudged and unlisted; `deviceData.onFoundChange` tells what lists or counts them), `send` (`keepChange` without a refetch each, one at the end: an add with the row's own id, or an update against `serverVersion`; `inSendOrder`: the vehicle, its schedules, its logs oldest first; a row with a change of its own waiting stays listed, `sync.found.leftWaiting`), `forget`; `deviceData.removeAll()` (Remove offline data) clears the found store too, sign-out just closes the account's data. ### Logging

- **Logging:** the standard `ILogger<T>` on the console, nothing else installed (no Serilog); Application uses `Microsoft.Extensions.Logging.Abstractions` (the layering rule only forbids EF Core and HotChocolate there). Style: `logger.LogX("... {Placeholder}", id)` with named placeholders, no `[LoggerMessage]`; the field is called `logger`, never `log` (a "log" here is a refueling or expense). Levels: *Information* for what an operator looks for (sign-ins and sign-outs, password changes, administration, access changes, sharing, imports, emptied trashes, migrations, reachability coming back), *Debug* for ordinary changes (with entity ids), *Warning* for refusals, failed sign-ins and failures that used to be swallowed (a `catch` that swallows something an operator would want to know about logs its exception; a provider that is not healthy says why by throwing, see `IRecognitionProvider.IsHealthyAsync`), *Error* only for unexpected exceptions (plus the one deliberate Error without an exception: the settings file left out at start, `SettingsFileReporter`), which `Api/GraphQL/GraphQLLoggingListener` logs once (HotChocolate has no logging of its own; it dedupes by exception instance; a non-null field that was null (`ErrorCodes.Execution.NonNullViolation` at a field path; without a path the same code is a required variable the client left out) is a server bug no hook tells about, so `RequestScope.Dispose` finds it in the result and logs a Warning naming the field the way the schema does (`SchemaField` walks the operation's selections by the path's response names); a request the engine turns down, such as a missing variable, is the client's doing and only Debug; `MediaEndpoints.TranslateErrors` logs the keyed errors of the REST side, an unexpected REST exception is logged by the framework as it always was). Ids only in the app's own lines: never e-mails, names, plates, notes, amounts, passwords, reset tokens or links, API keys, OIDC subjects or read values (two deliberate exceptions: the opt-in `Recognition:OpenAiCompatible:LogTraffic`, see Photo reading in the app, and the one-time restore code that `RestoreStep` logs at every start in mode None, where no administrator can guard a restore asked for from the app, see Backups; a backup's passphrase or identity never), and nothing a client sent (variables, documents, request-error text; an operation name only when it is a valid GraphQL name, a grid id only after it passed `GridSettings.CheckGridId`; a field by its schema name `Type.field`, not by the alias a client gave it; REST lines name the route pattern, not the path: a line break in client text would forge a log line). The edge, which `docs/configuration.md` states: the text of an unexpected exception and the framework's own lines are written as they come (a database can quote values in its error), and `Microsoft.AspNetCore` must stay at Warning or above (its request lines hold reset-link tokens). A lasting condition is logged when it changes, not on every check (`RecognitionAvailability`, `EfDatabaseProbe`); `SmtpEmailSender` throws an `EmailSendException` that keeps only the status of a refused command (a mail server's answer quotes the recipient). The shipped `appsettings.json` silences EF Core's SQL and the HttpClient's per-request lines, keeps `Tankstat` at Information (Debug in Development); smoke tests start the app in Production and expect "database migrations" and "up to date" in its output and nothing with "Photo reading" by default, so those texts are a contract. Console options such as `IncludeScopes` or `TimestampFormat` only apply when `Logging:Console:FormatterName` is set (`simple` or `json`); a scope must be a message with a placeholder (`BeginScope("UserId: {UserId}", id)`), since the console prints a dictionary as its type name (the smoke test reads the real output). Tests: `TestSupport/CapturedLog` (`World.Log` in the Application tests, `TestApp.Log` in the API tests, `TestDatabase.Log`) and canary tests that run a broad flow and assert that no typed value or secret reaches a line (`LoggingTests` in Application and in the API integration tests; `log.Mentions(needle)` does not count a find strictly inside a token shaped like a random id (a GUID, 16 or 32 hex characters, a `0H…` request id), typed or not, since such an id can spell a short needle such as `24687` by chance: search a canary's whole value, or one made of letters no id holds (`zzzz`), never a piece of a value that could be logged in such a shape: `CapturedLogTests`); find a line by its class (`log.From<T>()`) and level and read the values of its placeholders (`entry.Values["UserId"]`), do not assert the wording of a message. Frontend: `apolloClient.ts` (`reportOperationError`, an Apollo `ErrorLink`) and `ErrorBoundary` write unexpected request failures and crashed pages to the browser console and send nothing; an error with a `key` is expected (the screen shows it) and not reported.

- **Settings (`Domain/Settings`, `Application/Settings`):** what the UI remembers for a user follows them to every device. The Domain checks shape and limits only (grid id `^[a-z][a-z0-9-]*$` and column ids `^[A-Za-z0-9_-]+$`, both at most 40, ≤ 50 per list, page size 1..500, language `^[a-z]{2}(-[A-Z]{2})?$`); what an id means is the frontend's business (`useGridSettings.merge`). `UiSettingsService` (get; the grids listed separately, `UiSettingsInfo.grids` is a resolver so they load only when selected; partial update where `ClearLanguage` wins over `Language` and an empty change saves nothing; save/reset a grid; the repository upserts and turns a lost insert race into an update, so per row the later save wins whole) and `VehicleOrderService.SetAsync` (replaces the whole arrangement; dedupes; ≤ `VehicleQuery.MaxTake`; every id must be a vehicle in the user's View scope, else `vehicle.notFound`) go through `AccessService.RequirePrincipalAsync`. `VehicleQuery.OrderedFor` (set only by `VehicleService.ListMineAsync`) makes `VehicleRepository.Page` order by `COALESCE(position, max)`, name, id; the admin list and the counts are unchanged. GraphQL: `uiSettings`, `updateUiSettings` (null = unchanged, `clearLanguage`), `saveGridSettings`, `resetGridSettings`, `setVehicleOrder`; DTOs `UiSettingsInfo`/`GridSettingsInfo` in `Api/GraphQL/UiSettingsGraphQL.cs`. Frontend: `settings/UiSettingsProvider.tsx` (mounted by `App` with `key` = user, `enabled` = signed in or mode None; asks `UiSettings` once; localStorage stays the device's write-through copy; the server's answer is adopted unless the user changed that setting this session (`touched` refs); an absent server value keeps the local copy; an unknown language is ignored; every save is fire-and-forget and serial per setting (`useSerialSaves`: one request in flight, the newest value follows); a refused save is a `console.warn`, a failed request is logged by the Apollo error link) with `settings/uiSettingsContext.ts` (`useUiSettings()`, null without a provider: a grid alone remembers in the browser); `useGridSettings` re-merges once per server answer (`settings.server` identity) when untouched; `LanguageMenu` and `AppearanceMenu` tell the server too (`setColorMode`, `setSurface`; MUI switches the mode and keeps the browser's copy, `surfaceStore` the surfaces, and the server's answer is adopted unless the user changed it this session). `ArrangeVehiclesDialog` (home toolbar from two vehicles on, counted by `Welcome`'s `vehicleTotal`, not the searched count; lists at most 200; up/down buttons, a `role="status"` line, `setVehicleOrder` + refetch `Welcome`; cannot be closed while saving, and the list mounts only with the opening's own answer). Tests: `tests/frontend/support/server.ts` answers `UiSettings` (empty) and echoes the three settings mutations by default, `fakeSettingsBackend` keeps values, `fakeVehicleBackend.state.order` orders `Welcome` and answers `ArrangeVehicles`/`SetVehicleOrder`.
- **Home cards** (`components/VehicleCard.tsx`): a card's data is the `VehicleCardFields` fragment (`graphql/dashboard.graphql`), asked by `Welcome` and by `VehicleCard($id)`; a schedule's status is always `RecurrenceStatusFields` (`graphql/recurring.graphql`), so no two documents hold different shapes of one status. The quick actions (Refuel, Expense, and Done per schedule that needs attention; only for `canLogFor` in `vehicles.ts`, the vehicle page's rule too) mount the vehicle page's dialogs in the card with their own triggers (closed, they ask the server nothing: `usePhotoSession(vehicleId, purpose, open)`); the mutations live in `components/useCardActions.ts` and, once the mutation settled, ask for `VehicleCard` afresh with `client.query(..., 'network-only')` (not `awaitRefetchQueries`: a failed refresh must never make a saved log look like an error, a retry would log it twice), which updates the normalised `Vehicle:<id>` in place: never `refetchQueries: ['Welcome']` from a card or from the vehicle page (it reruns the first page and drops what infinite scroll loaded). A dialog's content is portalled but React still bubbles its events through the card: `components/cardClicks.ts` makes the click handlers ignore targets outside the card's DOM, lets the card's buttons act on the first tap (touch) and keeps the tap-away listener out of dialogs and the lists that open from them (`.MuiModal-root`, `.MuiPopper-root`). Layout: the top block (`.card-top`: title, badges, attention, actions) stays put and the figures panel (`.card-panel`) slides up from the bottom edge, revealed on `:hover` under `@media (hover: hover)`, on `:has(:focus-visible)` (not `:focus-within`: a closing dialog focuses a card button without the keyboard) or on `data-open` (touch); the card's `min-height` is `max(17rem, --top-h + --panel-h)` (a ResizeObserver on both blocks) and the list items are grids, so the cards of a row stretch to the tallest and nothing moves while one reveals; `.vehicle-card-action` sits above the link overlay with 44 px minimums. Done removes the row together with the dialog's trigger, so the card has one controlled Done dialog (`{ item, open }`, opened by the schedule's own button) and its `onClosed` moves the focus to the title link when that button is gone. jsdom lays nothing out: heights and the hover/focus reveal are checked by hand. Test fakes answering `Welcome`/`VehicleCard`/the recurring documents must carry `__typename` on vehicles, schedules and statuses (`fakeVehicle`, `typedRecurring` in `tests/frontend/support/mocks.tsx`): a typed fragment never matches an untyped object; the log, expense and recurring fakes change a vehicle's `summary`/`recurring` in place, so hand them the vehicle backend's own objects (`backend.state.vehicles[0]`).
- **Notices:** the server sends public `notices` (currently the `AUTH_DISABLED` warning, `SETTINGS_FILE_IGNORED`, the settings file left out at start, which names no setting: notices are public, and `RESTORE_PENDING`, a restore waiting for the next start); the UI renders them generically in `NoticeBanner`, worded by `notices.<code>` in English and Hungarian (the server's text only as a fallback).
- HotChocolate schema introspection only works in the Development environment, which is why `scripts/test-api.sh` sets it.

## Testing requirements

Every change must keep all three layers covering behavior, so breaking changes are caught:
- **Unit:** `tests/backend/Tankstat.Application.UnitTests` (pure logic, fakes for ports), `tests/backend/Tankstat.Infrastructure.UnitTests` (config binding, EF adapters on in-memory SQLite), `tests/frontend/*.unit.test.*`.
- **Integration:** `tests/backend/Tankstat.Api.IntegrationTests` (`WebApplicationFactory<Program>`, real DI/GraphQL/EF) and `tests/frontend/*.integration.test.*` (Apollo against msw-mocked GraphQL over HTTP).
- **API:** `tests/backend/Tankstat.Api.ApiTests` are black-box GraphQL contract tests against a running server (`TANKSTAT_API_URL`); `scripts/test-api.sh` starts one on a throwaway port with an in-memory database. A schema change the frontend depends on must fail here.

Frontend test files must be named `*.unit.test.ts(x)` or `*.integration.test.ts(x)` to be picked up by `vitest.config.ts`. They live in a folder per feature area, nested where an area has parts (`app/` with `apollo/` and `i18n/`, `auth/`, `pwa/`, `offline/` (connectivity and device data), `home/`, `vehicles/` with `logs/`, `recurring/` and `dashboard/`, `recognition/`, `pictures/`, `trash/`, `grid/`, `settings/`, `notifications/`, `admin/`, `import/`, `ui/` for the theme, forms, dialogs, toast and other shared building blocks); unit and integration tests of an area sit side by side, and the shared helpers (`mocks.tsx`, `server.ts`, `setup.ts`, `dates.ts` for the date pickers' fields) are in `tests/frontend/support/`. `stubViewport(kind, { scheme })` answers real media queries (widths, hover, pointer, `prefers-color-scheme`), and `renderWithApollo` uses the instant theme (no transitions), so a closed dialog is gone at once. A new test goes into the folder of the feature it covers.

## Scope

Besides health, auth and administration, the app covers vehicles and their refuelling logs (create/edit/trash/restore/purge, sharing a vehicle's logs, pictures) and recurring expenses (schedules by time, distance or both, shown on the home page), per-user notifications (access changes, due schedules), and per-vehicle statistics (the dashboard's key figures, the preset and saved charts, consumption between full fill-ups); there are no cross-vehicle reports. The OIDC token-validated provisioning path is covered by unit tests only, not against a real provider. Data created with auth off is owned by the anonymous user (id all zeros) and is only visible to administrators after switching modes. Photos picked in the add dialogs can be read by a vision model behind any OpenAI-compatible API (a server the operator runs, or a paid one at their choice) to fill in the form, or the saved log later (marked for review); it is off by default and nothing changes without it. Do not invent domain features or add infrastructure (CI, Docker, codegen) that was not asked for.
