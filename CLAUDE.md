# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Tankstat is a self-hosted web app: React + TypeScript frontend (Vite) and a .NET 10 backend. Kestrel serves both the API and the built SPA in production.

The README is short on purpose (what it is, the features by name, a quick start, the development commands, links). The user and operator documentation is in `docs/`, one file per topic: `configuration.md` (database, files, defaults, notifications, the app's own settings file, logging), `authentication.md` (modes, settings, access control), `user-guide.md`, `importing.md`, `install-as-an-app.md`, `photo-reading.md`, `backup-and-restore.md`, `self-hosting.md` and `development.md`. When a change alters behaviour or a setting that a docs file describes, update that file (and the README only when a feature's one-line summary changes). `docs/photo-reading.md` prints the built-in system prompt, both contracts and the JSON schema, pinned to the code by `OpenAiCompatiblePromptTests`.

Pull request descriptions never carry the claude.ai session link (no `https://claude.ai/code/session_...` line); the "Generated with Claude Code" line stays. Commit trailers are unchanged.

Issue workflow (`.claude/skills/`, for the maintainer's agent sessions; a contributor's agent leaves its labels alone, `AGENTS.md`): `/triage N` claims an issue with the `triaging` label (and skips issues carrying it unless named), analyses, reproduces and plans it, posts the handoff on it, labels it `triaged` and removes `triaging`, never fixes; `/dev N` implements a `triaged` issue (refuses one that is not; one that is `in progress` it does not start unless the user asks for it specifically, then picks up the ongoing work or restarts it from scratch as the user says, asking when unsure; claims it with `in progress` first and removes the label once the development is done; consults the `advisor` before every decision) on a branch off the freshly pulled `main` in the main checkout (a working tree that is not clean asks first): targeted tests while working, the full suite before every commit and/or push, a draft PR labelled `WIP` until finished, then ready to merge without waiting for CI; `/review N` (or `next`: the oldest open non-draft PR not opened by Dependabot) reviews only a PR that carries neither `reviewing` nor `reviewed` (on one being reviewed it asks whether to take it over, on a reviewed one it reviews again only on request), claims it with `reviewing` first, runs the built-in `code-review` (its levels `low`..`max`, `--max-findings`, `--fix` and `--comment` passed on; not `ultra`) and reports the findings in the session; it posts on the PR only when asked: `--comment` for an inline comment per finding, `--summarize` for one summary comment; then it labels it `reviewed` and removes `reviewing`; only with `--fix` does it change the PR's code: on the PR's branch in the main checkout, the full suite before committing, pushed to the PR's branch without force. One agent works at a time, in the main checkout (the repository folder itself), for every task including `/triage`: no git worktree (`git worktree add`, `EnterWorktree`) unless the user asks for one, also because the LSP indexes only the main checkout (`.claude/settings.json` turns Claude Code's background-session worktree guard off for this: `worktree.bgIsolation: none`).

## Toolchain and commands

All tooling is managed by `mise` (`mise.toml`: Node LTS, .NET 10). Prefer `mise run <task>` over calling tools directly.

- `mise run install` - `npm ci` (in `src/frontend/tankstat-react`) + `dotnet restore`
- `mise run dev:api` / `mise run dev:web` - API on :5080 with hot reload; Vite dev server proxying `/graphql`, `/auth/oidc/`, `/auth/token/`, `/media` and `/imports` to it (only those two of `/auth`: `src/frontend/tankstat-react/src/auth/` modules are served at `/auth/...`, so no module may live in `src/frontend/tankstat-react/src/auth/oidc/` or `src/frontend/tankstat-react/src/auth/token/`)
- `mise run test` - typecheck, lint, then every test layer (run this before finishing a change)
- `mise run test:unit`, `test:integration`, `test:api` - single layers
- `mise run test:e2e` - the real-browser tests (Playwright, in Docker here) against a fresh `out/`; not part of `mise run test`
- `mise run build` - self-hostable output in `out/` (published API + SPA in `wwwroot`)
- `mise run screenshots` - the README's pictures in `docs/screenshots/` from a fresh `out/` with the Seeder's data (`.claude/rules/e2e.md`); by hand when a page they show changes, never in CI

Single tests:
- Frontend, from `src/frontend/tankstat-react`: `npx vitest run tests/<area>/<file>` (add `-t "<name>"` to filter)
- Backend: `dotnet test tests/backend/<Project> --filter "FullyQualifiedName~<Name>"`

Code lookups (who uses a symbol, where it is defined, a file's symbols) go through the LSP tool (csharp-ls, typescript-language-server), with grep as the fallback. Check first that it answers for a symbol you know: csharp-ls can index a stale copy of the solution, and the TypeScript server's first `findReferences` after it starts can return only the declaration (ask once more before believing "no references"). When the LSP does not work, say so to the user: when it first fails, and again now and then while it stays broken, not on every call.

## Project structure rules

### Layout and layers

- Backend source lives under `src/backend/`, its tests under `tests/backend/`. The web app is one npm package in `src/frontend/tankstat-react`, everything frontend in it: `package.json` and `package-lock.json`, `node_modules`, the configs (`vite.config.ts`, `vitest.config.ts`, `playwright.config.ts`, `codegen.ts`, `tsconfig*`, `.oxlintrc.json`), the app in `src/`, the Vitest tests in `tests/`, the Playwright tests in `e2e/` and `scripts/durations.mjs`. npm commands run from that folder (mise tasks do it for you); `schema.graphql` stays at the repository root, where the API exports it.
- Vite's `root` is `src/frontend/tankstat-react/src`; the build goes to `src/frontend/tankstat-react/dist`, which `mise run build:api` copies into `out/wwwroot`. Frontend coverage still goes to the repository's `coverage/frontend`.
- Backend follows clean architecture, dependencies pointing inward only: `Api -> Application, Infrastructure`; `Infrastructure -> Application`; `Application -> Domain`. Application and Domain must not reference EF Core or HotChocolate. Application defines ports (interfaces such as `IDatabaseProbe`); Infrastructure implements them. Each layer registers itself through an `AddApplication` / `AddInfrastructure` extension.
- Add new .NET projects to `Tankstat.slnx`.
- Reusable building blocks (use them for new entities, do not add raw numbers): `OdometerReading` (all readings of a vehicle in one table, no maximum, unit per vehicle; neighbour validation across sources), `Cost` (amount + currency), `MeasurementUnits` (per-vehicle distance/volume units, locked once logs exist, never converted). Entities own their reading/cost; trash/restore/purge cascade in code.

## Stack decisions

### API and persistence

- **API:** GraphQL (HotChocolate 16 at `/graphql`); the only REST endpoints are the picture endpoints in `Api/Media` (`PUT/DELETE /media/me/avatar`, `PUT/DELETE /media/vehicles/{id}/picture`, `PUT/DELETE /media/expenses|refuelings/{logId}/photos[/{imageId}]`, `PUT /media/vehicles/{id}/photo-drafts`, `DELETE /media/photo-drafts/{id}`, `GET /media/{id}`) and the backup files (`PUT /media/backups`, `GET`/`HEAD /media/backups/{file}`), because files do not fit GraphQL. The same goes for `POST /imports/{format}` (`Api/Media/ImportEndpoints.cs`; named `/imports` so it does not collide with the SPA route `/import`). Frontend uses Apollo Client 4 and MUI v9 (`@mui/material`, Emotion) with MUI X (`@mui/x-data-grid`, `@mui/x-charts`, `@mui/x-date-pickers`; MIT editions only: Data Grid page size at most 100, no column drag-and-drop or saved resizing), icons from `lucide-react`. Use the MUI components directly, styled through the theme (`theme/`) and `sx`; there is no stylesheet of our own. The app is wrapped in `ThemeRoot` (`main.tsx`, and `renderWithApollo` in tests). **MUI rules learned**: Popover, Menu, Dialog and Drawer are modal, so the page behind them is `aria-hidden` while they are open: tests read it with `{ hidden: true }` or close the layer first, and axe-check a popup menu on its own element, not the whole body; options of a Select/Autocomplete render in a portal, so query with `screen`, not `within`; an `Autocomplete` rendered with a bare `OutlinedInput` must pass the autocomplete's input props through `inputProps` (`slotProps.input` drops their `onChange`); every model handed to the Data Grid (`sortModel`, `paginationModel`, column visibility) must keep its identity between renders, or server mode resets to the first page; jsdom lays nothing out, so heights, hover reveals and charts are checked in a real browser, and tests read the table behind a chart. The breakpoints are the old Radix pixels under MUI's names plus `xxl` (xs 0, sm 520, md 768, lg 1024, xl 1280, xxl 1640): Radix `initial/xs/sm/md/lg/xl` = MUI `xs/sm/md/lg/xl/xxl`; spacing is MUI's 8 px unit (Radix space 1..9 = 0.5, 1, 1.5, 2, 3, 4, 5, 6, 8); JS media checks use `theme/media.ts`.
- **Persistence:** EF Core 10. Provider is chosen at runtime from the `Database` config section: `Provider` (`Sqlite`, `PostgreSql`, `SqlServer`, `MySql`) and `ConnectionString`. With nothing configured it falls back to SQLite (`Data Source=tankstat.db`, working directory); only Sqlite may omit the connection string. MySQL uses Oracle's provider (Pomelo has no EF Core 10 release); MariaDB is not a tested target.
- **Configuration precedence** is standard ASP.NET Core with one source added: `appsettings.json` < `appsettings.{Environment}.json` < the app's own settings file < environment variables (`Database__Provider`, `Database__ConnectionString`) < command line. Environment variables must always be able to override both files; keep new settings in typed, validated options classes bound the same way as `DatabaseOptions`.
- **Migrations:** one project per provider (`src/backend/Tankstat.Migrations.<Provider>`, selected through `MigrationsAssembly`), applied at startup by `DatabaseMigrator`. After changing an entity or its mapping, run `mise run db:migration <Name>` so all four stay in sync (`MigrationsTests` fails otherwise). In-memory SQLite does not work for the app/integration tests because every pooled context gets its own database; use a temp file.

### Authentication, access and deletion

- **Access layer:** every user-owned entity implements `IOwned`. Use cases never compare owners themselves; they call `AccessService` (`ScopeAsync` for lists, `LevelAsync`/`CanAsync` for single items), and repositories filter lists with `InScope(scope)`. Levels are `None<View<Edit<Delete>`: Edit creates/changes/trashes/restores, only Delete (implicit for owner/admin, or granted) purges. Rules live in the pure `AccessPolicy` (admin/owner full; others get the larger of the instance default and any grant). Per-vehicle log sharing uses generic `ResourceGrant`s resolved by `OwnerScope` (owners + granted resource ids) and `InScope(scope, resourceIdSelector)`; granting never gives more than the granter holds. Invisible items look non-existent (null / `NOT_FOUND`), not `FORBIDDEN`. With `Auth:Mode=None` the actor is `Principal.Anonymous` (full access) and admin features are unavailable. The full, paged vehicle list (`vehicles`/`vehicleCount`, `/admin/vehicles`; the old `/vehicles` redirects) is such an admin feature; everyone else uses `myVehicles`/`myVehicleCount` (owned + shared, by name, `search` on name/license plate done in the database, `skip`/`take`), which the home page pages with infinite scroll (`fetchMore` + an `IntersectionObserver` sentinel + a Show more button).
- **Soft delete:** deletable entities implement `ISoftDeletable` (`DeletedAt`). Vehicles have an EF global query filter hiding trashed rows, so normal queries are safe by default; trash/restore/purge code must use `IgnoreQueryFilters()` (see `VehicleRepository`). Trashing and restoring need Edit access, emptying the trash needs Delete access and only purges what the user may delete (the UI gets `...DeletableCount`); `PurgeAsync` returns the picture ids so the files are removed too. `DeletedAt` is stored as a UTC date-time so comparisons translate on every provider. There is deliberately no scheduled purge job yet (user decision), only the user-initiated "empty trash".

### Frontend

- **GraphQL codegen (graphql 17):** no hand-written GraphQL types. `schema.graphql` (exported from the API) + `src/frontend/tankstat-react/src/graphql/*.graphql` generate `src/frontend/tankstat-react/src/gql/generated.ts` (typed documents, enums as string unions). After changing the schema or a document run `mise run codegen` and commit both generated files; `SchemaSnapshotTests` and `mise run codegen:check` fail otherwise. Optional grid columns use `@include(if: $withX)` variables so hidden columns are never fetched; because of that a row may lack fields, so anything that edits an entity must load it (see `VehicleDetails`), never trust grid rows.
- **i18n:** every user-visible string goes through `t('...')` with typed keys from `en.json`; add the Hungarian text too (a unit test enforces equal keys/placeholders). Domain/Application errors derive from `KeyedException` (stable `key` + camelCase `args`) and `BusinessErrorFilter` puts them in the GraphQL error extensions; the frontend translates `errors.<key>` (`useErrorText`) and falls back to the server message. New user-facing errors need a key, an English entry and a Hungarian entry. Format dates/numbers with `Intl` (`useFormat`), never by hand. The browser's language is cleaned to a valid tag when it is detected (`i18n/locale.ts` `validLocale` as the detector's `convertDetectedLanguage`: a POSIX locale such as `en-US@posix` makes `Intl` throw), and whatever hands the language to `Intl` or `<html lang>` passes it through `validLocale(i18n.language, i18n.resolvedLanguage)` too.
- **Accessibility is a requirement for all UI:** landmarks, skip link, labelled controls (`Field`), table semantics, live regions for async status, 44 px touch targets (links too, unless inline in a sentence: `standaloneLink`), no information by colour alone, reduced motion. `src/frontend/tankstat-react/tests/app/Accessibility*.integration.test.tsx` run axe (vitest-axe) on the pages and dialogs (`Accessibility`: pages, shell, sign-in; `AccessibilityLogs`: log dialogs and photos; `AccessibilityRecurring`: schedules and home cards; split so they run side by side, with `support/accessibility.tsx` for `setup`, `check` and `setupAccessibilityTests`, which also gives these files 30 s per test: a few scans of a whole page take that on CI); add new screens to the file of their area, and keep a test to a few scans.

### Notices and the schema

- **Notices:** the server sends public `notices` (currently the `AUTH_DISABLED` warning, `SETTINGS_FILE_IGNORED`, the settings file left out at start, which names no setting: notices are public, `RESTORE_PENDING`, a restore waiting for the next start, and `SETUP_PENDING`, a new instance waiting for its setup, always last); the UI renders them generically in `NoticeBanner`, worded by `notices.<code>` in English and Hungarian (the server's text only as a fallback).
- HotChocolate schema introspection only works in the Development environment, which is why `scripts/test-api.sh` sets it.

## Testing requirements

Every change must keep all three layers covering behavior, so breaking changes are caught:
- **Unit:** `tests/backend/Tankstat.Application.UnitTests` (pure logic, fakes for ports), `tests/backend/Tankstat.Infrastructure.UnitTests` (config binding, EF adapters on in-memory SQLite), `src/frontend/tankstat-react/tests/*.unit.test.*`.
- **Integration:** `tests/backend/Tankstat.Api.IntegrationTests` (`WebApplicationFactory<Program>`, real DI/GraphQL/EF) and `src/frontend/tankstat-react/tests/*.integration.test.*` (Apollo against msw-mocked GraphQL over HTTP).
- **API:** `tests/backend/Tankstat.Api.ApiTests` are black-box GraphQL contract tests against a running server (`TANKSTAT_API_URL`); `scripts/test-api.sh` starts one on a throwaway port with an in-memory database. A schema change the frontend depends on must fail here.

A fourth layer runs outside `mise run test`: **real browser** (`src/frontend/tankstat-react/e2e/*.e2e.ts`, Playwright against the published build at phone and desktop size; `mise run test:e2e`, CI's `e2e` job; `.claude/rules/e2e.md`). It checks what jsdom cannot: layout (sideways scroll, values past their panel, 44 px touch targets), axe with the real styles (colour contrast), and a few flows across the real server. A page whose layout changes gets its test there, and **every new user flow** (something a person does across pages or dialogs: a new feature, or a new way through an existing one) **gets a Playwright test** in `src/frontend/tankstat-react/e2e` with the change that adds it, at both sizes; a change of an existing flow updates its test.

Frontend test files must be named `*.unit.test.ts(x)` or `*.integration.test.ts(x)` to be picked up by `vitest.config.ts`. They live in a folder per feature area, nested where an area has parts (`app/` with `apollo/` and `i18n/`, `auth/`, `pwa/`, `offline/` (connectivity and device data), `home/`, `vehicles/` with `logs/`, `recurring/` and `dashboard/`, `recognition/`, `pictures/`, `trash/`, `grid/`, `settings/`, `notifications/`, `admin/`, `import/`, `ui/` for the theme, forms, dialogs, toast and other shared building blocks); unit and integration tests of an area sit side by side, and the shared helpers (`mocks.tsx`, `server.ts`, `setup.ts`, `dates.ts` for the date pickers' fields) are in `src/frontend/tankstat-react/tests/support/`. `stubViewport(kind, { scheme })` answers real media queries (widths, hover, pointer, `prefers-color-scheme`), and `renderWithApollo` uses the instant theme (no transitions), so a closed dialog is gone at once. A new test goes into the folder of the feature it covers.

## Scope

Besides health, auth and administration, the app covers vehicles and their refuelling logs (create/edit/trash/restore/purge, sharing a vehicle's logs, pictures) and recurring expenses (schedules by time, distance or both, shown on the home page), per-user notifications (access changes, due schedules), and per-vehicle statistics (the dashboard's key figures, the preset and saved charts, consumption between full fill-ups); there are no cross-vehicle reports. The OIDC token-validated provisioning path is covered by unit tests only, not against a real provider. Data created with auth off is owned by the anonymous user (id all zeros) and is only visible to administrators after switching modes. Photos picked in the add dialogs can be read by a vision model behind any OpenAI-compatible API (a server the operator runs, or a paid one at their choice) to fill in the form, or the saved log later (marked for review); it is off by default and nothing changes without it. Do not invent domain features or add infrastructure (CI, Docker, codegen) that was not asked for.
