# Offline sync (client ids, versions, the offline download, the device side and sending)

- Client ids and versions (the base of offline sync): `Vehicle`, `Refueling`, `Expense` and `RecurringExpense` take an optional client-chosen id in their `Create` factory (`EntityId.OrNew`; `Guid.Empty` is `id.empty`) and count their saves in `Version` (from 1; bumped by `Update`, `MarkDeleted`, `Restore`, `FillFromPhoto` when it filled something, `MarkDone`; **not** by `SetConsumption` (derived, saved by `ExecuteUpdate`), `Vehicle.SetPicture`, `FinishReading` alone or photo rows). Every bump also records what it did and who did it (`LastChange`: `EntityChange` Created/Edited/Trashed/Restored/Done/FilledFromPhoto; `ChangedById`, passed to the mutators by the services, null for a photo), and `SyncInterceptor` sets `ChangedAt` when a save carries a new version (the interceptor is built once for the pooled factory, so it knows no user); GraphQL `changedAt`/`changedBy`/`lastChange` on the four types, `changedBy` through `UserRefLoader` like `createdBy`; a moved user's `ChangedById` moves with the data. It is a plain column, not an EF concurrency token (the repositories save detached graphs with `db.Update`; `SaveLogAsync` saves twice). Adds with an id are idempotent (`Application/Sync/ClientIds`): the services look the id up (trash included) right after the access check and before any rule, answer an add of the same creator and vehicle (vehicles: owner) with what it created, and refuse anyone else's with `sync.idTaken`; for a log not in the trash the repeat also runs the steps after the save again (`FinishRepeatedAsync`: drafts still waiting via `LogPhotoService.DraftsStillWaitingAsync`, the photo fill, the consumption), because a first try can fail after saving; two identical adds at once both insert, and the repositories' `AddOnceAsync` turns the loser's key violation into `false` so it is answered the same way. `MarkDoneInput.ExpenseId` makes a visit idempotent: when `RecurringCompletion`s already link that expense to every requested schedule nothing moves (checked before `CheckDone`; links to other schedules are `sync.idTaken`); a retry after a failed first try restores the expense the failure trashed (only reachable without links, so never one a person trashed after the visit); the dialog sends it only when the visit logs an expense. Updates, trashes and restores take `int? expectedVersion` (`VersionCheck`, `sync.versionMismatch` with `expected`/`actual`, after the access check so it reveals nothing), and every save is conditional on the loaded version: `Version` is a concurrency token, entities remember the version they were loaded with (`SavedVersion`, bumped through `Bump()`), `SyncInterceptor` sets it as the original value of every Modified/Deleted `ISynced` entry, and `AppDbContext.SaveChanges` turns a lost race on one of them into `sync.versionMismatch` (other entities' `DbUpdateConcurrencyException`s stay theirs); `SavedVersion` is ignored by EF and GraphQL. The add dialogs send an id per opening (`dialogs/useClientId.ts` over `offline/uuid.ts`, `crypto.getRandomValues` because `randomUUID` needs a secure context), the same for every Save of that opening, so a retried Save never logs twice; test fakes use the browser's id like the server (`tests/frontend/support/ids.ts` `UUID` to match one).
- Offline download (the server side): `Vehicle`, `Refueling`, `Expense` and `RecurringExpense` are `ISynced` (`Domain/Sync`): `UpdatedAt` marks what a device must download again (`Version` only counts what a writer can conflict with), set on every save by `Infrastructure/Persistence/SyncInterceptor` (Added/Modified), which also writes a `Tombstone` (own id, entity type + id, vehicle id, `PurgedAt`; no foreign key) for every tracked removal, so a removal must go through the change tracker (`UserDataRepository` removes other people's schedules with `RemoveRange` for that); writes that bypass it set the column themselves (`SyncTouch`: `SaveConsumptionsAsync` (only the logs whose consumption changed), `LogPhotoRepository` add/remove (the log), `RecurringExpenseRepository` complete/update/remove (the expenses that list the schedule), `UserDataRepository.MoveAsync`). Default for older rows: `SyncMapping.Epoch` (2000-01-01). `OfflineFeedService.ChangesAsync` (`offlineChanges`): View on the logs (`LogAccessGuard`), first download by `from` (logs only; trash included for Edit, below it a trashed log is sent as `removed`, never its values), later ones by `since` - `Overlap` (2 min) whatever the date, plus `removed` (tombstones since then whose entity does not exist again; a purged or trashed vehicle never gets that far, it is `vehicle.notFound`, so a device drops a vehicle when `myVehicles` stops listing it); refuelings and expenses paged each by its own `(UpdatedAt, Id)` key in the database's order (`OfflineFeedRepository.RefuelingRows`/`ExpenseRows`, `Guid.CompareTo` translated on all four providers: `OfflineFeedTranslationTests`) inside the opaque `OfflineCursor` (`sync.cursorInvalid`, bound to the vehicle; it carries the watermark); schedules all on the first page via `RecurringExpenseService.ListAsync`; `resync` past `Sync:TombstoneRetentionDays` (`SyncOptions`), swept lazily at most hourly. `OfflineSettingsService` (`offlineSettings`/`updateOfflineSettings`, tables `OfflineSettings` (user key, no FK) and `OfflineVehicleSettings` (FK cascade to the vehicle), replaced as a whole, every vehicle in the View scope, deleted with the user) stores `OfflineWindow` rules (`settings.offlineWindowInvalid`); `Vehicle.logCountSince(from)` through `LogCountSinceLoader`. Log rows' `canEdit`/`canDelete` follow the vehicle's `logAccess` only, so a device can work them out from the vehicle.

## Offline sync (frontend)

The server side is under Photos, uploads and shared building blocks (client ids and versions, the offline download) and Notifications (`SyncNotificationSync`); the contracts are in `docs/development.md`, what a user sees in `docs/install-as-an-app.md`.

- **Connectivity** (`src/frontend/offline/`): `connectivity` is a store of the server's reachability (`unknown` counts as reachable), fed by request outcomes, not `navigator.onLine` (a LAN server is out of reach from an online phone): `createOfflineLink` (first link after the error link in `apolloClient.ts`) and `trackedFetch` (the REST calls, `auth/refresh.ts`) mark it unreachable on no answer, a `ServerParseError` or a gateway 502/503/504 (`classifyFailure`), reachable on any answer, and while unreachable send nothing and fail at once with `OfflineError` (`errors.offline`, an info alert with `role="status"`; `reportOperationError` does not log it). `startOfflineRuntime` (main.tsx) probes with `Health` under `context: { offline: 'bypass' }` (`watchConnectivity`: `PROBE_DELAYS` 2/5/15/30/60 s, at once on `online` and when the tab is shown; `offline` marks it unreachable) and refetches the active queries when the server is back. UI: `shell/ConnectivityIndicator.tsx` (top bar chip + one live region announcing changes; the top bar must never be wider than the screen, or the whole page scrolls sideways: below `MEDIA.narrow` its chips go `compact` (Offline as an icon with the word visually hidden, the pending chip as its number with the sentence as its `aria-label`), the admin badge hides, the colour mode and language menus move into the drawer (`DrawerSettings`) while there is one, the title is the only thing that shrinks, and the header clips as a last resort), `HealthFooter` (Try again = `probeServer`), `ServerGrid`/`NotificationBell`/`useDraftReadings` poll only while reachable.
- **The generation** (`Session.instance.generation`, see Backups): `offlineLink.ts` `generationOf` hands every `Session` answer to `deviceData.generationSeen` after `signedIn` and before that answer is kept (the wipe empties the snapshots, the `Session:` key included): the first generation is kept under `GENERATION_KEY` (`meta:generation`, spared from pruning) without a wipe; another one means a restore: the `onGenerationChange` listeners run `'before'` (`runtime.ts`: `foundRows.setAside` into the `found` store, IndexedDB v6, additive, which `store.clear()` spares like the changes and photos), then the snapshots and rows go, the new generation is kept, and `'after'` downloads; `generationSeen` takes its turn (a promise chain in the tab, the Web Lock `tankstat-generation` across tabs, like the outbox's `exclusive`) and reads the kept generation inside it, so a second answer, in this tab or another, finds the new one kept and does nothing (but drops that tab's copies of the logs in memory, `RowStore.forget`, when it last saw another generation), and never wipes what the first just downloaded; a `'before'` listener that cannot set aside (nobody's data open) throws, and nothing goes; a sign-in or sign-out meanwhile drops nothing either; the link keeps the `Session` answer even when the check failed. Every download asks the server first (`ServerGeneration`, policy `never`: a tab whose requests all went through the restart gets no `Session` answer) and waits for `generationSeen` before it writes anything, and its cursors carry the generation they were written in (`PullCursor.generation`): one of another history counts as none, and a run that finds the kept generation changed at its end (another tab started afresh meanwhile) is followed by another at once; tests get an inert `ServerGeneration` (an empty generation) from `support/server.ts`. `offline/foundRows.ts`: `setAside` (what this account may make again: its own vehicles with their schedules from the kept `RecurringExpenses` answer, the logs it created, not in the trash, read from the store, never a tab's copies; `values` = `valuesOf` in the input's shape), `reconcile` after every download (`pull.ts`, a failure there costs no download; pure `compare`: a row a download covers (`covered`: the vehicle no longer listed, or downloaded in full and, for a log, dated inside its window, for a schedule with its answer kept) is judged (`checked`): the server has it at the same or a newer version and it leaves, or it lacks or holds it older and it stays with `serverVersion`; the rest waits unjudged and unlisted; `deviceData.onFoundChange` tells what lists or counts them), `send` (`keepChange` without a refetch each, one at the end: an add with the row's own id, or an update against `serverVersion`; `inSendOrder`: the vehicle, its schedules, its logs oldest first; a row with a change of its own waiting stays listed, `sync.found.leftWaiting`), `forget`; `deviceData.removeAll()` (Remove offline data) clears the found store too (never the changes waiting or their photos); a sign-out deletes the account's whole database (`deviceData.signOut`, see Signing out). UI `pages/sync/FoundOnDevice.tsx` over `offline/useFoundRows.ts` on Waiting to sync (`sync.found.*`), the judged rows per vehicle, Send/Forget per row and for all (one at a time, a failure said), Forget behind a `ConfirmDialog`; the navigation's Waiting to sync entry shows while judged rows wait too (`offline/useFoundCount.ts`, light enough for the shell; `sync.found.navCount`). Test fakes of `Session` must carry `instance` (`fakeInstance` in `mocks.tsx`), a missing non-null field makes Apollo drop the answer.
- **Device data** (the last answers seen; the rows downloaded ahead are under Downloaded window): the offline link keeps every error-free answer of a `keep` query (`offline/snapshotPolicy.ts`: every query is listed as `keep`, `onlineOnly` (admin, `Trash`, sharing, import, sessions: `OfflineError('onlineOnly')`) or `never` (`Health`, the photo-reading polls); a unit test fails for a query without a decision) under its name + sorted variables (`snapshotKey`) in `deviceData` (`offline/deviceData.ts` over `deviceStorage.ts`: IndexedDB `tankstat-offline-<user>` per user, `anonymous` for mode None, `tankstat-offline-meta` remembers the last user, `memoryStorage` when IndexedDB is missing; at most `MAX_SNAPSHOTS` (300) per user, oldest pruned, never `Session`/`UiSettings`, the older half when the quota is full; each answer carries `documentId` of its query and is not answered from for another version; every connection closes on `versionchange` and an open blocked by an old tab gives up after `BLOCKED_WAIT_MS`) and, while unreachable or when a query fails for want of the server, answers from it (`OfflineError('notLoaded')` when nothing is kept). `main.tsx` awaits `deviceData.boot()` (opens the last user's data); every `Session` answer says whose data it is (`userOf`: switch, or close on sign-out and forget the last user); nothing is written until a `Session` answer of this page load confirmed the user, and a `Login`/`Logout`/`ResetPassword` mutation unconfirms, so an answer for another account never lands in this one's data; the tabs tell each other on the `TABS_CHANNEL` `BroadcastChannel` whom a `Session` answer named, and a tab that hears of another account unconfirms and asks `Session` again (`onSignedInElsewhere`, from `runtime.ts`), since the cookies are shared.
- **Downloaded window** (`offline/pull.ts`, loaded on demand by `runtime.ts`: once a `Session` answer confirmed the user (`deviceData.subscribe`), when the server is back, hourly while visible, and `PUSH_AFTER_MS` after a `DOWNLOAD_AFTER` mutation (`AddVehicle`, `RestoreVehicle`: the offline link tells `appliedMutations` the name of every mutation the server applied); one run at a time, `offlineDownload()` for screens): the home list (`Welcome`, take 200; vehicles kept as `VehicleRow`s, the unlisted dropped with their logs, its pages of `HOME_PAGE_SIZE` kept as `Welcome` answers), the rules (`OfflineSettings`), then per vehicle (two at a time) `offlineChanges` in pages of 200: full the first time, when the window grew (`narrower`) or on `resync` (rows stamped `pulledAt`, the unseen removed at the end, resumable from `PullCursor.next`), else since the watermark (rows dated before the window removed, `removed` applied); a shrunk window only removes; `none` keeps no logs (and growing from it answers nothing offline until the first download is through); `sync.cursorInvalid` starts that vehicle afresh next time; a run stops (`AccountChanged`) once the server names another account; showing the tab again downloads only after `SHOWN_GAP_MS`. The first page's vehicle and schedules are kept as the `VehicleDetails`/`RecurringExpenses` answers (the feed selects `VehicleDetailsFields`/`RecurringFields`, so test fakes of those must carry `__typename`). Rows live in the user's IndexedDB v2 stores (`deviceStorage.ts` `RowStore`: `vehicles`, `refuelings`/`expenses` by vehicle, `cursors`; a per-vehicle copy in memory). `offlineWindow.ts` turns a rule into a local start date (`fromDate`: calendar months with month-end clamping, sub-day parts round down to the day). Offline, the link first asks `localResolvers.ts` (loaded on demand; `Refuelings`/`Expenses` any page and order once a vehicle's download completed, `*Details`, `*Trash` over the downloaded vehicles with Edit, `canEdit`/`canDelete` from the vehicle's `logAccess`), then the kept answers. The order mirrors the repositories (`sortLogs`; nulls first going up, cost/odometer/price as 0, refuelings tie on the odometer, then the id): `tests/backend/contracts/log-order/log-order.json` is checked by both `SortParityTests` (Infrastructure, real SQLite) and `LocalResolvers.unit.test.ts`.
- **Changes kept on the device** (`offline/changes.ts`, `outbox.ts`, `submitChange.ts`, `useLogChange.ts` (`useLogChange(entity, vehicleId)`, `useSubmitChange()`); sent by `push.ts`): every add, update, trash and restore of a log, a vehicle (home page, Details tab, the administrators' list `/admin/vehicles`, whose `Vehicles` query selects `version` and whose rows carry `PendingBadge`) or a schedule (deleting it = `trash`), and every visit (`markDone`: one change, `targetIds` = its schedules, `targetId` = its expense id) goes through `submitChange` (kept when unreachable, when the vehicle already has changes waiting, or on a connection failure of the mutation, with the same client id; otherwise sent as before), which stores a `Change` (`entity`, `action`, `vehicleId`, `targetId`, `input`, `expectedVersion` = the row's `version`, now selected by the grid, trash and details documents; a kept edit or trash also `base`: the values the entry had at that version, read from the Apollo cache by `offline/conflicts.ts` `baseOf` (the `*ChangeValues` fragments of `graphql/conflicts.graphql`, partial data, only when the cached `version` is the change's; `valuesOf` maps an entry to its input shape over `changes.ts` `UPDATABLE`), kept through folds from the first change, sent as JSON in `ChangeInput.base` and read back by `fromParked`) in the open user's IndexedDB v3 `changes` store (kept before the server confirmed the user too: the user made it on screen; `clear()`/Remove offline data never touches it). `collapse` folds an entity's changes (add+update = add, add+trash = nothing, update+update = last from the first version, update+trash = trash carrying the update's `input`, trash/restore cancel, a trash that took an edit's place coming back as that edit, also on `discard`, a second trash/restore or an edit of one waiting to be trashed = nothing); a vehicle added here and trashed takes every change of that vehicle along, a schedule added here and deleted leaves the visits waiting (a visit left with none goes); visits never fold, but a trash of the expense a waiting visit would log drops the visit's amount and photos (and what was made to that expense), and taking back such a visit takes its expense's changes along. A change marked `sent` (kept after a connection failure of its mutation, or about to be sent by `push.ts`: it may have been applied) is never folded into, a later change of the entity follows it from `versionAfter` it (`markOf` picks the mark that says most). The trash is never answered by the device while the server can be reached (Empty trash empties the server's), a waiting restore bumps the overlaid row's `version`, and a waiting add whose row was downloaded overlays that row. `localResolvers.withChanges` lays them over the rows after reading, never writing into them (a download may replace a row): an add is a row (`version` 0, no consumption), an update its values, a restore leaves the trash, a trash stays listed, marked (`usePendingMark`, the grids' sync column (below)); `LogDefaults`/`ExpenseCategories` are answered by the device too (for a vehicle it knows but holds no logs of, while unreachable: the last answer seen, else empty starting values, so its dialogs still open; `knownWithoutLogs`); `Vehicles` (the administrators' list, policy `keep`) is answered offline from the vehicles the device holds with their kept `VehicleDetails` and the vehicle changes over them, in any order (`vehicleKey`, like `VehicleRepository.Page`), and the page says only the device's vehicles are listed (`vehicles.offlineList`); vehicles and schedules build on the kept answers (`answerLocally`'s `kept`): `Welcome` (vehicles added here counted on every page but listed at the end of the last one, so `skip` stays the server's; never one it lists already), `VehicleCard`, `VehicleDetails` (a vehicle added here: `version` 0, no summary), `RecurringExpenses` (an added schedule is `UPCOMING`, never worked out on the device; a visit's expense with an amount is an expense row at version 1, as the server will create it; a waiting visit moves its schedules' baseline and version on and shows them `UPCOMING`, so they are not preselected again and an edit after it goes from that version), and `VehicleDashboard`/`ChartData` are empty for a vehicle added here. - **Sending them** (`offline/push.ts`, loaded on demand by `runtime.ts`, which sends before every download, and `PUSH_AFTER_MS` after a change is kept while reachable; `offlineSync()`/`usePushState()` for screens; *Sync now* on `/sync`): `batches` (vehicles added here first, then by `seq`, `CHUNK_SIZE` 20, never a change in the request of the add it depends on), `toChangeInput` (each mutation's input allowlisted), `syncChanges`; APPLIED and PARKED both leave the device (`outbox.remove`, after the download so nothing blinks; the download runs after every sync); each change is taken as it is when its request goes and `outbox.markSent` first, so an edit made during a run follows it instead of folding in and being removed with it; a request refused as a whole is sent again one change at a time (the one it cannot take waits); a change made on an add the server parked is not sent and waits, also in later runs (`PARKED_ADDS_KEY`, `unblockAdd`). Automatic runs (`runtime.ts` `download`) go through `tabLock.ts` `inOneTab('tankstat-sync')` (Web Locks, `ifAvailable`; without the API they just run; held at most `LOCK_HOLD_MS`; a run another tab kept from going is tried again after `LOCK_RETRY_MS` while changes wait), so several open tabs sync once; every outbox write runs one at a time across tabs (`exclusive`: lock `tankstat-outbox`, re-read from IndexedDB first, other tabs told over the `tankstat-outbox` BroadcastChannel) and push sends what `markSent` returns (the changes as stored), so an edit made in another tab or during a send is never lost; the Sync page's Edit is disabled while a sync runs, and a waiting add with kept photos stays savable without its amounts (`ChangeEdit.mayWait`); `keepStorage()` asks `navigator.storage.persist()` once an account's data is open. **Pictures kept for offline use** (`offline/keptPictures.ts`: IndexedDB v5 `pictures` store by image id, bytes + type; no runtime caching, see PWA): after the logs, every download (`pull.ts` `keepPictures`) keeps the downloaded vehicles' `pictureUrl`s, their owners' avatars and the user's own (from the `Session` answer) through `fetchSignedIn` (a 401 is retried after a refresh), never asks for a kept id again (an image never changes under its id), drops those no longer wanted, leaves out one the server does not give, and ends only this step on a lost connection or `QuotaExceededError`; `usePictureSrc` (`CoverLayers`, `VehiclePicture`, `UserAvatar`, the Account page) shows the kept copy first, online too, else the server's address unchanged (offline too: the browser's HTTP cache may hold it), and revokes every object URL on `deviceData.onStoreChange`; `clear()` (Remove offline data) empties the store, signing out closes it with the rest of the account's data; saved logs' photos and the avatars of who logged an entry are not kept; `VehiclePicture` falls back to its placeholder when a picture does not load.
- **A vehicle's picture offline**: `ImagePicker` with `keep={{ vehicleId }}` (only the Details tab; the avatar stays online-only and off while unreachable) keeps the picture (`keptPhotos.keep`) and submits a `setPicture` change (`{ key }`), or `removePicture`, while unreachable, while the vehicle has changes waiting, or after a connection failure (a new picture through `keepChange`, since a change with a kept photo always waits; a removal through `submitChange`, whose `queued` picks the status text); `collapse` keeps only the last picture change of a vehicle (never folded into its other changes; left out while the vehicle waits to be trashed); `localResolvers.vehicleOf` shows the last one (`keptPhotos.url`, or none); push sends it alone after the draft upload, like a log photo, and one whose picture is gone is done with.
- **Photos kept on the device** (`offline/keptPhotos.ts`: IndexedDB v4 `photos` store, bytes + type because a `Blob` does not survive every IndexedDB (fake-indexeddb included), key `local:<uuid>` in place of a draft id, `clear()` never touches it): `usePhotoQueue` keeps a picked photo (state `kept`, in `ids`, not in `busy`) while unreachable, while the vehicle has changes waiting (a draft would expire before the change is sent) or after an upload's connection failure; `submitChange` keeps any change that carries one; `PhotoGallery` (`vehicleId`) turns a saved log's add/remove into `addPhoto`/`removePhoto` changes (`{ key }`/`{ imageId }`; no reading), which `collapse` folds into a waiting add (`photoIds`), cancels (a kept photo removed) or drops with a trash; `localResolvers` lays them over the log's `photos` (`keptPhotos.url`); the add dialogs and the visit dialog let amounts wait for kept photos while reading is on as last heard (`readLater`, `ReadLaterNote`); `push.ts` sends a change with kept photos alone (`withPhotosAlone`), uploads them as drafts just before (`keptPhotos.asDraft`, reused for `DRAFT_REUSE_MS`), sends the draft ids (`toChangeInput(c, drafts)`), keeps a change waiting, photo and all, when the server will not take one of its photos this time (`photosWaiting`), leaves out a photo no longer on the device (`photosLeftOut`; an `addPhoto` without one is done with) and stops on a connection failure; `outbox` removes the photos of changes that fold away, are discarded or answered, and garbage-collects at load (only photos older than `GC_GRACE_MS`: a dialog in another tab may hold a newer one).
- **Parked changes**: what the server parked comes from the server, not the last run: `useParkedChanges` (`ParkedChanges`, `onlineOnly`, asked while reachable and after every run; tests get an empty default from `support/server.ts`) feeds `PendingChip` (`offline.notApplied`, after the waiting count), the navigation entry and *Not applied* on `/sync`, where `syncKinds.ts` `fromParked` (the inverse of `toChangeInput`) lets a parked change be shown like a waiting one, with *Apply anyway* (only where `canForce`: not for `*.notFound`/`auth.*`, a sender's `*.notFound` only while `current` is null) and *Discard* (`ConfirmDialog`s, `resolveSyncChange`, only with `canResolve`); an edit or trash is worded by `offline/conflicts.ts` `situationOf(change, current, reason)` (`changed`/`restored`/`alreadyTrashed`/`gone` for a trash, `trashedMeanwhile`/`gone`/`edited` for an edit): `pages/sync/ParkedDecision.tsx` `ParkedAccount` says what happened on each side (`current`'s who/when/how, `changedOnServer` against the change's `base`, worded by `pages/sync/useFieldText.ts`, texts `sync.conflict.*`/`sync.fields.*`) with a link to it now, and `ParkedActions` offers the choices of the case, each confirmation saying what it does (Done = APPLY, answered by the server's trash-once; *Restore it with your change* = APPLY + `restoreFirst` from `current.version`); Edit and apply sends `current.version` as `expectedVersion` and is not offered where an edit cannot work (`trashedMeanwhile`, `gone`); an `edited` one (a version mismatch with something to merge) is merged instead: `conflicts.ts` `merge(entity, base, mine, theirs)` (pure: one-sided changes taken from that side, `both` starts with this device's, a null on a `KEEP_WHEN_NULL` field is no change, values compared by `same`), the card's `MergeTable` (read only, states in words), *Merge…* = `EditChange` opening the entity's dialog with the merged values and `ChangeEdit.merge` (`MergeInfo`: both sides of each conflicting field in words, which side a one-sided field came from), which every entity dialog renders through `dialogs/useMergeFields.tsx` (`note(field, label, set?)`: the value the field does not hold with *Use it*; a controlled field takes it through its setter, an uncontrolled one through `value`/`key`, restarting only that field), applied against `current.version`; *Use mine everywhere* = APPLY, *Keep the server's* = DISCARD (texts `sync.merge.*`); a refusal says "Still not applied: ..." and the item stays. **Edit** (a waiting change) and **Edit and apply** (a parked one, with `canResolve`) for adds and updates of logs, vehicles and schedules (`changes.ts` `canEdit`): `pages/sync/EditChange.tsx` opens the entity's own dialog with `change` (`dialogs/changeEdit.ts` `ChangeEdit`: the change's values, its title and Save label; the dialog loads nothing, offers no photos and keeps an error `onSubmit` throws), and saves a waiting one as an `update` that folds into it (an add keeps its id and `photoIds`) or applies a parked one with `resolveSyncChange(change: toChangeInput(...))` (a refusal stays in the dialog, `ParkedChanges` is asked again). Visits, trashes, restores and photo changes have no Edit.
- **The server's side of sending**: `SyncMutations.SyncChanges` (`Api/GraphQL/SyncGraphQL.cs`: `ChangeInput` with exactly one of 22 operations (`setVehiclePicture`/`removeVehiclePicture` set a vehicle's picture from one of the sender's drafts, `ImageService.SetVehiclePictureFromDraftAsync`: idempotent (a draft row a first try left behind goes), a per-vehicle lock that uploads and removals take too (`StripedLocks`; the picture is not versioned), the draft's file moved into the picture folder, the old picture deleted; or remove it; the four before them add or remove a saved log's photo: `LogPhotoService.AttachDraftAsync` turns one of the sender's drafts into its photo, idempotently; the services come through the scoped `SyncChangeServices`), `sync.oneOperationRequired`, adds need an id `sync.entityIdRequired`; each becomes a `SyncChangeRequest` whose `Apply` calls the same service as the mutation with `expectedVersion`, and whose `VehicleOf` finds the vehicle without access checks) → `SyncService.SyncAsync` (batch checks `sync.tooManyChanges`/`sync.duplicateChange`/`sync.payloadTooLarge`, a striped per-user lock, a known id of another user is `sync.idTaken`, a known id of the same user is answered from the ledger, a `KeyedException` parks with key + args as text (filed under its vehicle and that vehicle's owner, or with the sender alone when the vehicle does not exist: the ledger's vehicle has a foreign key), anything else stops the batch with earlier rows recorded; a row is recorded with `CancellationToken.None` once applied, and one another server recorded first (`AddOnceAsync` false) is answered from the ledger; applied rows older than `Sync:RetentionDays` purged after each batch) → `SyncChange` rows (`SyncChanges` table: id = the device's change id, payload JSON ≤ 4000, FK cascade to the vehicle, deleted or moved with the user). A change may carry `base` (JSON of the values it was made from; kept apart from the payload in `SyncChange.Base`, only on parked rows, never read by the server) and `SyncChangeInfo` answers it with `current` (`SyncCurrent`: LIVE/TRASHED, version, `changedAt`/`changedBy`/`lastChange`, exactly one of `vehicle`/`refueling`/`expense`/`schedule`) through `SyncCurrentLoader` over `SyncTargetService.CurrentAsync` (re-checks access whoever sent it: View for what is live, Edit for what is in the trash, nothing for a log of a trashed vehicle or what is gone). `resolveSyncChange` keeps the `expectedVersion` of an edited change (a merge against the version the person saw parks again when it moved), applies a photo or picture change with its sender's draft whoever applies it (`uploadedBy`, the change's `SubmittedById`), and takes `restoreFirst` (an edit of a log or vehicle in the trash: restore, then edit, back to the trash when the edit is refused; `sync.cannotRestoreFirst`); a trash of what is already in the trash is applied on the sync path only (`TrashOnce` + the services' `InTrashAsync`).
