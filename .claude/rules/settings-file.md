# The app's own settings file and the Server settings page

- **The app's own settings file** (`Settings:Path`, default `settings.json` in the working directory, Docker `/data/settings.json`; documented in `docs/configuration.md`): `Api/Settings/SettingsFile.Prepare` runs first thing in `Program.cs` and inserts it as a `JsonConfigurationSource` right below the unprefixed environment variables (`ReloadOnChange = false`: no file watcher, a save reloads it, see System settings; the path comes from the sources already there, never from the file). The file must never stop the start: before the host is built, `SettingsCheck` is run on the sources with the file (`ConfigurationSources.With`: its JSON sources copied to be read once, the candidate disposed). It checks the shapes first, so a value of the wrong shape is named by its setting rather than by the binder, which quotes the value: `SettingsCatalog.Problems` (leaving out photo reading, never fatal, the log-level floor, a rule for what the page writes, and an empty value, which the binder reads as unset where a setting may be, `Backups:Keep`, and refuses by name elsewhere) and every `Logging` level, nested ones too, an empty one skipped as the logging filter does; then the refusals, through a throwaway container with the app's own registrations (`AddApplication` + `AddInfrastructure` + `AddAuthModes`): the logging set-up `Build()` makes (`AddConfiguration` + `AddConsole`, the factory resolved: `Logging:CaptureScopes`, the console's options and its formatters'), `IStartupValidator`, binding `Smtp`; a binder failure keeps the path, taken from the end of the message, never the value. A file that cannot be read or is not valid JSON, or whose candidate has problems the sources without it have not (`SettingsCheck.Added`, shapes and refusals compared each on their own because `Check` stops at the shapes), is left out (`SettingsFileStatus`, a singleton; `SettingsFileReporter`, the first hosted service, writes the one deliberate Error line that is no exception, naming the settings at fault and never their values, and `NoticeService` appends the public `SETTINGS_FILE_IGNORED` warning, which names nothing because notices are public and kept by devices); what the environment gets wrong on its own neither keeps a broken file in nor leaves a good one out, and an environment the host would not start with at all (`SettingsCheck.Starts`: only what the host itself refuses) stops the start as it always did, with a readable file in place so the host names its mistakes too. What the host only finds while starting (Standalone with no administrator while the setup is turned off, a database it cannot reach) still stops it (the docs say so); a new instance waits for its setup instead (see Setup). A left-out file takes its `Auth:Mode` with it, but never the authentication: when the mode without the file is None, no source above the file holds it (`ConfigurationSources.HoldsFrom`) and the file names a sign-in mode or cannot be read, `Prepare` throws `SettingsFileRefusedException` (before the host exists; the message names the file, the settings at fault and `Auth__Mode`) instead of leaving it out. `Application/SystemSettings/SettingsCatalog` is the list of what the file manages (groups in the page's order, keys, kinds, secrets, choices and spellings still accepted but not offered, `AlsoAccepted`: `Smtp:Security` offers MailKit's names, pinned by `SmtpEmailSenderTests`, and still accepts the old `Ssl`, which runs as Auto; pinned to the options classes by `SettingsCatalogTests`, which fails for a property neither listed nor in `LeftOut`: the prompt file and `Backups:Path` are left out on purpose; `Validate` checks a value's shape and the log-level floor, `Logging:LogLevel:Microsoft.AspNetCore` and below never under Warning). `Infrastructure/Settings/SettingsFileStore` reads the file through the JSON provider (so the keys are the configuration's: lists as `Key:0`; `SourceFor` roots the provider at the file's folder hiding nothing, so a name starting with a dot is read too, and the start and the Seeder read the file through it as well) and writes it whole: nested JSON, lists as arrays, every value a string, the previous file kept as `.bak`, both created owner-only (`UnixCreateMode`), one write at a time. `SettingsFile.Source` is the file's source, read at start or not, so a candidate configuration with other file values can be built in its place (`ConfigurationSources.With`) and checked the same way. The Seeder reads the file below the environment too (`--settings`, `Settings:Path`). A local run's `src/backend/Tankstat.Api/settings.json` is no Content item (`Tankstat.Api.csproj`), so no build, test folder or `out/` carries it. **System settings** (`Application/SystemSettings/SystemSettingsService`, administrators through `RequireAdminAsync`, or the setup page's wizard with the one-time code while the setup waits, `SetupGate`, see Setup; GraphQL `systemSettings`, `updateSystemSettings(changes)`, `restartServer` in `Api/GraphQL/SystemSettingsGraphQL.cs`): the view is every catalog entry with its `SettingSource` (`ISystemConfiguration`, implemented by `Api/Settings/SystemConfiguration` over the live `ConfigurationManager`: a provider above the file's place is `Environment` and read-only, the file `File`, below it `Shipped`, nowhere `Default`; a list counts as held by the highest source of any item), its value after the next start (the file's content in the file's place, `ISystemConfiguration.With`; a secret as `IsSet` only) and `RestartPending`, only for a setting that waits for a restart (`SettingDefinition.AppliesAtOnce` false: that value differs from `ISystemConfiguration.Started`, the start's copy of the configuration, which the OIDC check below compares with too). The groups of `SettingsCatalog.LiveGroups` (Defaults, Notifications, Sync, Backups, Logging; GraphQL `SystemSettingsGroup.appliesAtOnce`) apply at once: after the write `ISystemConfiguration.ApplySavedFile` puts a fresh `SettingsFileStore.SourceFor` in the file's place (or below the environment when the start had none or left it out), which reloads the `ConfigurationManager`, and their readers take `IOptionsSnapshot<T>` or, in a singleton, `IOptionsMonitor<T>.CurrentValue` (the backups'; the log levels: the framework's own monitor), pinned by `LiveSettingsReadersTests` (no `IOptions<T>` of a live group's options anywhere); a single setting of a group read at start can apply at once too (`SettingsCatalog.LiveKeys`, `SettingDefinition.AppliesAtOnce` = its group's or its key's, GraphQL `SystemSetting.appliesAtOnce`): `Auth:Standalone:PasswordMinLength` (#120), bound into its own `PasswordOptions` (section `Auth:Standalone`, in `OptionsSections`, validated 10..128 at start and by the save's check) and read through `PasswordRequirements`' `IOptionsMonitor`, never through `AuthOptions`, which keeps no change token (pinned by `LiveSettingsReadersTests` too) and `SystemSettingsTests`; the sign-in, the mail (built from `Auth:PublicUrl`) and photo reading (provider built at start) are read once and wait (`AuthOptions` is bound without a change token, so the reload never validates the saved sign-in again against the `Smtp` its validator read at start, which failed the save; `_source` is taken before the sources change, and an apply that throws anyway leaves the save saved: a Warning, and the view says what runs). **Rule for new settings:** make a setting apply at once wherever its readers can read it afresh (`IOptionsSnapshot`, `IOptionsMonitor.CurrentValue`, never a kept `IOptions` value), and show *Restart needed* only where a restart is really needed. An update applies the changes to the file's current content (a blank clears a setting, a blank keeps a secret, `Clear` removes either, a list is one item per line; a file it cannot read is replaced only when the start left it out, else `settings.invalid`: what it holds may run, the sign-in mode too, and a save would drop it), refuses `settings.unknownKey`/`settings.readOnly`, validates the shapes (`SettingsCatalog.Validate`) and then what the next start would hold against the file (`ISystemConfiguration.Check` = `SettingsCheck.AgainstFile` against the sources with no file: what the file's values add, else what the host itself refuses, so a mistake of the environment's own that the app runs with anyway holds no save back, as it leaves no file out at start; `settings.invalid` with `problems`), then the rules only a running app knows: `settings.standaloneNeedsAdministrator` (no args: Standalone with no enabled local administrator while the setup does not wait; only the setup page makes the first one, #149, so the way there is a switch outside the app, after which the start reopens the setup, see Setup), and when the next start's mode is Oidc and its mode or authority is not the running one (whatever the save changed: a file left out at start may hold them), `IOidcDiscovery` (`Infrastructure/Settings/OidcDiscovery`, a typed HttpClient: 10 s for the whole exchange, body included, no redirects although the handler would follow them, 64 KB, a body cut short is `unreachable`, a byte order mark is read, http allowed and the User-Agent sent like the handler; in tests a fake) must answer with the authority as its issuer (`settings.oidcUnreachable` with `reason`, `settings.oidcIssuerMismatch` with `issuer`; `SameIssuer` ignores a trailing slash and the case of the scheme and host); all or nothing and one save at a time (a static lock from the read to the write), a secret stored as typed, every candidate configuration disposed (a source of the host's chains a configuration that lives as long as the host), `settings.fileNotWritable` on an I/O failure (a Warning with its exception); Information "Administrator {AdminId} changed system settings {Keys}" (names only) and "... restarted the server". A start that fails ends the process, so `RestartAsync` first asks `ISystemConfiguration.PrepareNextStart` (the running sources without the file's, `SettingsFile.Prepare` on them: the file read afresh) and refuses a restart the next start would refuse (`settings.restartWouldFail` with `problems`, the file's refusal; `settings.standaloneNeedsAdministrator`, the same rule as a save); what only the start finds (a database out of reach) still stops it. `IServerRestart` (`Api/Settings/ServerRestart`) sets `RestartRequests` and stops the host a moment later, and a stop signal ends the process even with a restart pending (`RestartRequests.EndOnStopSignals`, registered once before the loop; the host's own handler still stops it gracefully); `Program.cs` is a `do { build; run } while (restarts.Requested)` loop (in-process, never by exiting: Docker's default policy leaves a clean exit stopped; nothing may catch around `Build()`: `WebApplicationFactory` aborts it with `HostAbortedException`; `schema export` stays a one-shot), so a restart is a second "database migrations ... up to date" in the same process (`RestartSmokeTests`, `docker-smoke.sh`'s Standalone container). `Domain/Instance/InstanceState` is a one-row table (`LastStartMode`, `LastStartedAt`, and the restore's `Generation`, `RestoredAt`, `RestorePoint`, see Backups; race-safe upsert) that `InstanceStartService` writes at every start through the hosted `ModeChangeSignOut` (after `DatabaseMigrator` and `SetupStep`, so a start that fails before it records nothing, and before the server listens; the row also holds the setup state, which only `SetupStore`'s conditional updates change, see Setup): a start in another mode than the recorded one revokes every `UserSession` (`IUserSessionRepository.RevokeAllAsync`, Information with `Before`/`After`/`Count` when any, else Debug), the first start and a same-mode restart revoke nothing (`ModeChangeSignOutTests` over `SharedData`). Frontend: `admin/SystemSettingsPage.tsx` (lazy, `/admin/settings`, administrators only, *Server settings* in the navigation's Administration group (`NavList`: a `role="group"` named by its heading, a label, not a page: *Overview* `/admin` = `admin/AdminOverviewPage.tsx`, what needs an administrator (a restart pending, the settings file left out, the database unreachable) with a link each, else one line, a few facts, and the folders the environment decides (`SystemSettingsInfo.folders`, `ServerFolder`: kind, full path as started, setting and its variable; the photos `sameAsPictures` on one root; the database left out, its connection string can hold a password), from the `AdminOverview` query asked `no-cache` (`onlineOnly`; its partial `systemSettings` must never replace the page's whole one in the cache); *People* `/admin/people` = `admin/AdminPanel.tsx`, Users and Access tabs in `?tab=`; *Vehicles* `/admin/vehicles`, the full list; `App`'s `AdminHome` sends the old `/admin?tab=access|users` to People and `KeepQuery` the old `/vehicles` to the new address with its query); the `SystemSettings` query is `onlineOnly`, and its error hides the earlier answer Apollo keeps beside it): the file's status (`SETTINGS_FILE_IGNORED` worded with the problems for administrators), a restart card (`ConfirmDialog` → `restartServer`, a request that got no answer counting as the restart happening, never an `OfflineError`, which was not sent (`classifyFailure`), then `admin/restartFlow.ts` `waitForRestart` probes `Health` with `offline: 'bypass'` and the runtime's `withDeadline(…, PROBE_TIMEOUT_MS)` until the old host went and the new one answers, then `navigation.reload()`, unless the page was left meanwhile (then `Session` is asked again instead); `RESTART_WAIT` is shortened by tests), a tab per group (`TabbedPanels`, the chosen one in `?tab=<group in lower case>`, the first without; a tab with unsaved changes is named "<group> (not saved)") and `SettingsGroupForm` in it. The drafts live in the page (`SettingsTabs`: per group `{ basis, draft }`, a draft whose basis is no longer the server's settings starts afresh as the page is drawn, and a save drops it by `onSaved`), since only the chosen tab is mounted; every group's held values decide which settings of the others are used: `admin/settingsRelevance.ts` (pure: `RULES` by the sign-in mode (`Auth:PublicUrl`, `Auth:Standalone:*`, `Smtp:*` Standalone; the session lifetimes Standalone or Oidc; `Auth:AdminEmails` Oidc or ProxyHeader; `Auth:Oidc:*`, `Auth:ProxyHeader:*` their mode), by `Smtp:Host` (port, security, login only with a server) and by `Recognition:Provider` (OpenAiCompatible); `valueOfDraft`: the typed value, else the running one, and nothing greyed out on a guess: a value the file holds and the form cleared, or a setting the server did not list, is unknown) worded by `useUnusedText`. An unused setting is shown with its value but disabled (a change typed before it became unused is still saved), its reason said once at the widest place it holds: a note above the group, a section's header, or the field's hint. `admin/settingsSections.ts` `layoutOf` lays a group out: the deciding settings (and any no section names) above, then MUI `Accordion`s per kind (sign-in: sessions, Standalone, OIDC, proxy, administrators; e-mail: server, login; photo reading: model server, how photos are read; one-kind groups have none), open while used and closed while not unless the person chose (a choice that leaves one unused folds it), the header saying why and "changes not saved yet"; each panel is named by its header (explicit ids: an unnamed region fails axe). Every setting shows its source as a `LabelBadge` beside its label (`components/LabelBadges.tsx`, a chip whose full wording is read as the start of the control's description; `Field`, `LabeledSelect` and `LabeledSwitch` take `badges`), a "Restart needed" badge while it waits (only a setting of a group read at start ever does; each tab says whether its changes apply at once or after a restart, a setting that applies otherwise than its tab says so in an "Applies at once" badge (`SettingsGroupForm`, `groupAppliesAtOnce`), and the toast after a save says which from the answer's `restartPending` of the settings that save sent, never the whole tab's, since a tab can mix them: the password minimum applies at once beside sign-in settings an earlier save left waiting), and a question mark (`admin/SettingHelp.tsx`: a tooltip on hover, focus and tap, `describeChild`) with what it does (`systemSettings.help.<Key>`) and its environment variable. A setting nothing sets starts at its built-in default: `SystemSetting.defaultValue` (`SettingsCatalog.BuiltInDefault`: the options class's own value read by reflection, as the page writes it; none for a secret, a list (the items are added to built-in ones) or a log category other than `Default`, which follow that one; a choice the class leaves empty that offers `None` is `None`), `admin/settingsDraft.ts` `effectiveOf`; leaving it there, or emptying it, saves nothing. `SettingsGroupForm` per group (the environment's settings read-only in a `DefinitionList`, the rest as controls by kind: `LabeledSwitch`, `LabeledSelect` (its `hint` is the select's description) with a *Default (not set)* choice, a password field with *Remove the stored value* for a set secret, lists one per line; values are compared as the server reads them: a switch's `True` and a choice in any case, a choice it takes but no longer offers (`Ssl`) shown as written, a decimal sent with a dot; only what changed is sent, a blank clears, a change of `Auth:Mode` asks once more, naming what a cleared mode or `None` comes to, with the recovery sentence; the save's answer is written into the `SystemSettings` query (no refetch) and starts the form afresh; a `settings.invalid` answer's `problems` are said at the controls they name (`admin/settingsText.ts` `problemsByKey`: a validator's message starts with the setting's key; `Field`'s `refusal`, `LabeledSelect`'s `error`; the first one takes the focus), and only what names no editable text or choice of the group (another group's setting, the environment's, a switch, the days) is listed under the form; after a refusal the focus returns to the button the closing confirmation could not give it to, being off while busy); labels are `systemSettings.fields.<Key__With__Underscores>` (colons and dots replaced: i18next's separators), hints carry only the reason a setting is unused and a list's *one per line* (the source and a pending restart are badges, the variable is behind the question mark); test fakes must carry `__typename` (the documents use fragments). Tests: `TestApp` registers a `FakeServerRestart` (`app.Restarts.Count`) over the app's own, because a real restart would stop the test host, and hands `Settings:Path` to the host through `UseSetting` (a command-line argument, since Program.cs reads it before the host is built, where the in-memory settings do not exist yet) and gives every host a file of its own (`SharedData` one shared file); `ApiFixture` and `scripts/test-api.sh` set `Settings__Path`, `AppProcess` drops `Settings__` (`RunUntilExitAsync` takes a work folder, the default file's place), `SeederAppTests.Run` names a settings file that does not exist unless a test names one; in-process the fixture's `Auth__Mode` beats any file, so a file faulting the authentication is a smoke test (`SettingsFileSmokeTests`), the other faults are `SettingsFileTests`. A `TestApp`'s in-memory settings join only when the host is built, after `Prepare` decided, so the tests of the decision itself call `SettingsFile.Prepare` on a `WebApplication.CreateBuilder` of their own, with command-line arguments standing in for the environment, or, for the refusal (which the fixture's `Auth__Mode` would hide), on a `ConfigurationManager` with one in-memory source and no environment at all. **Backups carry it** (#140, see Backups): the file on disk when a run starts, the instance's settings only (`Application/Backups/SettingsInBackups`: the catalog's and the `Logging` section, never a machine's own key, a secret only with `Backups:Secrets`) through `ISettingsBackup` (`Api/Settings/SettingsBackup.cs`, registered by Program.cs before `AddInfrastructure`); a restore judges the file it would leave with `With` + `Check` like a save, writes it through `ISettingsFileStore.WriteAsync` (`.bak`), keeping this server's machine keys and, from a backup without secrets, its secrets, and the next host reads it (`IServerRestart.RestartNow`).
