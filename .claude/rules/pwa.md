# The installable app (PWA)

- **PWA:** `vite-plugin-pwa` (Workbox; `registerType: 'prompt'`: a new build is downloaded in the background and waits (`skipWaiting` only on the page's message); `pwa/registerApp.ts` hands it to `pwa/appUpdate.ts` and `shell/UpdateNotice.tsx` shows "A new version is available" with a Reload button, so nothing reloads by itself and a form is never lost; Reload posts `SKIP_WAITING` to the waiting worker and reloads on `controllerchange` (or after `RELOAD_FALLBACK_MS`), and when nothing waits any more (another tab took it) it just reloads; a tab another tab moved to the new worker says "Reload to finish updating" (`appUpdate.finishing`, `behind`); every later version is offered too (`updatefound` stays attached), and one still installing when the page opened once it is installed; the first worker still controls the page at once (`clientsClaim`), and that first take-over is the app being ready offline (`pwa/offlineReady.ts`: `storing`/`ready`/`unsupported`, a one-time toast from `shell/OfflineReadyNotice.tsx`, a line on the Offline data panel, `keepStorage()` from then on), not an update; `pwa/watchForUpdates.ts` asks for a new version every hour and when a tab is shown again, because a browser only checks when a page is opened) generates `manifest.webmanifest` from the `manifest` option in `vite.config.ts` (the icons are the files in `src/frontend/public`) and `sw.js`, which precaches the built shell (`**/*.{js,css,html,ico,png,svg,webmanifest}`, every lazy chunk included) and answers navigations with `index.html` except the paths of `pwa/serverPaths.ts` (`/graphql`, `/auth/`, `/media/`, `/imports/`; unit-tested, and the smoke script greps the built worker for `auth`: an `index.html` answer to the OIDC login or callback would end sign-in and make the instant redirect loop); no runtime caching. `main.tsx` registers it through `pwa/registerApp.ts` (own registration over `navigator.serviceWorker`, production builds with service workers only; the container is a parameter, so `RegisterApp.unit.test.ts` drives it with `EventTarget` fakes) and imports `pwa/installPrompt.ts` first of all (module-level capture of Chromium's `beforeinstallprompt`, which fires before any menu exists); `pwa/useInstallPrompt.ts` with `pwa/platform.ts` (standalone and iOS detection; an object tests spy on) drives `shell/InstallMenuItem.tsx` in the navigation (Chromium: the browser's dialog; iOS: a how-to dialog; nothing elsewhere or once installed). Kestrel sends the cache rule of `Api/StaticCaching.HeaderFor` (`/assets/*` immutable, fixed names `no-cache`) for the static files and the SPA fallback (`MapFallbackToFile("index.html", staticFiles)`); `index.html` carries `viewport-fit=cover`, `theme-color` and the Apple meta tags, and the top bar, the drawer, `#main`, the footer and the skip link keep clear of the safe-area insets (their `sx`). No worker under `vite dev`. A lazy page whose code cannot be loaded (a tab on an older release than its worker or the server; `pwa/chunkRecovery.ts` knows the Chromium, Firefox, Safari and Vite messages) is handled by `ErrorBoundary`: it reloads the same address once (`tankstat.chunkReload` in sessionStorage, not again within a minute) when a newer worker controls the tab (`appUpdate.behind`; its cache answers the reload, offline too) or the server answers `serverAnswers` (a `HEAD /sw.js` past every cache, which the worker never answers; not even asked when `connectivity` or `navigator.onLine` says offline, since a reload there lands on the browser's offline page), which loads the current version; otherwise it says the page is not available offline yet (`app.notOfflineYet`). The offline engines' lazy imports (`runtime.ts`, `usePushState`, the Offline data panel) catch a failed load and try again later. Only that page reloads, since the person just asked for it; a background import (`pull`, `push`, `localResolvers`) never reloads anything, so there is deliberately no `vite:preloadError` handler. `scripts/docker-smoke.sh` checks the manifest, the worker and the cache headers. Tests: `tests/frontend/support/setup.ts` clears sessionStorage and resets the install prompt after each test.
