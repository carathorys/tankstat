# Authentication and sessions

- **Authentication** (`Auth:Mode`: None, Standalone, Oidc, ProxyHeader; default None) is selected lazily at runtime, so all schemes are registered and `ModeAwareSchemeProvider` hides OIDC unless it is the mode; the default scheme follows the mode too (`AuthExtensions`: the proxy's in ProxyHeader, the cookie in Standalone and OIDC, none in mode None, so a cookie left over from another mode never names a user in mode None, and nothing may authenticate or challenge without naming its scheme). Sign-in only produces a cookie/proxy identity that names a user; `HttpCurrentUser` always reloads the user (admin flag, disabled, session version) from the database. Users live in the `Users` table for every mode. Standalone passwords use the framework PBKDF2 hasher; reset tokens are random, stored hashed, single use, one live link per user (every issue, the administrator's too, replaces the earlier ones and lazily purges the rows whose lifetime ended over a day ago, by `IssuedAt` and the current `ResetTokenMinutes`); a self-service request (`requestPasswordReset`) does the same work for every address, so neither its time nor its answer tells accounts apart: one lookup, and for a known account `IPasswordResetQueue.Enqueue` with the user's `SessionVersion` (`Infrastructure/Auth/PasswordResetQueue.cs`: a bounded in-memory channel of 1000, a user at most once with the session version of their latest request, full = a Warning, lost when the app stops); `PasswordResetMailer` (a `BackgroundService`, says nothing at start) serves it after the answer, `PasswordResetMailer.Senders` (4) at a time, each in a scope of its own (so a mail server that does not answer holds one sender, not the line), through `PasswordResetService.SendRequestedAsync`, which looks at the account again and issues nothing once its `SessionVersion` moved (a new password or disabling since the request revoked every link, and no link may outlive that), without SMTP or while the user's latest link is younger than `Auth:Standalone:ResetCooldownMinutes` (5, 0 = off) and still valid, all logged by user id (a mail server's failure a Warning, anything else the mailer's Error, after which the next request is still served; at stop, however the cancellation surfaces, the request cut short and those still waiting are an Information line each; tests: `World.ResetQueue.DrainAsync()`, and `PasswordResetQueue.WhenIdleAsync()` in the API tests, never a sleep). The look at the latest link, the note of the ids already there (`IdsForUserAsync`) and the storing of the new one run under a per-user `StripedLocks` lock (so the mailer never stores its link after an administrator's that its look at the cool-down missed, pinned in `UserAdministrationTests`; an administrator's issue has no cool-down; a burst of the user's own requests is one queued request, and two of them served at once by different senders do not both pass the cool-down), the e-mail after it; only then are exactly those earlier ids removed, so two issues at once never remove each other's link. A self-service link whose e-mail failed is taken back by its own id (never the user's other links: one an administrator handed over keeps working), so it holds no request back; an administrator's issue (`createUser`, `issuePasswordReset`) keeps such a link instead and answers it with `emailFailed` (`IssuedReset.Email` = `EmailOutcome.Failed`, a Warning by user id), so the administrator hands it over; any other failure takes back the new link and leaves the earlier ones. `SmtpEmailSender` bounds a whole send by `SendTimeout` (20 s: within HotChocolate's 30 s request limit for the administrators' inline sends, and the only limit on the mailer's), so a mail server that never answers is an `EmailSendException`. Never expose `User` entities directly in GraphQL (password hash): use the DTOs in `Api/GraphQL/Dtos.cs`. The OIDC browser flow: `auth/OidcSignIn.tsx` sends a fresh visitor to `/auth/oidc/login?returnUrl=<path+query>` through the `navigation.replace` seam (`src/frontend/navigation.ts`; spy it in tests, jsdom cannot navigate), shows a signed-out screen while `auth/oidc.ts`'s `signedOut` flag is set (sessionStorage `tankstat.auth.signedOut`, set by `NavList`'s sign-out in OIDC mode, so the provider's live session does not sign the user straight back in) and a failed screen for `?signIn=failed&reason=<code>`; on the server `OnRemoteFailure`/`OnAccessDenied` redirect there through `Api/Auth/OidcFailures.cs` (`OidcFailure` codes classified by exception type, a nonce or state mismatch counting as ours; `ProvisionOidcUser` refuses with `OidcSignInRefusedException` or the `ForbiddenException` itself, never a message; `LocalPathOrRoot` accepts one leading slash and printable ASCII only) and log one Warning with the code and the exception type, never the provider's text. `OidcProviderFlowTests` runs the whole flow against a stubbed token endpoint with a test-signed id_token. **Sessions (Standalone and OIDC):** a short access cookie (`tankstat.session`, `Auth:AccessTokenMinutes` 15, not sliding, always persistent: `SessionCookies.SignInAsync`; OIDC sets `IsPersistent` in `ProvisionOidcUser`, which must only call `IssueRefreshAsync` because the remote handler signs the principal in itself) carrying a `sid` claim, plus a refresh cookie (`tankstat.refresh`, `Path=/auth/token`, HttpOnly, `SameSite=Lax`) holding the refresh token of a `UserSession` row (`UserSessionService`, the `PasswordResetService` stack: `"{id:N}.{secret}"`, SHA-256 hash, fixed-time compare; plus the secret encrypted by `ISecretProtector` = the Data Protection key ring). `POST /auth/token/refresh` (`TokenEndpoints`, needs `X-Requested-With: fetch`, 404 in None/ProxyHeader) rotates the secret and slides the expiry (`Auth:RefreshTokenDays` 90; session rows are only written by conditional `ExecuteUpdate`s: a rotation only while the presented secret is current and the session not revoked, the loser of two at once answered like the grace, a revoke only where `RevokedAt` is null, never a whole-row save); the previous secret within `Auth:RefreshRotationGraceSeconds` (60) gets the *current* secret back (no new rotation, so racing tabs converge), later it is reuse: the session ends with a Warning. Every refusal is `UnauthenticatedException` (401 + both cookies cleared). Password change: `AdoptVersionAsync` on the asking session *before* `RevokeOthersAsync`; reset, admin set-password and disabling revoke all; `HttpCurrentUser`'s per-request reload stays the immediate revocation, and it also refuses an access cookie whose `sid` session ended; a start in another `Auth:Mode` than the last one revokes every session (`InstanceStartService`, see The app's own settings file). `POST /auth/token/logout` (what the app uses, works after the access cookie ran out) and the `logout` mutation (by `sid`) end the session; the Account page lists the user's devices (`mySessions` with `current` from the `sid`, `revokeSession(id)`, which also clears the cookies when it is this device, `revokeOtherSessions`; `UserSessionService.ListMineAsync`/`RevokeMineAsync`/`RevokeMyOthersAsync`, `auth.modeUnavailable` outside Standalone/OIDC; UI `pages/account/SessionsPanel.tsx`, this device's Sign out is the normal sign-out through `auth/useSignOut.ts`, shared with `NavList`; `ClientLabel` turns the User-Agent into "Firefox on Linux" and only that is stored; tests get one device by default from `support/server.ts`); stale rows go a week later, lazily on refresh. The key ring is persisted (`DataProtection:KeysPath`, `KeyRingOptions`, Docker `/data/keys`; `TestApp` gives each host its own folder; `SharedData` in `TestApp.cs` gives several hosts in turn one database, key ring and upload folders, an instance restarted with other settings, and its `StandaloneAdminCookiesAsync` hands back a Standalone administrator's cookies for it). Frontend: `auth/refresh.ts` (`refreshSession` single flight per tab, `fetchSignedIn` for REST: one retry after a 401, `signOutDevice`), `refreshLink` in `apolloClient.ts` (UNAUTHENTICATED → refresh → the operation once more; when the device has to sign in the `Session` query is asked again so the sign-in screen appears, a refresh that did not get through leaves the answer alone; never for the sign-in operations, except that a `Session` answer of nobody in STANDALONE/OIDC tries one refresh first, so a reopened app with only its refresh cookie left stays signed in); test fakes default to a refused refresh and a working sign-out (`support/server.ts`).
