# The setup of a new instance

- **What waits** (`Application/Setup`, #90): a new instance waits for its gatekeeper: its first administrator (Standalone, OIDC, proxy) or, with sign-in off, the acknowledgement that everyone who reaches it sees and changes everything. The step that provides it completes the setup; so while it waits no administrator exists, and the one-time code (`OneTimeCode`, the instance's only code, also the mode None restore code: 12 characters of a 32-letter alphabet without 0/O/1/I, shown `XXXX-XXXX-XXXX`, compared in fixed time ignoring hyphens, whitespace and case, made per process (`RestartRequests.Code`, registered by `Program.cs` over the Application's `TryAddSingleton`): a restart in the process keeps it, so the setup page goes on with the code it was given (the wizard's restart, a provider's sign-in after it), a new process makes a new one; no lockout: the `SETUP_PENDING` notice is public, so a lockout would let anyone keep the setup locked, and 60 bits cannot be guessed over HTTP; a refusal is the GraphQL listener's Warning, never the typed code) opens its steps instead. Once completed nothing in it opens again (`setup.completed`); restore, backup keys and defaults are any-time administrator operations of the Backups and Server settings pages, not setup steps.
- **The state** (`InstanceState.SetupPendingSince`, `SetupCompletedAt`, `SetupCompletedVia`: `SetupCompletion` Upgrade/Environment/Administrator/Acknowledged; `InstanceState.Setup` = `SetupPhase` Undecided/Pending/Completed, ignored by EF): changed only by `Infrastructure/Persistence/Repositories/SetupStore`'s conditional `ExecuteUpdate`s (decided only while undecided, completed only while pending), never by `InstanceStartService`'s save of the row, which leaves them unmodified (`InstanceStateRepository.Update`: written back as read, they would undo a completion another server made meanwhile). `CompleteWithAdministratorAsync` completes the row first, then adds the user, in one transaction: of two requests at once the second waits on the row and adds nobody (`SetupStoreTests`). Undecided = a row from before the setup existed, or a backup's from then (a restore brings the backup's row, setup state included: `TableLoad.StampAsync`). A restore into Standalone with neither bootstrap credential takes a backup without an administrator when its own setup waits (`RestoreStep.BackupSetupWaits`: its row pending, or undecided with no user and no vehicle), since that start waits for the setup page instead of stopping.
- **The start** (`SetupStep`, the hosted step after `RestoreStep` and `PhotosMove`, before `ModeChangeSignOut`, where `StandaloneBootstrapper` was; `SetupService.StartAsync`): undecided is decided by `HoldsDataAsync` (any user, any vehicle with the trash) **before** the bootstrap administrator is made, which would count as data: data = completed `Upgrade`, none = pending; then a pending one is completed `Environment` by `Setup:Enabled=false` (`SetupOptions`, environment only, not in the settings catalog, validated on start; `BootstrapAdminAsync(setupWaits: false)` first, so a Standalone start without an administrator or credentials stops before the completion is written and a later start with the setup on still waits), in Standalone by an existing local administrator or the bootstrap credentials (`AuthService.BootstrapAdminAsync(setupWaits: true)` creates it), in OIDC/proxy by a non-empty `Auth:AdminEmails`; a weak bootstrap password, or only one of the two credentials, still stops the start; a set-up instance runs `BootstrapAdminAsync(setupWaits: false)`, which throws as it always did (Standalone, no administrator, no credentials: the message the smoke test pins), so the three refusals that keep a set-up Standalone instance from losing its administrator (`settings.standaloneNeedsAdministrator` on a save and a restart, a restore whose backup has none) stay. `SetupStatus` (a singleton) is the process's copy of "pending", set at start and cleared by a completion here; while it says pending, what the setup opens (`setup { pending }`, every step's code check, `RestoreService`'s code path, `BackupWorker`) asks the database through `SetupStatus.PendingAsync`, so a completion on another server on the same database closes it here at the first such request, and the notice goes with it (else at the next start). While pending the start logs `Setup is waiting: open /setup in the browser and enter the one-time setup code {Code}` at Warning (a log kept to warnings has it too), a start-up contract like the restore code's line.
- **The steps** (`SetupService`, GraphQL `Api/GraphQL/SetupGraphQL.cs`): `setup { pending }` (public, `SetupStatus.PendingAsync`), `setupRestorePoints(code)` (the folder's restore points as `RestorePointInfo`, the administrators' list stays `backups`), `setupUploadLimitMb(code)` (`Backups:MaxUploadMb`, which the Backups page tells administrators only) with `PUT /media/backups` and the code in its `X-Setup-Code` header (`BackupAdminService.RequireUploaderAsync`, see Backups), `restoreBackup(input: { ..., code })` (`RestoreService` takes the code in mode None **or while the setup waits**), the wizard's settings through the settings page's own `systemSettings(code)`, `updateSystemSettings(changes, code)` and `restartServer(code)` (`SystemSettingsService`: an administrator, or with `code` the gate; logged as the setup page's, no administrator id; while the setup waits `settings.standaloneNeedsAdministrator` steps aside on a save and a restart, since the start then waits for the setup page instead of stopping), `setupFinish(input: { code, email, password, acknowledgeOpenAccess })` (the last step, `SetupService.FinishAsync`, in the sign-in mode the next start runs, `ISystemConfiguration.Running`: Standalone makes the first administrator by the bootstrap administrator's rules through `AuthService.NewAdministrator`, `user.emailExists`, `setup.administratorExists`, with the completion in one transaction, and signs them in through `SessionCookies.IssueAsync` when Standalone runs already; sign-in off needs `acknowledgeOpenAccess`, `setup.acknowledgementRequired`; OIDC and proxy complete nothing there: `Auth:AdminEmails` saved by the wizard completes it at the next start, else the claim after the restart; what the next start would refuse is refused first (`SystemSettingsService.RequireStartableAsync`), then the one restart when a saved setting waits for it, `RestartPendingAsync`; answers `restarting` and `signedIn`), `setupClaimAdministrator(code)` (OIDC, proxy: the signed-in user, `AccessService.RequirePrincipalAsync`, is made administrator with the completion in one transaction, `SetupStore.CompleteWithClaimAsync`; a mode without a provider is `setup.otherMode`); every operation the code opens goes through `SetupGate` (pending as the database says first, `setup.completed`, then the code, `setup.codeInvalid`, `ForbiddenException`), `RestoreService` too. In mode None GraphQL stays fully open while the acknowledgement waits: the gate there is the page, not the API.
- **The page** (`src/frontend/setup/SetupPage.tsx`, lazy): `App.tsx` `useSetupTakesOver(data)` (the `SETUP_PENDING` notice, and mode None or Standalone with nobody signed in, while the server is reachable: offline the session is the device's last answer and the page could only say it needs the server; except while the page waits for a restart it asked for, the last step's or a restore's, which it holds through `setup/takeoverHold.ts` (`useHoldTakeover`, read by `useTakeoverHeld`): the server is away on purpose then, and the page in its place would lose the wait that reloads or goes on once it is back) puts it in place of every page, the sign-in included, with no menu; with a provider (OIDC, proxy) the visitor signs in first and the notice links to `/setup` (`NoticeBanner`), a route for everyone (`setup.notPending` once done). The banner leaves that notice out where the page is what is shown (`App.tsx` `Notices`: in place of every page, or at `/setup` past the sign-in; it reads the address, so a navigation redraws only it), and while the setup waits there `AUTH_DISABLED` too (the shipped None is not chosen yet: the wizard asks for a mode and `OpenAccessStep` says what sign-in off means; the server still sends it, and the app shows it again once the setup is done). When `setup` says done while the session still carries the notice (completed on another server), the page asks the session again, which ends the takeover. `Setup` (`setup { pending }`, `network-only`) decides between the steps and "nothing to set up"; `Setup`/`SetupRestorePoints` are `onlineOnly`. The wizard (`setup/SetupWizard.tsx`, the page's only way while the setup waits): the code is typed once and kept in the page's state only; `SetupRestorePoints` is its check (`setup.codeInvalid` under the form), the restore list and the upload limit at once. Then `SystemSettings` with the code and a step per group of the Server settings page, in its order, through the page's own `SettingsGroupForm` and `useGroupDrafts` (nothing copied: `code`, `required: ['Auth:Mode']` for the sign-in, which starts empty although the shipped None runs, no *Default (not set)*, *Choose one to go on.* at the select until a mode is chosen; `confirmModeChange={false}`, Next saves the step with the code or goes on when nothing changed, `saveUnchanged`, no toast; Back, and Skip on every step after the sign-in, which drops what was typed there); a group with nothing to choose (the environment holds it whole, or another setting leaves every one of it unused: the e-mail without local accounts) has no step. `WizardProgress` says "Step n of m: <group>" with a bar and takes the focus as each step appears. The first step offers *Restore from a backup*, which only then shows *Restore a backup* (*Start fresh instead* goes back; the folder's points, a newer release's without a button; under them the Backups page's own `UploadBackup` (`admin/upload.tsx`, its own module so the setup page never loads `BackupsPanel`) with `code`: `uploadBackup(file, code)` sends the header and renews no session, then the list is asked again; `admin/restore.tsx` `RestoreDialog` with `code`, shared with the Backups page, then `RestartWait` with the generation taken when the restore was asked for, whose `notRestored` slot offers *Back to the setup*: the restart kept the code). The last step by the mode the saved settings name (`LastStep`): Standalone `AdministratorStep`, sign-in off `OpenAccessStep` (its checkbox, Finish off until ticked), both through `setupFinish`; a provider not running yet `ProviderRestartStep` (*Restart and finish*: the administrators named become them as they sign in; none named, `claimNext.ts` remembers in this tab that the claim follows, so after the provider's sign-in the wizard opens at its last step, the code asked again); a provider running `ClaimStep` (`setupClaimAdministrator`). `useFinishSetup`: `setupFinish`, then when it answers `restarting` the settings page's wait (`restartFlow.ts` `waitForRestart` over `healthProbe`, `RestartStatus` says it), then `/setup` (`/` with sign-in off) and `client.resetStore()`: the done screen, after the sign-in a mode change asks for (`useStepAction` holds a step's busy state and refusal). `/setup` once done: for an administrator the done screen (`Done`: the Backups page's own key set, `admin/encryption.tsx` `EncryptionSetup`, fed by `BackupRecipient` (`backups { settings { recipient } }` alone, `no-cache` so it never replaces the Backups page's id-less overview in the cache, `onlineOnly`; the `Backups` query would read every backup and walk the folders), which it asks again after the keys are saved (`refresh`), its error said in its place; the setup page never loads the Backups page's module, then links to the settings page's Backups and Defaults tabs and, in Standalone, People), for anyone else `setup.notPending`. Tests: `tests/frontend/setup/Setup.integration.test.tsx` (per mode through the wizard, a mode chosen and the restart, the claim resumed, the restore with its reload, the done route; the settings fake `wizardSettings` in `support/mocks.tsx`), scans of the code, a settings step and the restore view in `Accessibility.integration.test.tsx`; in a real browser `tests/e2e/setup.e2e.ts` (the wizard to the first administrator with its restart, and a restore of an uploaded backup, each on a waiting server of its own that `scripts/test-e2e.sh` starts, see `.claude/rules/e2e.md`).
- **Around it**: `NoticeService` appends `SETUP_PENDING` (Info) after every other notice, so `notices[0]` stays `AUTH_DISABLED`; `BackupWorker` writes nothing while pending and the database holds nothing (`HoldsDataAsync`; Backups). Test hosts: `TestApp` sets `Setup:Enabled=false` (the setup's tests turn it on, `SetupTests`), its template database is left undecided, `scripts/test-api.sh` turns it off, the smoke processes keep it on (`StartupSmokeTests`: Standalone with nothing configured waits and logs the code; with the setup off it still stops).
