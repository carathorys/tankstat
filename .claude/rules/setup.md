# The setup of a new instance

- **What waits** (`Application/Setup`, #90): a new instance waits for its gatekeeper: its first administrator (Standalone, OIDC, proxy) or, with sign-in off, the acknowledgement that everyone who reaches it sees and changes everything. The step that provides it completes the setup; so while it waits no administrator exists, and the one-time code (`OneTimeCode`, the instance's only code, also the mode None restore code: 12 characters of a 32-letter alphabet without 0/O/1/I, shown `XXXX-XXXX-XXXX`, compared in fixed time ignoring hyphens, whitespace and case, made at every host start, an in-process restart too; no lockout: the `SETUP_PENDING` notice is public, so a lockout would let anyone keep the setup locked, and 60 bits cannot be guessed over HTTP; a refusal is the GraphQL listener's Warning, never the typed code) opens its steps instead. Once completed nothing in it opens again (`setup.completed`); restore, backup keys and defaults are any-time administrator operations of the Backups and Server settings pages, not setup steps.
- **The state** (`InstanceState.SetupPendingSince`, `SetupCompletedAt`, `SetupCompletedVia`: `SetupCompletion` Upgrade/Environment/Administrator/Acknowledged; `InstanceState.Setup` = `SetupPhase` Undecided/Pending/Completed, ignored by EF): changed only by `Infrastructure/Persistence/Repositories/SetupStore`'s conditional `ExecuteUpdate`s (decided only while undecided, completed only while pending), never by `InstanceStartService`'s whole-row save, which writes back what it read. `CompleteWithAdministratorAsync` completes the row first, then adds the user, in one transaction: of two requests at once the second waits on the row and adds nobody (`SetupStoreTests`). Undecided = a row from before the setup existed, or a backup's from then (a restore brings the backup's row, setup state included: `TableLoad.StampAsync`).
- **The start** (`SetupStep`, the hosted step after `RestoreStep` and `PhotosMove`, before `ModeChangeSignOut`, where `StandaloneBootstrapper` was; `SetupService.StartAsync`): undecided is decided by `HoldsDataAsync` (any user, any vehicle with the trash) **before** the bootstrap administrator is made, which would count as data: data = completed `Upgrade`, none = pending; then a pending one is completed `Environment` by `Setup:Enabled=false` (`SetupOptions`, environment only, not in the settings catalog), in Standalone by an existing local administrator or the bootstrap credentials (`AuthService.BootstrapAdminAsync(setupWaits: true)` creates it), in OIDC/proxy by a non-empty `Auth:AdminEmails`; a weak bootstrap password still stops the start; a set-up instance runs `BootstrapAdminAsync(setupWaits: false)`, which throws as it always did (Standalone, no administrator, no credentials: the message the smoke test pins), so the three refusals that keep a set-up Standalone instance from losing its administrator (`settings.standaloneNeedsAdministrator` on a save and a restart, a restore whose backup has none) stay. `SetupStatus` (a singleton) is the process's copy of "pending", set at start and cleared by a completion here (another server's completion is learned when this one's conditional write fails, or at its next start); while pending the start logs `Setup is waiting: open /setup in the browser and enter the one-time setup code {Code}` at Information, a start-up contract like the restore code's line.
- **The steps** (`SetupService`, GraphQL `Api/GraphQL/SetupGraphQL.cs`): `setup { pending }` (public, from `SetupStatus`), `setupRestorePoints(code)` (the folder's restore points as `RestorePointInfo`, the administrators' list stays `backups`), `restoreBackup(input: { ..., code })` (`RestoreService` takes the code in mode None **or while the setup waits**), `setupCreateAdministrator(input: { code, email, password })` (Standalone: the bootstrap administrator's rules through `AuthService.NewAdministrator`, `user.emailExists`, `setup.administratorExists`; signs the new administrator in through `SessionCookies.IssueAsync`), `setupAcknowledgeOpenAccess(code)` (mode None); a step of another mode is `setup.otherMode`; every step checks pending first (`setup.completed`), then the code (`setup.codeInvalid`, `ForbiddenException`). In mode None GraphQL stays fully open while the acknowledgement waits: the gate there is the page, not the API.
- **Around it**: `NoticeService` appends `SETUP_PENDING` (Info) after every other notice, so `notices[0]` stays `AUTH_DISABLED`; `BackupWorker` writes nothing while pending (Backups). Test hosts: `TestApp` sets `Setup:Enabled=false` (the setup's tests turn it on, `SetupTests`), its template database is left undecided, `scripts/test-api.sh` turns it off, the smoke processes keep it on (`StartupSmokeTests`: Standalone with nothing configured waits and logs the code; with the setup off it still stops).
