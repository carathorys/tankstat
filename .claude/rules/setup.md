# The setup of a new instance

- **What waits** (`Application/Setup`, #90): a new instance waits for its gatekeeper: its first administrator (Standalone, OIDC, proxy) or, with sign-in off, the acknowledgement that everyone who reaches it sees and changes everything. The step that provides it completes the setup; so while it waits no administrator exists, and the one-time code (`OneTimeCode`, the instance's only code, also the mode None restore code: 12 characters of a 32-letter alphabet without 0/O/1/I, shown `XXXX-XXXX-XXXX`, compared in fixed time ignoring hyphens, whitespace and case, made at every host start, an in-process restart too; no lockout: the `SETUP_PENDING` notice is public, so a lockout would let anyone keep the setup locked, and 60 bits cannot be guessed over HTTP; a refusal is the GraphQL listener's Warning, never the typed code) opens its steps instead. Once completed nothing in it opens again (`setup.completed`); restore, backup keys and defaults are any-time administrator operations of the Backups and Server settings pages, not setup steps.
- **The state** (`InstanceState.SetupPendingSince`, `SetupCompletedAt`, `SetupCompletedVia`: `SetupCompletion` Upgrade/Environment/Administrator/Acknowledged; `InstanceState.Setup` = `SetupPhase` Undecided/Pending/Completed, ignored by EF): changed only by `Infrastructure/Persistence/Repositories/SetupStore`'s conditional `ExecuteUpdate`s (decided only while undecided, completed only while pending), never by `InstanceStartService`'s save of the row, which leaves them unmodified (`InstanceStateRepository.Update`: written back as read, they would undo a completion another server made meanwhile). `CompleteWithAdministratorAsync` completes the row first, then adds the user, in one transaction: of two requests at once the second waits on the row and adds nobody (`SetupStoreTests`). Undecided = a row from before the setup existed, or a backup's from then (a restore brings the backup's row, setup state included: `TableLoad.StampAsync`). A restore into Standalone with neither bootstrap credential takes a backup without an administrator when its own setup waits (`RestoreStep.BackupSetupWaits`: its row pending, or undecided with no user and no vehicle), since that start waits for the setup page instead of stopping.
- **The start** (`SetupStep`, the hosted step after `RestoreStep` and `PhotosMove`, before `ModeChangeSignOut`, where `StandaloneBootstrapper` was; `SetupService.StartAsync`): undecided is decided by `HoldsDataAsync` (any user, any vehicle with the trash) **before** the bootstrap administrator is made, which would count as data: data = completed `Upgrade`, none = pending; then a pending one is completed `Environment` by `Setup:Enabled=false` (`SetupOptions`, environment only, not in the settings catalog, validated on start; `BootstrapAdminAsync(setupWaits: false)` first, so a Standalone start without an administrator or credentials stops before the completion is written and a later start with the setup on still waits), in Standalone by an existing local administrator or the bootstrap credentials (`AuthService.BootstrapAdminAsync(setupWaits: true)` creates it), in OIDC/proxy by a non-empty `Auth:AdminEmails`; a weak bootstrap password, or only one of the two credentials, still stops the start; a set-up instance runs `BootstrapAdminAsync(setupWaits: false)`, which throws as it always did (Standalone, no administrator, no credentials: the message the smoke test pins), so the three refusals that keep a set-up Standalone instance from losing its administrator (`settings.standaloneNeedsAdministrator` on a save and a restart, a restore whose backup has none) stay. `SetupStatus` (a singleton) is the process's copy of "pending", set at start and cleared by a completion here; while it says pending, what the setup opens (`setup { pending }`, every step's code check, `RestoreService`'s code path, `BackupWorker`) asks the database through `SetupStatus.PendingAsync`, so a completion on another server on the same database closes it here at the first such request, and the notice goes with it (else at the next start). While pending the start logs `Setup is waiting: open /setup in the browser and enter the one-time setup code {Code}` at Warning (a log kept to warnings has it too), a start-up contract like the restore code's line.
- **The steps** (`SetupService`, GraphQL `Api/GraphQL/SetupGraphQL.cs`): `setup { pending }` (public, `SetupStatus.PendingAsync`), `setupRestorePoints(code)` (the folder's restore points as `RestorePointInfo`, the administrators' list stays `backups`), `restoreBackup(input: { ..., code })` (`RestoreService` takes the code in mode None **or while the setup waits**), `setupCreateAdministrator(input: { code, email, password })` (Standalone: the bootstrap administrator's rules through `AuthService.NewAdministrator`, `user.emailExists`, `setup.administratorExists`; signs the new administrator in through `SessionCookies.IssueAsync`), `setupClaimAdministrator(code)` (OIDC, proxy: the signed-in user, `AccessService.RequirePrincipalAsync`, is made administrator with the completion in one transaction, `SetupStore.CompleteWithClaimAsync`), `setupAcknowledgeOpenAccess(code)` (mode None); a step of another mode is `setup.otherMode`; every step checks pending first (`setup.completed`), then the code (`setup.codeInvalid`, `ForbiddenException`). In mode None GraphQL stays fully open while the acknowledgement waits: the gate there is the page, not the API.
- **The page** (`src/frontend/setup/SetupPage.tsx`, lazy): `App.tsx` `setupTakesOver(data)` (the `SETUP_PENDING` notice, and mode None or Standalone with nobody signed in) puts it in place of every page, the sign-in included, with no menu; with a provider (OIDC, proxy) the visitor signs in first and the notice links to `/setup` (`NoticeBanner`), a route for everyone (`setup.notPending` once done). The banner leaves that notice out where the page is what is shown (`App.tsx` `Notices`: in place of every page, or at `/setup` past the sign-in; it reads the address, so a navigation redraws only it). When `setup` says done while the session still carries the notice (completed on another server), the page asks the session again, which ends the takeover. `Setup` (`setup { pending }`, `network-only`) decides between the steps and "nothing to set up"; `Setup`/`SetupRestorePoints` are `onlineOnly`. The code is typed once and kept in the page's state only; `SetupRestorePoints` is its check (`setup.codeInvalid` under the form) and the restore list at once. Steps: *Restore a backup* (the folder's points, a newer release's without a button; `admin/restore.tsx` `RestoreDialog` with `code`, shared with the Backups page, then `RestartWait` with the generation taken when the restore was asked for, whose `notRestored` slot offers *Enter the new code*: a refused restore comes back with a new code), *Start fresh* by mode (`AdministratorStep` `setupCreateAdministrator`, `ClaimStep` `setupClaimAdministrator`, `OpenAccessStep` with its checkbox, Finish off until ticked), each ending with `client.resetStore()` and `/setup` (`/` with sign-in off). `/setup` once done: for an administrator the done screen (`Done`: the Backups page's own key set, `admin/encryption.tsx` `EncryptionSetup`, fed by `BackupRecipient` (`backups { settings { recipient } }` alone, `no-cache` so it never replaces the Backups page's id-less overview in the cache, `onlineOnly`; the `Backups` query would read every backup and walk the folders), which it asks again after the keys are saved (`refresh`), its error said in its place; the setup page never loads the Backups page's module, then links to the settings page's Backups and Defaults tabs and, in Standalone, People), for anyone else `setup.notPending`. Tests: `tests/frontend/setup/Setup.integration.test.tsx` (per mode, the restore with its reload, the done route), a scan in `Accessibility.integration.test.tsx`.
- **Around it**: `NoticeService` appends `SETUP_PENDING` (Info) after every other notice, so `notices[0]` stays `AUTH_DISABLED`; `BackupWorker` writes nothing while pending and the database holds nothing (`HoldsDataAsync`; Backups). Test hosts: `TestApp` sets `Setup:Enabled=false` (the setup's tests turn it on, `SetupTests`), its template database is left undecided, `scripts/test-api.sh` turns it off, the smoke processes keep it on (`StartupSmokeTests`: Standalone with nothing configured waits and logs the code; with the setup off it still stops).
