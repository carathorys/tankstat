# Logging

## Logging

- **Logging:** the standard `ILogger<T>` on the console, nothing else installed (no Serilog); Application uses `Microsoft.Extensions.Logging.Abstractions` (the layering rule only forbids EF Core and HotChocolate there). Style: `logger.LogX("... {Placeholder}", id)` with named placeholders, no `[LoggerMessage]`; the field is called `logger`, never `log` (a "log" here is a refueling or expense). Levels: *Information* for what an operator looks for (sign-ins and sign-outs, password changes, administration, access changes, sharing, imports, emptied trashes, migrations, reachability coming back), *Debug* for ordinary changes (with entity ids), *Warning* for refusals, failed sign-ins and failures that used to be swallowed (a `catch` that swallows something an operator would want to know about logs its exception; a provider that is not healthy says why by throwing, see `IRecognitionProvider.IsHealthyAsync`), *Error* only for unexpected exceptions (plus the one deliberate Error without an exception: the settings file left out at start, `SettingsFileReporter`), which `Api/GraphQL/GraphQLLoggingListener` logs once (HotChocolate has no logging of its own; it dedupes by exception instance; a non-null field that was null (`ErrorCodes.Execution.NonNullViolation` at a field path; without a path the same code is a required variable the client left out) is a server bug no hook tells about, so `RequestScope.Dispose` finds it in the result and logs a Warning naming the field the way the schema does (`SchemaField` walks the operation's selections by the path's response names); a request the engine turns down, such as a missing variable, is the client's doing and only Debug; `MediaEndpoints.TranslateErrors` logs the keyed errors of the REST side, an unexpected REST exception is logged by the framework as it always was). Ids only in the app's own lines: never e-mails, names, plates, notes, amounts, passwords, reset tokens or links, API keys, OIDC subjects or read values (two deliberate exceptions: the opt-in `Recognition:OpenAiCompatible:LogTraffic`, see Photo reading in the app, and the instance's one-time code (`OneTimeCode`), which `SetupService` logs at every start while the setup waits (at Warning, so a log kept to warnings has it) and `RestoreStep` at every start in mode None, where no administrator can guard the setup's steps or a restore asked for from the app (see Setup), see Backups; a backup's passphrase or identity never), and nothing a client sent (variables, documents, request-error text; an operation name only when it is a valid GraphQL name, a grid id only after it passed `GridSettings.CheckGridId`; a field by its schema name `Type.field`, not by the alias a client gave it; REST lines name the route pattern, not the path: a line break in client text would forge a log line). The edge, which `docs/configuration.md` states: the text of an unexpected exception and the framework's own lines are written as they come (a database can quote values in its error), and `Microsoft.AspNetCore` must stay at Warning or above (its request lines hold reset-link tokens). A lasting condition is logged when it changes, not on every check (`RecognitionAvailability`, `EfDatabaseProbe`); `SmtpEmailSender` throws an `EmailSendException` that keeps only the status of a refused command (a mail server's answer quotes the recipient). The shipped `appsettings.json` silences EF Core's SQL and the HttpClient's per-request lines, keeps `Tankstat` at Information (Debug in Development); smoke tests start the app in Production and expect "database migrations" and "up to date" in its output and nothing with "Photo reading" by default, so those texts are a contract. Console options such as `IncludeScopes` or `TimestampFormat` only apply when `Logging:Console:FormatterName` is set (`simple` or `json`); a scope must be a message with a placeholder (`BeginScope("UserId: {UserId}", id)`), since the console prints a dictionary as its type name (the smoke test reads the real output). Tests: `TestSupport/CapturedLog` (`World.Log` in the Application tests, `TestApp.Log` in the API tests, `TestDatabase.Log`) and canary tests that run a broad flow and assert that no typed value or secret reaches a line (`LoggingTests` in Application and in the API integration tests; `log.Mentions(needle)` does not count a find strictly inside a token shaped like a random id (a GUID, 16 or 32 hex characters, a `0H…` request id), typed or not, since such an id can spell a short needle such as `24687` by chance: search a canary's whole value, or one made of letters no id holds (`zzzz`), never a piece of a value that could be logged in such a shape: `CapturedLogTests`); find a line by its class (`log.From<T>()`) and level and read the values of its placeholders (`entry.Values["UserId"]`), do not assert the wording of a message. Frontend: `apolloClient.ts` (`reportOperationError`, an Apollo `ErrorLink`) and `ErrorBoundary` write unexpected request failures and crashed pages to the browser console and send nothing; an error with a `key` is expected (the screen shows it) and not reported.
