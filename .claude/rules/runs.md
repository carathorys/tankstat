# Runs: one transaction across the services

A run (#335, the first part of #334) is background work, an import from a backup or a partial restore, whose every save through the app's services lands in **one database transaction**. Nothing starts one yet: parts 3 and 6 of #334 do. The owner's decisions are in #335's handoff.

- **The port** (`Application/Runs`): `IRunScope.RunAsync(RunStart(starter, vehicleIds), work, ct)` commits when `work` returns; anything it throws rolls the whole run back and is rethrown. A token cancelled before the commit rolls back too, but the commit itself is never cut short (one cancelled halfway may have gone through, and the undos would take back the files of rows that stayed). The work gets an `IRun`:
  - `InSavepointAsync(work)`: a savepoint of its own, nestable (a car, an entry inside it). When the work throws, what it saved is rolled back, the run goes on, and the exception reaches the caller, who decides what a refusal means.
  - `OnRollback(undo)` and `AfterCommit(act)` for what is outside the database (a photo's file written, an old picture's file to delete). Each follows the savepoint it was registered in: rolled back, its undos run at once (newest first) and its deferred acts are dropped; kept, both pass to the level around it (also when the savepoint could not be rolled back or released: they then follow what is around it). A hook that throws is logged as a Warning with the run's id and the rest still run.
  - `ThrowIfStoppedAsync()`, for the work to call **between its entries**: `RunStoppedException(RunEnd.Cancelled | TimedOut)`. Nothing stops a run in the middle of a save.
  - A run inside a run is refused.
- **The scope** (`Infrastructure/Persistence/Runs`): `RunScope` opens a connection and a transaction of its own and sets `RunTransaction.Current` and `RunContext.Current` (both `AsyncLocal`, set in a method of their own so the commit and the hooks run outside the run again). `RunDbContextFactory` is the `IDbContextFactory<AppDbContext>` everyone takes: the pooled factory outside a run, and inside one an **unpooled** context enlisted in the run's connection and transaction (a pooled one that was enlisted keeps the finished transaction when leased again). `CreateOutside()` goes around the run: only the marks use it.
  - **Only what the work calls is inside:** a request, a hosted service and a `Task.Run` started elsewhere never are. Work that starts a task inside a run hands the run on with the execution context, so it does not start any.
  - **One connection:** nothing inside a run may run two database calls at once, or keep a reader open across another call.
- **A repository's own transaction** goes through `db.BeginInnerAsync(ct)` (`InnerTransaction`): a transaction outside a run, a savepoint inside one (a context enlisted in a run refuses a second transaction). The seven sites on a run's path use it (a log's linked rows, the schedules, the photos, the tyre save). A new repository method that needs several saves to hold together uses it too, never `BeginTransactionAsync`, unless it can never run inside a run (settings, setup, backups).
- **A database error that is caught and worked on from** (`AddOnceAsync`, `Upsert`, the tyre save's repeat check): PostgreSQL refuses every statement after an error in a transaction. EF puts a savepoint of its own around each `SaveChanges` on a context that is in a transaction and rolls back to it, which is what keeps these going; `RunScopeTests.AKeyViolationARepositoryCatches_DoesNotEndTheRun` pins it. A statement outside `SaveChanges` (`ExecuteUpdate`, raw SQL) whose failure is caught needs `BeginInnerAsync` around it.
- **Who the services act as:** inside a run `AccessService.RequirePrincipalAsync` answers the run's starter (`RunContext.Current.Starter`); there is no request. Nothing else reads the current user.
- **The mark** (`RunMarker` with its `RunMarkerVehicles`, tables of their own, no foreign keys): saved **before** the transaction opens and ended after it (`RunEnd`: Done, Failed, Cancelled, TimedOut, Interrupted), always around the run's transaction (`RunMarkerRepository` over `CreateOutside`). It is what every server sees of a run, and all that is left of one a stopped server rolled back.
  - `RunMarkerSweep` (hosted, after the migrations and a restore) ends marks that can no longer be running, as Interrupted, with a log line: on SQLite every one open at start; on a database server only those older than the limit, at start and once a minute, since another instance may be mid-run. It never ends a mark of a run open in this process (`RunGateState.IsOpenHere`: a run is only stopped between its entries, so one can outlive its limit), and a run's own end replaces an Interrupted another server's sweep guessed. Ended marks are kept 30 days. Telling the starter is the caller's part (#337 has the texts).
- **The gate** (the owner's decision 1): `RunGate.WaitAsync(vehicleId)` waits while an open mark not older than the limit holds the car, `RunTimings.BusyWait` (10 s), then throws `BusyException` (`import.busy`). The run's own saves pass. Every door that changes a car calls it through `AccessService.WaitForRunsAsync`: `LogAccessGuard.RequireEditAsync` (logs, schedules, tyres, photos: **use it, not the static `RequireEdit`, for a change**), `VehicleService`'s edit, trash and restore, the vehicle's picture, its sharing, its saved charts and widgets and its dashboard layouts. A change that is not about one car waits while **any** run is open (`WaitForRunsAsync(ct)`, `RunGate.WaitForAllAsync`): emptying a trash (vehicles, refuellings, expenses, tyres) and deleting a user, whose rows may be a run's. A new door that changes a car or what belongs to it calls one of the two. Not gated: what belongs to a person and no car (settings, the vehicle order, notifications, sessions), and the Fuelio import, whose every save goes through the gated services (`VehicleService`, `RefuelingService`, `ExpenseService`, `RecurringExpenseService`; its repositories it only reads).
  - `RunGateState` remembers for a second that no run is open, so a save asks the database at most once a second; the scope forgets it when it writes or ends a mark. A run therefore pauses `RunTimings.Settle` (2 s) between its mark and its transaction: saves that passed the gate just before finish, and another server's gate sees the mark. A save in flight on another server longer than that can still cross a run: an accepted limit.
- **Busy on the wire** (decision 2): GraphQL code `BUSY`, key `import.busy`; the picture endpoints and the token refresh **409** (never 503, which a client reads as a server out of reach). `SyncService` never parks it: the batch stops, what came before is recorded. Clients: `offline/errors.ts` `isBusy`; the push keeps its changes, does not mark the server unreachable, and sends again after `BUSY_RETRY_MS` (a minute); a dialog shows `errors.import.busy` and stays open. A session renewal answered busy (`auth/refresh.ts` `RefreshBusyError`) signs nobody out: the refresh link answers the operation that needed it with `BUSY` (`apolloClient.ts`, the Session query too), and `fetchSignedIn` hands back the busy 409. A Standalone sign-in during a SQLite run is told busy like any save. **Known limit:** an OIDC sign-in whose session cannot be saved during a SQLite run ends as `callback_rejected` (the callback's save is outside GraphQL), and the person signs in again after the run.
- **SQLite** has one lock to write: a run holds it for its length, so every other save waits, whatever car it is for.
  - While a run of this process is open (`SqliteLock.Held`), commands and transaction starts outside the run wait `RunTimings.BusyWait` instead of the driver's 30 seconds (`SqliteLock`, `SqliteLockTransactions`), and a save that still finds the database locked is `BusyException` (`AppDbContext.SaveChangesAsync`); a statement of its own that fails so is recognised by `IBusyFailures` where failures become answers (`BusinessErrorFilter`, `MediaEndpoints.TranslateErrors`, the token refresh).
  - What writes on its own time looks at `RunGateState.WritesLockedOut` and comes again later (decision 5): the scheduled backup, the inbox's bring-up-to-date on the bell's query, the tombstone sweep. A new background writer does the same. The photo worker waits while any run is open on any database (`RunGate.AnyOpenAsync`): the log a photo fills may be the run's.
  - **Reads go on** however much a run has written: the app's SQLite files are in WAL mode (EF sets it when it creates the file; pinned by `RunScopeTests.TheAppsSqliteDatabase_IsInWalMode_SoARunNeverShutsReadersOut`). A database made otherwise, in rollback-journal mode, would shut readers out once a run outgrew its page cache.
  - The client's request timeout is 30 seconds (`REQUEST_TIMEOUT_MS`), three times the wait: a save that waits is answered busy long before it could be taken for a server out of reach.
  - `SqliteLock.Held` is a process-wide count: one database per process in the app, but in tests every host of the process shares it, so a test's open run shortens the waits of tests running beside it.
  - The marks cannot be written while a run is open there, so a cancel is this process's own (`RunScope.CancelAsync` finds the run in memory, from its mark on: one asked for before the transaction opens is kept for the run; the flag is only ever set, so the mark's answer never writes over it); on a database server a run of another instance is asked through its mark, which the run reads between its entries.
- **Cancel and the limit** (decision 3): `IRunScope.CancelAsync(runId, by)` for the starter and any administrator (others: forbidden). `Runs:LimitMinutes` (10; the Server settings page, under Backups; read when a run starts and by the gate, no restart) is how long a run may hold its transaction, and how old an open mark may be before it stops making saves wait.
- **Tests:** `RunScopeTests` (Infrastructure) runs the real services inside a run on SQLite always, and on PostgreSQL, SQL Server and MySQL when `TANKSTAT_TEST_*` names them (`docs/development.md`); **a change to the scope, the helper or a repository on a run's path is run against PostgreSQL before it is pushed**, since only PostgreSQL shows a missing savepoint. MySQL runs the vehicles only until #345 is fixed. `RunBusyApiTests` (API): every door busy, a device's batch, an open run on SQLite. `Push.integration` on the device's side.
