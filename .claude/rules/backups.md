# Backups, restore, the Backups page, schedule and retention

## Backups

- Backups (`Domain/Backups`, `Application/Backups`, `Infrastructure/Backups`, `Api/Backups`; `docs/backup-and-restore.md`): one file per run, written by `BackupWriter` (`IBackupWriter`, the port in Application; `BackupRequest`/`BackupResult`): an outer **stored** zip holding `data.age` (encrypted) or `data.zip` (plain) and, **after it**, `manifest.json` in plain (`BackupManifest`, camelCase JSON, found by name, never by position: the sizes, row counts and the SHA-256 of the inner archive are only known once that is written; nothing personal in it, pinned by a canary test). The inner zip holds `tables/<Table>.jsonl` (`TableDump`: every table of the EF model by `GetTableName()`, an owned type with its owner, plus `__EFMigrationsHistory`; one row per line, column names as in the database, each value read with the type mapping's `GetDataReaderMethod()` (a `DateOnly` column through `GetValue` first: Oracle's MySQL connector returns a `date` as a `DateTime` and throws on `GetFieldValue<DateOnly>`, which also keeps the app itself from reading logs there) and written typed, whatever the process's culture (the custom date patterns with `CultureInfo.InvariantCulture`: th-TH would write the year 2569, fi-FI `12.34.56`): GUIDs and ISO 8601 UTC date-times as strings, numbers, booleans, null, base64 for bytes; ordered by the key; an unknown value type fails the backup rather than guessing), from **one consistent read** that ends before the files are copied (`BackupSource`, scoped to the table loop: `Serializable` locks would otherwise hold the app's writes up through the whole copy, and an idle snapshot would meet a server's idle-in-transaction timeout; SQLite = `BackupDatabase` from the live file, opened `ReadWrite` so a missing one is never created, to a copy in a temporary folder of its own (`Directory.CreateTempSubdirectory`, never the backups folder), dumped from the copy; PostgreSQL/MySQL `RepeatableRead`; SQL Server `Snapshot` where `sys.databases.snapshot_isolation_state` is ON, else `Serializable` with an Information line: asked first, because a database that does not allow snapshots only says so at the first statement inside the transaction, not at `BEGIN`; a rollback the clean-up cannot do, on a broken connection, is a Warning, never the backup's failure), `files/pictures/...` (everything under `Storage:Path`, `BackupFiles.Walk`: never a `vehicles/<id>/drafts` folder; a folder the app cannot list, a disk's lost+found, is left out with a Warning; a database that lists `Images` while neither root exists is a Warning), `files/photos/...` (a photos root of its own, only with `Backups:Photos` or `--photos`; on one root the photos are in `files/pictures` anyway, `BackupPhotos.WithPictures`) and `keys/*.xml` (`KeyRingOptions`, now in Application, bound by `AddApplication`; **encrypted backups only**: the key files hold their key in plain; the manifest's `keys` is true only when key files went in). **The settings file** (#140) goes beside the inner archive as an outer entry of its own, `settings.age` (`AgeStream.Encrypt` for the backup's recipient) or `settings.json`, written after the data and before the manifest, its SHA-256 and size as stored in the manifest's `settings` (`BackupSettingsFile`: `state` `included`/`none`/`ignored`, `entry`, `sha256`, `bytes`, `omitted`: names only, in the configuration's spelling, a list once; additive, `format` stays 1: an older manifest reads with `settings` null, an older release skips the member and the entry, since entries are read by name), so a restore request reads the settings without decrypting the data. The copy is taken when the run starts, before the database read, through `ISettingsBackup.CopyAsync` (Application port; the Api's `Api/Settings/SettingsBackup.cs` over `ISystemConfiguration` and `ISettingsFileStore`, registered by Program.cs before `AddInfrastructure`, whose `NoSettingsBackup` (no file) and `NoServerRestart` are the `TryAdd` defaults of a host of the backups alone, the Infrastructure tests): the file on disk (`none` without one, `ignored` when the start left it out or it no longer reads), filtered by the pure `SettingsInBackups` (Application): the instance's settings only, `SettingsCatalog.All` (a list with its items) and the `Logging` section, never the machine's (`Database`, `Storage`, `DataProtection`, `Settings`, `Backups:Path`, the bootstrap administrator, the prompt file: none of them in the catalog), and in a plain backup no secret (`SettingDefinition.IsSecret`). `BackupFile.ReadSettings` (by key; the entry's checksum first, decrypted with the identity checked against the recipient, `backup.wrongKey`; damage `backup.corrupt`), `VerifyChecksum`/`VerifyChecksumAsync` check the entry too (so an upload with a damaged one is refused), `ReadManifest` refuses an `included` without its checksum or with the other kind's entry, `IBackupStore.ReadSettings`; `decrypt` writes it as `settings.json` beside the tables (owner-only), `backup` prints what went in (`settings file <bytes> bytes, without <names>`). **The environment** (#140, `Backups:Environment` = `BackupEnvironmentMode` Record (default) | Merge, live like the group, a catalog choice with words `systemSettings.choices.backupEnvironment` (`CHOICE_SETS`); `backup --environment record|merge`, `BackupRequest.Environment`): every backup's manifest records it (`BackupEnvironment`: `mode`, `settings` (the instance's: `SettingsInBackups.IsInstanceSetting`) and `server` (the machine's: `IsMachineSetting`, `Database`/`Storage`/`DataProtection`/`Settings`/`Setup` and `SettingsCatalog.LeftOut`), by variable name (`Auth__Mode`, a list once), sorted, never a value; anything else of the process, `PATH`, the runtime's, is not named), from `ISystemConfiguration.EnvironmentKeys` (every key the sources above the settings file's place hold a non-null value for). `Merge` puts the running values of the environment's carried settings into the backup's copy (`SettingsInBackups.Merged`: a list whole, the file's items of it dropped, since the configuration merges by index; a secret only into an encrypted backup; the live file never), so a server with variables and no file writes a file. Streamed end to end (`HashingStream` counts and hashes the inner archive), written as `<name>.partial`, created new (`FileMode.CreateNew`: two runs never share one, and a run deletes only its own), flushed to disk and renamed; a dated name (invariant culture), with `-2`, `-3` when the second already has one; an existing `--output` is refused before any work. A database whose last applied migration this release does not know (a newer release migrated it) is refused, `backup.databaseNewer`: the model would leave its new tables and columns out. **Encryption is the age format exactly** (`AgeFormat` in Domain: the header, stanzas, MAC input, STREAM chunk nonces, strict unpadded base64; `AgeKeys`/`Bech32`: `age1...` recipients and `AGE-SECRET-KEY-1...` identities; `AgeStream` in Infrastructure: `Encrypt`/`Decrypt` streams, 64 KiB ChaCha20-Poly1305 chunks, `AgeX25519` wraps the file key on BouncyCastle's X25519, the version MailKit already brings), so `age -d -i` opens `data.age`; age's own passphrase mode (an scrypt stanza) is refused (`backup.passphraseEncrypted`), a wrong identity is `backup.wrongKey`, any damage `backup.corrupt`; fixtures written by age 1.3.2 in `tests/backend/contracts/age/`, and `AgeStreamTests` runs the real tool on the writer's file when it is there (else says it skipped). The identity is Argon2id of a passphrase and a 16-byte salt (`BackupKeys`, `Argon2idParameters.Default` 64 MiB/3/1, pinned with a vector; the manifest carries recipient, salt and parameters, so a passphrase is enough to open an older file); the server keeps only `Backups:Encryption:Recipient` + `Salt` (`BackupOptions`, both or neither; `Backups:Path` default `backups`, Docker `/data/backups`, must not be a storage root, inside one or hold one: `BackupOptionsValidator`), never an identity, and no passphrase, identity or path of a user is ever logged (the Information line names the file, counts and "encrypted"/"in plain"). CLI in `Api/Backups/BackupCommands` (handled in `Program.cs` before `app.Run()`, like `schema export`; no hosted service runs, so the database is backed up as it is, never migrated first): `backup [--output <file>] [--photos] [--passphrase-stdin]`, `backup keygen --passphrase-stdin` (prints the two settings and the identity once), `decrypt <file> --output <folder> (--identity <file> | --passphrase-stdin)` (`BackupFile`: manifest by name, and only a whole one `writtenBy` tankstat, else `backup.corrupt`, as a damaged entry header (`InvalidDataException`) is; checksum, the identity checked against the recipient **before** anything is unpacked, a newer `format` refused; a folder it creates is owner-only on Unix, and the plain spool `data.zip` goes in every case); a passphrase only ever comes from stdin; exit 0, or 1 with the reason on stderr (the host never starts, so options are validated when first read: an `OptionsValidationException` is such a reason, and so are `CryptographicException` and `NotSupportedException`, e.g. no ChaCha20-Poly1305 on Windows 10); `backup` says on stderr when the app's own settings file was left out (`SettingsFileStatus`: `SettingsFileReporter` is a hosted service, which a command never runs). The smoke test runs the command as a process (`AppProcess.RunCommandAsync`), `docker-smoke.sh` inside the container.
- **Restore** (`RestoreStep`: applied by `DatabaseMigrator.StartAsync` first thing at start, `RestoreStep.ApplyWaitingAsync`, before the migrations (user decision: a waiting restore first, else the backup before migrations, then the migrations), and registered as itself and as a hosted step right after `DatabaseMigrator` and before `PhotosMove` and `SetupStep`, so no administrator is created first and the setup is decided on the restored data (the backup's `InstanceState` row brings its setup state); its `StartAsync` stamps the generation of a restored backup of an older migration once the migrations ran and deletes the marker only then (a stop in between repeats the restore at the next start; that window was there in the replay before too); it also gives a fresh instance its generation (an `InstanceState` row without one, written before generations existed, too, stamped only where it is still empty, and a lost insert race read back, so two instances starting at once agree; `TableLoad` loads the backup's row and stamps a new one with `Restored`, so a backup's last start mode comes along and the start's `ModeChangeSignOut`, which runs after it, signs out the sessions it brought from another mode) and fills `InstanceGeneration`, which `Session.instance { generation restorePoint }` answers): it does nothing unless `<Backups:Path>/restore.pending` exists (`RestoreMarker`: the backup's file name, who asked, when, the identity in plain, mode 600). Then, each phase an Information line: manifest and checksum (`BackupFile`), the backup's `migration` is found among this release's **by name** (`MigrationNames.Same`: each provider's copy of a migration has its own timestamp, `mise run db:migration` makes the four one after the other, so the ids differ and the names and their order do not, pinned by `MigrationsTests`; that is what lets a backup move between providers): where the database is at it already the rows are loaded in place (one transaction, so a failure undoes itself), at another one (or empty) the database is **set up** as below (`FileBackupStore.MigrationOfAsync` gives this provider's id of it, `MigrationModels.IdOf`), one this release does not know (a newer release's) is `backup.otherMigration`; the identity must open the recipient (`backup.wrongKey`); **no backup** of what it replaces is written (user decision: the backup restored is the one there is; whatever changed since it was made is gone, and a failure after the data was replaced has no way back but restoring the backup again); unpacked into a temporary folder (`Directory.CreateTempSubdirectory`, never into the backups folder; a folder that cannot be removed afterwards is a Warning naming it, as it holds the data in plain); `TableLoad` (every table of the model in foreign-key order from `DumpTable.DependsOn`, a cycle refused: emptied in reverse, filled forward from `tables/<Table>.jsonl` in one transaction, each value parsed into the provider's type, taken back through the column's converter and written with `RelationalTypeMapping.CreateParameter`, counts checked against the manifest (also for a table whose file is missing: `backup.corrupt`, never a silently emptied table), `__EFMigrationsHistory` never written; before anything changes, from the backup's own `Users.jsonl` read by the columns its migration's model names (`UsersOf`; `Provider` stored as its name, flags as booleans or numbers), `RestoreStep.RequireAdministratorAsync`: in Standalone an enabled local administrator among them, or bootstrap credentials the start can create one from, `StandaloneBootstrap.ProblemOf`, shared with the system settings' rule; else `settings.standaloneNeedsAdministrator`, refused, since the setup step would fail every start; not with neither credential set when the backup's own setup waits, `BackupSetupWaits`: that start waits for the setup page), the `InstanceState` row stamped last inside the load's transaction for a backup of this release's last migration (`InstanceState.Restored(now, manifest.CreatedAt)` → a new `Generation`), else by `RestoreStep.StartAsync` once the migrations ran); the **contents** of the pictures root replaced (the folder itself stays: a mount point; what the app may not remove, a disk's lost+found, stays with a Warning, as a backup leaves it out), of the photos root when the backup holds it (`Separate`; on one root they join the pictures), the `*.xml` key files right inside the keys folder for an encrypted backup (only what a backup takes of it); a backup without the photos (`LeftOut`) spares the `refuelings`/`expenses` folders below the vehicles of the pictures root (one root, or photos `PhotosMove` has not moved yet: they keep matching their logs); the marker deleted. A refusal renames the marker `restore.refused.<time>` (Error line with the reason key) and the start goes on; a failure after the data was replaced `restore.failed.<time>` (an Error line; the start then migrates with no backup, as the restore branch takes none); a renamed marker is written again without the identity (it opens every backup of the folder), one that cannot be read is moved as it is; nothing there stops the start (an unreadable marker or backup, a marker naming no file, no temporary folder: refused). **Set up at the backup's migration** (`RestoreStep.SetUpAsync`, after the unpacking and the administrator rule, when the database is at another migration or empty): first `TableLoad.CheckRows` (every line of the backup's tables read as a row and every value parsed with the old model's mappings, as the load will, and the counts against the manifest's, which the checksum does not cover: what the load would refuse is refused here, before anything is removed); then every table of today's model dropped children first plus `__EFMigrationsHistory` and `__EFMigrationsLock` (`DropAllAsync`, names from the model only), in one transaction on every provider but MySQL (a drop the database refuses, a view or a foreign key of the operator's, a lock, a stop, undoes the others and the restore is `Refused` with the data as it was; MySQL commits each DROP), the point of no return (`replaced`, after which a failure is `Failed`, never `Refused`) at that transaction's commit (on MySQL before the first drop; an empty database has nothing to drop), `IMigrator.MigrateAsync(id)` up to the backup's migration (Up steps only: the path every new installation runs; Down steps are never relied on; no migration's Up drops or renames a table, so today's model names every table an older database has), the rows loaded with that migration's model (`TableLoad.LoadRowsAsync`, `MigrationModels.ModelOf`: the migration's `TargetModel`, finalized and initialized at design time like EF's own migrator, so its columns have the provider's mappings; the release's last migration loads through `TableLoad.LoadAsync` with today's model and stamps in its transaction), then the start's own `DatabaseMigrator.MigrateAsync` (the newer migrations and what follows them, the consumption backfill; no backup, the restore branch takes none) and `TableLoad.StampAsync` in `RestoreStep.StartAsync`, in a save of its own (a backup that brought no `InstanceState` row, one made before the instance recorded its sign-in mode, has every session it brought ended there: the mode they were issued in is unknown, and `ModeChangeSignOut` would take a missing last mode for a first start). After a failure past the drop the migrations still run, so the rest of the start meets its tables. `BackupWriter` dumps a database with any of this release's migrations pending (the CLI never migrates first, nor does the start's backup before migrations; a migration merged in after a later one was released is pending below the last applied one) with its last applied migration's model too, today's model only when nothing is pending, so such a backup names, and holds, what is there. `RestoreStep.Outcome` (`RestoreOutcome`: None/Applied/Refused/Failed) is what `StartupSteps.RestoreAndMigrateAsync` hands the CLI. The request side: `RestoreService.RequestAsync` (Application; `IBackupStore`, implemented by `FileBackupStore`: files by bare name in `Backups:Path` (`backup.notFound`), `IdentityFor` derives from the passphrase with the manifest's salt and parameters or parses the identity and checks the recipient (`backup.wrongKey`, `backup.keyRequired`; a recipient that is none `backup.corrupt`), `RequireRestorableMigrationAsync` (the start's own check, `backup.otherMigration` for a newer release's, refused before anything is written or restarted), `RestorePending`, `RequestRestore`, which looks for the file once more right before it writes the marker, `backup.notFound` for one deleted since its manifest was read, so no restart is asked for a restore the start would refuse): an administrator, or in mode None and while the setup waits (as the database says: `SetupStatus.PendingAsync`) the instance's `OneTimeCode` (`Application/Setup`, a singleton made per process and kept over a restart in it, 12 characters shown `XXXX-XXXX-XXXX`, compared in fixed time ignoring hyphens, spaces and case; logged at Information by `RestoreStep` in mode None, by `SetupService` while the setup waits, at Warning: `backup.codeRequired`, no lockout; see Setup); nothing secret is ever logged (canaries in `RestoreRequestTests`). GraphQL `restoreBackup(input: { file, passphrase, identity, code }) { file restorePoint }` (`Api/GraphQL/BackupGraphQL.cs`): `RestoreService` refuses a restart the next start would refuse (`NextStart.RequireStartable`, `settings.restartWouldFail`, shared with `restartServer`; not the Standalone administrator rule, which would read the users the restore replaces) before it writes the marker, then restarts in the process through `IServerRestart` like `restartServer` (no restart policy needed; `TestApp`'s `FakeServerRestart` counts it, `RestartSmokeTests` restores in a real process); `NoticeService` adds `RESTORE_PENDING` while a marker waits (worded by `notices.RESTORE_PENDING`). CLI `restore <file> [--yes] [--now] [--identity <file> | --passphrase-stdin]`: a newer release's backup refused first (`RequireRestorableMigrationAsync`, as the app does), then the marker, or with `--now` the start's two steps at once (`StartupSteps.RestoreAndMigrateAsync`: the migrator, which restores first, then the restore step's generation; only for a stopped server; an explicit flag, not a guess), saying from its `RestoreOutcome` whether the restore was applied, refused (the data as it was) or failed after the data was replaced (no backup of the data before it; the backup is still there to try again); a name that is no backup of the folder (a path) is the reason and exit 1 like every `KeyedException`, never a crash. Tests: `ProviderRoundTripTests` (opt-in: with `TANKSTAT_TEST_POSTGRESQL`, `_SQLSERVER`, `_MYSQL` connection strings, `{db}` for a database made and dropped by the test, see `docs/development.md`; CI has no servers, and this is what found the SQL Server snapshot default, the MySQL `date` and the per-provider migration timestamps: a backup is loaded into another database of the provider, and moved SQLite to the server and back, compared line by line and by value), `TableLoadTests` (a backup of A loaded into B comes out of B's backup line for line), `RestoreTests` (from an empty database, the whole replace with keys/sessions/pictures and a refresh that still works, every refusal, the ledger answering a repeated add, the one-root photos case), `RestoreRequestTests`, the smoke test runs `restore --now` as a process. `MigrationUpgradeTests` (Infrastructure: from **every** older migration of the release, a database at it is backed up at start before it is migrated and that backup restored at a later start and brought up to date, with no backup of what it replaced; a backup that cannot be written stops the migration; none for a new database or after an applied restore, one after a refused restore; a stale partial removed, one held open kept), `UpgradeTests` (API: the app started on a database an older release left, its data kept and the consumption worked out; the committed `tests/backend/contracts/backups/older-migration-AddExpenses.zip`, which every release must restore, never regenerated for a new one), `MigrationModelsTests`. **The settings file on a restore** (#140): `SettingsInBackups.Restored` leaves the backup's file plus what no backup of that kind carries from this server's own file (its machine keys, and restoring a plain backup its secrets), and `ISettingsBackup.RestoredAsync` judges it as the settings page judges a save (`ISystemConfiguration.With` + `Check`, under this server's environment) and binds the sign-in it gives (`RestoredSettings.Auth`). The request (`RestoreService.RequireStartableAsync`, shared with the `restore` command, which asks it before the marker too): problems are `backup.settingsRefused` (the settings named), a backup without a file keeps `NextStart.RequireStartable` on this server's file. The start: read and judged among the checks, before anything changes (a refusal leaves the data and the file as they were), `RequireAdministratorAsync` takes the restored file's `AuthOptions` (mode and bootstrap credentials) in both branches, the file written after the keys (`ISettingsBackup.WriteAsync`, the previous kept as `.bak`; a failure there is past the point of no return), and at the end of `RestoreStep.StartAsync` (after the stamp and the marker) `IServerRestart.RestartNow()`, which asks for the restart and throws `ServerRestartException`, so no later step runs (`SetupStep` decides the setup under the sign-in it reads, `ModeChangeSignOut` compares it) and Kestrel never listens under the file it replaced. **In a real process a waiting restore runs before the host starts**: Program.cs calls `StartupSteps.ApplyBeforeHostAsync` (`RestoreAndMigrateAsync`: the migrator, which restores first, then the restore step, as `restore --now` does; it catches the exception and returns the outcome) when `IBackupStore.RestorePending`, disposes that host and goes round the loop when a restart was asked for, so the host never starts at all (a start ended by an exception is logged as "Hosting failed to start" at Error); otherwise the host's start skips both steps once (`SkipNextStart`, asked for only there: tests start the same instance twice for two starts). Tests: `SettingsInBackupsTests` and `RestoreServiceTests` (Application), `BackupSettingsEntryTests` (Infrastructure), `RestoreSettingsTests` (API, the collection `AloneCollection` with `DisableParallelization`: a host whose sign-in comes from its file leaves `Auth:Mode` out of its in-memory settings, and `ApiFixture` sets `Auth__Mode` in the process while its tests run), `RestartSmokeTests` (a restore from the app and `restore --now`, a real process, no `fail:` line), and the setup's real-browser restore (`tests/e2e/setup.e2e.ts`: a setting saved on the shared server before its backup is there after the restore).
- **The backup before migrations** (`DatabaseMigrator`, registered as itself and as a hosted service; `StartAsync`, in the user's order: `BackupWriter.RemoveStalePartials`, then `RestoreStep.ApplyWaitingAsync`, then `MigrateAsync(ct, backupFirst: outcome is None or Refused)`): a start with migrations pending on a database that has applied ones, and no restore applied, writes a safety net through `IBackupWriter` (`BackupRequest(SafetyNet: true)`, settings as configured) of the database as it is, before anything is migrated; when it cannot be written, nothing is migrated and the start stops (`InvalidOperationException` naming the cause), user decision: an upgrade always has a way back. Not for a new, empty database, nor after a restore that was applied or failed after it replaced the data (user decision: the restore branch takes no backup; after a failed one the start migrates whatever is there with none), while a refused restore leaves the data as it was and so gets its backup like any upgrade. **Stale partials** (`BackupWriter.RemoveStalePartials`, at every start, the `restore --now` command's too): `*.zip.partial` files in the backups folder that a stopped run left (a crash, the restart loop of a start that fails), removed when an exclusive open succeeds (`FileShare.None` + `DeleteOnClose`; a run holds its partial with `FileShare.None` while it writes, so one being written stays), an Information line per file; that lock is advisory on Linux, honoured by the .NET processes of one host, not necessarily across hosts on a network share, so a partial another server is writing could go (user decision: instance ids to tell several servers apart are out of scope; they would live in the database, which the start may not have yet). A start whose migration keeps failing still writes one safety net per try (user decision: only the partials are cleaned up).
- **The Backups page** (`/admin/backups`, lazy, *Backups* in the navigation's Administration group: `admin/BackupsPage.tsx` over `admin/BackupsPanel.tsx`; administrators only through `BackupAdminService`, so mode None has only the CLI): GraphQL `backups { folder run settings }` costs nothing (`BackupAdminService.StatusAsync`) and is what the page polls while a run goes (`BackupRun`, `fetchPolicy: 'no-cache'`: an answer of only `run` would replace the id-less overview in the cache and make the full query refetch;
