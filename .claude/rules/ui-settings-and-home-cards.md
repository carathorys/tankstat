# UI settings, formats and home cards

## Settings, home cards and notices

- **Settings (`Domain/Settings`, `Application/Settings`):** what the UI remembers for a user follows them to every device. Three tables keyed by the user id with **no** foreign key to `Users` (the anonymous user of `Auth:Mode=None` has no row and shares them with every visitor; `UserDataRepository` deletes them with the user, never moves them): `UiSettings` (`NavOpen`, `Language`, `ColorMode`: Light/Dark/System, stored by name, null = Dark; `Surface`: Glossy/Transparent/Opaque, stored by name, null = Glossy, `settings.surfaceInvalid`; `TimeFormat` (TwentyFourHour/TwelveHour) and `DateFormat` (Iso, DayMonthYearDots/Slashes, MonthDayYear, YearMonthDayDots), stored by name, null = the instance's `Defaults:TimeFormat`/`DateFormat` (`VehicleDefaultsOptions`, sent as `defaultTimeFormat`/`defaultDateFormat` with `uiSettings`), else the language's own; forgotten by `clearTimeFormat`/`clearDateFormat`), `GridSettings` (per grid id: `Order`/`Hidden` as JSON text, `PageSize`, `SortColumn`, `SortDirection`, which now lives in `Tankstat.Domain`) and `VehicleOrders` (per vehicle: `Position`; FK cascade to `Vehicles`). The Domain checks shape and limits only (grid id `^[a-z][a-z0-9-]*$` and column ids `^[A-Za-z0-9_-]+$`, both at most 40, ≤ 50 per list, page size 1..500, language `^[a-z]{2}(-[A-Z]{2})?$`); what an id means is the frontend's business (`useGridSettings.merge`). `UiSettingsService` (get; the grids listed separately, `UiSettingsInfo.grids` is a resolver so they load only when selected; partial update where `ClearLanguage` wins over `Language` and an empty change saves nothing; save/reset a grid; the repository upserts and turns a lost insert race into an update, so per row the later save wins whole) and `VehicleOrderService.SetAsync` (replaces the whole arrangement; dedupes; ≤ `VehicleQuery.MaxTake`; every id must be a vehicle in the user's View scope, else `vehicle.notFound`) go through `AccessService.RequirePrincipalAsync`. `VehicleQuery.OrderedFor` (set only by `VehicleService.ListMineAsync`) makes `VehicleRepository.Page` order by `COALESCE(position, max)`, name, id; the admin list and the counts are unchanged. GraphQL: `uiSettings`, `updateUiSettings` (null = unchanged, `clearLanguage`), `saveGridSettings`, `resetGridSettings`, `setVehicleOrder`; DTOs `UiSettingsInfo`/`GridSettingsInfo` in `Api/GraphQL/UiSettingsGraphQL.cs`. Frontend: `settings/UiSettingsProvider.tsx` (mounted by `App` with `key` = user, `enabled` = signed in or mode None; asks `UiSettings` once; localStorage stays the device's write-through copy; the server's answer is adopted unless the user changed that setting this session (`touched` refs); an absent server value keeps the local copy; an unknown language is ignored; every save is fire-and-forget and serial per setting (`useSerialSaves`: one request in flight, the newest value follows); a refused save is a `console.warn`, a failed request is logged by the Apollo error link) with `settings/uiSettingsContext.ts` (`useUiSettings()`, null without a provider: a grid alone remembers in the browser); `useGridSettings` re-merges once per server answer (`settings.server` identity) when untouched; `LanguageMenu` (*Language and formats*: the language and the time and date formats as `RadioMenu` groups, each format with an example from `useFormat`'s `sampleTime`/`sampleDate`; `i18n/formatStore.ts` keeps them with the instance's defaults and the browser's copy `tankstat.formats`, `useFormat` applies them: an `hourCycle` on every time, numeric dates by `numericDate`, the date pickers' `format`; the settings page offers the two defaults by those examples, `SettingsGroupForm`'s `useChoiceLabel`; the provider takes the account's formats as they are, a null too, unless changed this session) and `AppearanceMenu` tell the server too (`setColorMode`, `setSurface`, `setTimeFormat`, `setDateFormat`; MUI switches the mode and keeps the browser's copy, `surfaceStore` the surfaces, and the server's answer is adopted unless the user changed it this session). `ArrangeVehiclesDialog` (home toolbar from two vehicles on, counted by `Welcome`'s `vehicleTotal`, not the searched count; lists at most 200; up/down buttons, a `role="status"` line, `setVehicleOrder` + refetch `Welcome`; cannot be closed while saving, and the list mounts only with the opening's own answer). Tests: `tests/frontend/support/server.ts` answers `UiSettings` (empty) and echoes the three settings mutations by default, `fakeSettingsBackend` keeps values, `fakeVehicleBackend.state.order` orders `Welcome` and answers `ArrangeVehicles`/`SetVehicleOrder`.
- **Home cards** (`components/VehicleCard.tsx`): a card's data is the `VehicleCardFields` fragment (`graphql/dashboard.graphql`), asked by `Welcome` and by `VehicleCard($id)`; a schedule's status is always `RecurrenceStatusFields` (`graphql/recurring.graphql`), so no two documents hold different shapes of one status. The quick actions (Refuel, Expense, and Done per schedule that needs attention; only for `canLogFor` in `vehicles.ts`, the vehicle page's rule too) mount the vehicle page's dialogs in the card with their own triggers (closed, they ask the server nothing: `usePhotoSession(vehicleId, purpose, open)`); the mutations live in `components/useCardActions.ts` and, once the mutation settled, ask for `VehicleCard` afresh with `client.query(..., 'network-only')` (not `awaitRefetchQueries`: a failed refresh must never make a saved log look like an error, a retry would log it twice), which updates the normalised `Vehicle:<id>` in place: never `refetchQueries: ['Welcome']` from a card or from the vehicle page (it reruns the first page and drops what infinite scroll loaded). A dialog's content is portalled but React still bubbles its events through the card: `components/cardClicks.ts` makes the click handlers ignore targets outside the card's DOM, lets the card's buttons act on the first tap (touch) and keeps the tap-away listener out of dialogs and the lists that open from them (`.MuiModal-root`, `.MuiPopper-root`). Layout: the top block (`.card-top`: title, badges, attention, actions) stays put and the figures panel (`.card-panel`) slides up from the bottom edge, revealed on `:hover` under `@media (hover: hover)`, on `:has(:focus-visible)` (not `:focus-within`: a closing dialog focuses a card button without the keyboard) or on `data-open` (touch); the card's `min-height` is `max(17rem, --top-h + --panel-h)` (a ResizeObserver on both blocks) and the list items are grids, so the cards of a row stretch to the tallest and nothing moves while one reveals; `.vehicle-card-action` sits above the link overlay with 44 px minimums. Done removes the row together with the dialog's trigger, so the card has one controlled Done dialog (`{ item, open }`, opened by the schedule's own button) and its `onClosed` moves the focus to the title link when that button is gone. jsdom lays nothing out: heights and the hover/focus reveal are checked by hand. Test fakes answering `Welcome`/`VehicleCard`/the recurring documents must carry `__typename` on vehicles, schedules and statuses (`fakeVehicle`, `typedRecurring` in `tests/frontend/support/mocks.tsx`): a typed fragment never matches an untyped object; the log, expense and recurring fakes change a vehicle's `summary`/`recurring` in place, so hand them the vehicle backend's own objects (`backend.state.vehicles[0]`).
