# Photos of logs and upload folders

## Photos, uploads and shared building blocks

- Photos (`Application/Photos`, `Domain/Photos/LogPhoto`): up to 10 photos per refueling or expense, one `LogPhoto` table for both kinds (log id without a foreign key, like `ResourceGrant`; cascading foreign key to the vehicle). `LogPhotoAccess` applies the vehicle's *logs* rules through `LogAccessGuard`, the one place (shared with `RefuelingService`/`ExpenseService`) that decides who may see or edit a vehicle's logs (View to see and to GET `/media/{id}`, Edit to add/remove; trashed logs hide their photos); `LogPhotoService` adds/removes; `IExpenseRepository`/`IRefuelingRepository.PurgeAsync` return `PurgedLogs`, delete the photo rows in the same save, and the services then remove the folders. Upload is `PUT /media/expenses|refuelings/{logId}/photos`, remove is `DELETE .../photos/{imageId}`; GraphQL only has the read field `photos { id url }` (batched per response by `ExpensePhotosLoader`/`RefuelingPhotosLoader`, which trust the already authorised parent log). Photos picked for a log that is not saved yet are uploaded at once as `PhotoDraft`s (`PhotoDraftService`; `PUT /media/vehicles/{id}/photo-drafts`, `DELETE /media/photo-drafts/{id}`; id = the image id, folder `vehicles/<id>/drafts`, visible to the uploader only, Edit on the vehicle's logs to upload, at most 20 per user and vehicle, expired after a day and removed whenever anyone uploads a draft, so no background job; only a picture still in the draft folder is deleted with its row (`ImageService.DeleteDraftPicturesAsync`): one moved out is a photo or a vehicle's picture, even when a failure left its row behind); `logRefueling`/`addExpense` take `photoIds`, which `LogPhotoService.RequireDraftsAsync` checks before the log is saved and `AttachDraftsAsync` turns into its photos afterwards (the file moves into the log's folder; a draft that cannot be attached goes back and never fails the save, the response's `photos` tell the UI). The frontend `PhotoGallery` (+ `usePhotoQueue`/`usePhotoSession`: per-photo uploading/uploaded/failed with retry, Save waits for uploads, closing the dialog deletes its drafts, `PhotosLeftOut` when the server attached fewer) has a camera input (`capture="environment"`) and a library input; photos are resized to 1600 px in the browser.
- Upload folders: `StoredImage.Folder` (null = legacy file directly in `Storage:Path`) built only from ids by `ImageFolders` (`users/<id>`, `vehicles/<id>/picture`, `vehicles/<id>/drafts`, `vehicles/<id>/expenses|refuelings/<logId>`); `FileSystemImageStore` re-validates the folder. Two roots with the same layout below them (`ImageFolders.RootsOf`): the pictures (`Storage:Path`: avatars, vehicle pictures, legacy files) and the photos of logs (`Storage:PhotosPath`, **opt-in**: drafts and log photos, which grow without limit; unset or blank = the very folder of `Storage:Path`, so nothing moves on upgrade, `StorageOptions.PhotosRoot`; the Docker image does not set it but makes `/data/photos` owned by the app's user, so a volume of its own there is writable (`docker-smoke.sh` mounts one with `Storage__PhotosPath=/data/photos`); the two may be one folder, never nested, `StorageOptionsValidator` refuses that at start); the store resolves a folder against its root, a draft made a vehicle's picture moves between them (`File.Move`, which copies between disks; never `Directory.Move`), and a photo still in the pictures root is read, moved and deleted there, because `Infrastructure/Storage/PhotosMove` (a hosted service right after `DatabaseMigrator`) moves those file by file at every start (counts at Information, a file it cannot move is a Warning, and so is a folder it cannot read, after which the rest moves; a part of a photo that a copy between disks cut short left at the target is removed, since the store looks there first; it never stops the app); the Seeder deletes the photos folder too when one is set (`--photos`, else `Storage:PhotosPath`). Purging a vehicle removes `vehicles/<id>` with everything below it under both roots (`ImageService.DeleteVehicleFilesAsync`). New kinds of uploads belong in a folder below their owner. Deleting a user (`UserDataRepository`) moves `LogPhoto` (and `PhotoDraft`) owner/creator along with the logs, or purges the vehicles; `UserService` then removes the purged vehicles' folders and `users/<id>`.
