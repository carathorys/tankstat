# Expenses, imports and recurring expenses

## Expenses, imports and recurring expenses

- Expenses (`Expense`, `ExpenseService`) are non-fuel costs of a vehicle (free-text category, optional odometer reading); they use the vehicle's *logs* access rules and trash like refuelings. Importing (`Application/Imports`): one `IImportParser` per format turns a file into an `ImportBatch` (`FuelioCsvParser` first); `ImportService` keeps the batch under a token in `ImportSessionStore` (in memory, 30 minutes, per user), previews duplicates and commits row by row through `RefuelingService`/`ExpenseService`/`RecurringExpenseService` (schedules last, so a distance schedule without a known odometer starts from the imported readings), so all rules apply and bad rows are reported, not fatal; repeating Fuelio reminder templates become `ImportedRecurring` (duplicates: same title). A new format = a new parser + its tests; the UI (`pages/ImportPage.tsx`) lists formats in `FORMATS`.
- Recurring expenses (`Domain/Recurring`, `Application/Recurring`): `RecurringExpense` is a schedule of a vehicle (kind Time, Odometer or Combined = whichever is reached first; interval in months and/or distance; baseline = last done date and odometer; per-item warn days/distance). It is not a cost (no `Cost`) and its baseline odometer is a plain number, not an `OdometerReading`, so it never takes part in neighbour validation. `RecurrenceCalculator` (pure) turns it plus today and the vehicle's latest reading into a `RecurrenceStatus` (Upcoming/DueSoon/Overdue, which limit decides, days and distance left); the service computes it on every read, nothing is stored (`Vehicle.recurring` goes through `RecurringByVehicleLoader` -> `ListForVehiclesAsync`, so a list of vehicle cards costs a fixed number of queries, not several per card). `RecurringExpenseService` uses the vehicle's *logs* access rules through `LogAccessGuard` (like expenses and photos); `MarkDoneAsync(ids, input)` marks a service visit: schedules of one vehicle (another vehicle's or an unknown id is `recurring.notFound`; ids deduped; none is `recurring.noneSelected`), one Edit check, `CheckDone` on every one first (its errors carry the schedule's `title`: `doneBeforeLast`, `doneOdometerRequired`, `odometerBelowLast`; `Apply` keeps `recurring.odometerRequired`), then, when an amount or photos came, ONE `Expense` through `ExpenseService` (all expense/odometer/photo rules; title/category default to `RecurringDoneDefaults`: titles joined and cut at 120, common or first category, the note only for a single schedule), then `CompleteAsync` saves the moved baselines and the `RecurringCompletion` links (expense id + schedule id) in one save; a failure trashes the expense (`TryTrashAsync`). All or nothing; the amount is never split. `RecurringCompletions` has one foreign key, cascading from the schedule; the expense side has none (expenses and schedules both cascade from the vehicle, and SQL Server refuses two cascade paths), so `ExpenseRepository.PurgeAsync` removes the links in code like photo rows. `Expense.schedules { id title }` comes through `ExpenseSchedulesLoader` (the Expenses grid's `schedules` column, `defaultHidden`). Schedules are hard-deleted (no trash); the table cascades with the vehicle and `UserDataRepository` moves or purges them. GraphQL: `Vehicle.recurring`, `add/update/deleteRecurringExpense`, `markRecurringExpensesDone` (`{ schedules, expense }`), `Expense.schedules`. UI: the vehicle page's Recurring tab (`RecurringPanel` with a selection column and *Mark selected as done*, `RecurringFormDialog`, `RecurringDoneDialog`: the vehicle's schedules as labelled checkboxes, `recurringDone.ts` `preselect` ticks the clicked one plus every other one not `UPCOMING` of its category (#161, `sameCategory`: both non-empty once trimmed, compared by one `Intl.Collator` of the runtime's default locale with `sensitivity: 'accent'`, made on first use and kept (`localeCompare` with options would build one per call, for every row on every render), so case does not count and accents do; one without a category starts alone; the `DoneItem` type requires `category`, so a list without it does not compile), optional amount, title/category prefilled from the ticked ones until typed) and, on the home cards, attention badges (`useDueText`, `RecurringStatusBadge`) each with a Done button that opens `RecurringDoneDialog` right there (see Home cards).
