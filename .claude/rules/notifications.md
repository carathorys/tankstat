# Notifications

## Notifications

- Notifications (`Domain/Notifications`, `Application/Notifications`): a `Notification` belongs to its recipient only (not `IOwned`; every query filters by `RecipientId`, admins included) and is attached to a subject and an optional context by `NotificationRef` (entity type + id, no foreign key; a new source adds a `NotificationEntityType`). Its identity (unique index) is recipient + topic + subject + context id (`Guid.Empty` when none) + `Occurrence`. Every producer goes through `Notifier.NotifyAsync(actorId, drafts)` (the actor is never notified); the pure `NotificationPolicy` decides: *derived* drafts (with an occurrence, worked out from current state) are added once and only raised to a more urgent kind (reopened); *events* are folded into the unread one of the same topic/subject/context (`Count`), removed when undone (`After == Before`), and past `Notifications:MaxPerHour` become one `MoreActivity` digest. Sources: `ResourceSharingService` and `AccessAdminService` (events built with `NotificationArgs.AccessChange`, `Before`/`After` = access levels), `SyncNotificationSync` (`SyncChangeParked`, topic `Sync`, subject `SyncChange`, context the vehicle, occurrence `parked`: every parked change the reader may see as themselves or sent; args `change` (kind in API spelling), `vehicleName`, `submitterName`, `reason`, `reasonArgs` as JSON), `BackupFailureNotifier` (`BackupFailed`, topic `Backup`, derived, subject `Instance`, occurrence the server's local date of the run: every enabled administrator, the anonymous user in mode None, args `error` (a key), `errorArgs` (its arguments as JSON, like `reasonArgs`) and `startedAt`; see Backups), `ImportRunNotifier` (#337, topic `Imports`, subject `ImportRun`: the starter gets `ImportFinished` (args `count`, `names`, `refused`), `ImportNotFinished` (`reason`, the failure) or `ImportCancelled` (`actor`; only when someone else cancelled), every enabled administrator but the starter `CarsImported` (`actor`, `count`, `names`); the first three lead to `/import?run=<id>`, whose report is kept 7 days; see Imports), `TyreReminderSync` (#292: `TyreSwapDue`, topic `Tyres`, derived, subject `TyreSet`, context the vehicle, occurrence the season's `yyyy-MM`, args `set`, `season` (API spelling), `vehicleName`: every due set of `TyreService.ListRemindersAsync` over the vehicles of `ITyreRepository.ListReminderVehicleIdsAsync` in the personal scope; the swap or a dismissal removes nothing, the next season raises a new one; worded by the season, linked to `?tab=tyres`), and `RecurringNotificationSync`, which, like `SyncNotificationSync` and `TyreReminderSync`, runs lazily once per request from `NotificationService` (no background job) over `AccessService.PersonalLogScopeAsync` (an admin's blanket rights do not count; anonymous keeps everything), one occurrence per schedule cycle (last done date + odometer). Arguments are display-ready snapshots; the frontend words them per kind (`notifications/useNotificationText.ts`, `notifications.kinds.*`; a kind the bundle does not know, from a newer server while an older tab waits for its update, is `notifications.unknownKind` without a link, never a crash: the bell is outside the error boundary). Users never delete notifications (deliberate): they only mark them read (`ReadAt`; `markNotificationsRead` returns the changed rows so Apollo updates loaded lists in place), and `NotificationService` purges the ones read more than `Notifications:ReadRetentionDays` ago on the same lazy path, keeping reminders of schedules and tyre sets that are still due and of changes still parked (else the sync would re-add them). UI: `shell/NotificationBell.tsx` (polls the unread count every minute; tests get an empty-inbox default handler from `src/frontend/tankstat-react/tests/support/server.ts`, override with `fakeNotificationBackend`) and `pages/NotificationsPage.tsx`. User deletion purges the inbox; actions go through `notifications/useNotificationActions.ts`.
- **During a run** (#335, `runs.md`): on SQLite the inbox is read as it is and brought up to date by the next look after the run.
- **A partial restore** (#340, `ImportRunNotifier`, topic `Imports`, all after the commit, nothing after a rollback): the administrator who ran it `RestoreFinished` (no actor), the other administrators `CarsRestored`, and each restored car's owner and everyone its logs are shared with then `CarRestored` (subject the vehicle, args `how` = `back` (entries came back, those that took the backup's values again counted too), `replaced` (a kind replaced, `kinds` the codes), `again` (a gone car's owner: it is theirs again) or `changed` (only a tyre set without lines, a chart, the picture or a dashboard came: said without a count, the owner's answer on #376), `count`, `vehicleName`, `date` the backup's day; a car still here that got nothing back tells nobody, the owner's answer); a restore that did not finish or was cancelled by another administrator `RestoreNotFinished` / `RestoreCancelled`. An owner of many cars gets one per car up to `MaxPerHour`, the digest after. The bell links the administrator's to `/admin/backups/restore?run=`, a car's to the vehicle.
